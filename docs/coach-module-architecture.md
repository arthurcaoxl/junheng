# 教练模块全景架构梳理

## 1. 文档目标与范围

本文归集菌衡计划打卡 App 中用户、教练、店员与平台后台的业务关系，说明一盒一码、打卡同步、教练雷达、归属托管及后续迭代边界。

宏观 CEO 沙盘只接收另行审批的聚合快照，不与打卡 App 共用代码、数据库写入链路或纯函数引擎。本文不构成生产发布或数据库执行授权。

## 2. 角色与核心实体

### 2.1 角色

| 角色 | 核心职责 | 权限边界 |
| --- | --- | --- |
| 营员／用户 | 凭体验码或充值码激活、每日打卡、查看个人记录 | 匿名 `auth.uid` 是认证主体；本机 `userCode` 是档案标识，不是登录凭证 |
| 教练 | 服务营员、拿货发码、查看名下脱敏雷达、跟进补货 | 只能查看自己名下或经授权范围内的数据，不得读取其他教练数据 |
| 店员／助理 | 协助教练进行客情跟进 | 只能查看被分配教练的雷达数据，不得查看财务分润；1:5 为 UI 软提示，不作数据库硬阻断 |
| Admin／平台运营 | 审核、查看全局码状态、处理归属及休眠托管 | 仅限 `camp_admins` 白名单；所有特权操作必须审计 |
| 主任务／子任务／验证者 | 协同研发与验收 | 详见第 7 章，不得互相越权代替物理执行 |

### 2.2 核心数据实体

- `box_codes`：产品码、类型、状态、来源教练、激活关联及版本事实。
- `code_activations`：唯一激活事实、审核与激活主体、幂等和审计信息。
- `user_coach_relation`：当前及历史教练归属，保存 `referrer_id`、来源码和有效期。
- `user_profiles`：受限用户档案；`phone` 为可空业务联系方式，不承担认证功能。
- `box_code_commands` / `box_code_events`：命令幂等、领域事件和审计证据。
- `box_code_attempt_guards`：防爆破失败窗口与阻断状态。
- `camp_admins`：平台管理白名单及角色边界。

## 3. 端到端业务流

### 3.1 教练准入与箱码生成

1. 教练本人完成 21 天营且有效打卡不少于 18 天，并扶持 8 名去重用户完赛。
2. 平台完成人工准入审核后，方可解锁拿货和发码资格。
3. 每生成一箱，系统在同一原子操作中预生成 24 个同类型、`unused` 状态的唯一产品码。
4. 体验码格式为 `JH-EL-XXXX`，充值码格式为 `JH-RC-XXXX`；字符集排除易混淆字符。
5. 可分配库存只统计 `unused` 码；默认补货预警线为 12，数量小于 12 时预警。

### 3.2 用户激活与教练绑定

1. 用户在 `/check-in` 输入产品码，或通过 `?code=...` 自动填入。
2. 前端复用统一格式校验；码面不得进入公共日志、分析事件或非必要持久化。
3. 系统取得匿名或已认证会话的 `auth.uid`，服务端只信任自身 `auth.uid`，不得接受客户端指定 uid。
4. 激活必须经过契约规定的审核与状态机，禁止把 `unused` 跳过审核直接改为 `active`。
5. 激活、打卡授权、归属写入和审计在同一原子流程内完成；任一失败不得留下部分成功状态。
6. 首次有效激活建立当前 `referrer_id`；用户 `auth.uid` 与本机 `userCode` 均不改变。
7. 一码一用，不得解绑、复用或改绑其他用户。相同请求按幂等键返回首次结果，并发争抢最多一个成功。
8. 新设备输入已激活码时必须拒绝，并引导“通过绑定邮箱找回”，不得重新绑码。

### 3.3 打卡与云端同步

1. 激活成功后，用户直接开始打卡，不再被日常强制绑邮箱弹窗拦截。
2. 数据按现有同步契约静默上传；邮箱只用于登录和跨设备找回。
3. 手机号只作为选填业务联系方式，文案为“选填手机号，方便您的教练为您提供更好的指导”。
4. 衣物扣减按每日快照保存，修改今日默认值不得篡改历史净重。
5. 既有无码老用户的兼容和灰度行为必须在 Staging 单独验证，不能与新用户准入口径混为一谈。

### 3.4 教练雷达

`get_coach_radar_v1` 以当前有效归属关系为数据边界，教练只能查看自己名下或经明确授权范围内的营员。

每条结果只允许返回：

- `camper_code`
- `weight_delta`
- `waist_delta`
- `bmi`
- `alert_level`

灯号由 SQL 服务端派生：

- 红灯：距最后打卡大于等于 3 天、从未打卡，或结营未复购。
- 黄灯：距最后打卡等于 2 天。
- 绿灯：其余正常状态。

新激活但从未打卡的用户必须立即出现在来源教练雷达中，且为红灯；不能因为 inner join 打卡记录而漏人，也不能通过重复关联产生笛卡尔积。`null` 指标在 UI 显示 `--` 或“待首测”，严禁显示为 `0`。

### 3.5 复购、休眠与托管

1. 体验码不计入教练月新增付费用户；充值码用于复购、延伸营或维持期。
2. 已有当前归属时，充值码不得改绑到发码教练。
3. 教练当月新增低于 4 人进入 `buffer`，连续两月满足条件进入 `dormant`；统计采用自然月和 `Asia/Shanghai` 时区，每月 1 日跑批。
4. 休眠托管后，用户 `auth.uid` 与本机 `userCode` 不变，仅当前 `referrer_id` 转移至平台官方账号。
5. 托管后的复购不回绑原教练，不计提原教练差价；历史关系和原始激活事实不得删除。

## 5. RPC 与数据安全

| RPC | 用途 | 关键边界 |
| --- | --- | --- |
| `activate_box_code` | 产品码激活、授权与教练绑定 | HMAC 核验、匿名 `auth.uid`、Advisory Lock、幂等、防爆破、原子写入 |
| `get_coach_radar_v1` | 教练脱敏雷达 | SQL 层物理脱敏、归属隔离、防漏人、防笛卡尔积、五个规范字段 |
| `admin_get_box_code_overview` | Admin 查看全局码状态、绑定教练和联系方式 | 仅 `camp_admins` 白名单；不得返回原始 `height`、`weight` 或 `records` |

统一红线：

1. 浏览器只使用 `anon key`，`service_role` 不得进入前端、仓库、日志或报告。
2. 所有权威写入必须经过受控 RPC 与 RLS，前端不得直接修改码、激活或归属事实。
3. 普通日志、公共事件和错误响应不得泄露完整码面、原始健康档案或原始打卡记录。
4. 已合并 migration 不得原地改写；新变更只能新增 migration，并先经 Staging 验证。

### 6.9 全链路标准化工作流（SOP 2.0）

以下四阶段为所有任务必须遵守的执行流程：

1. **阶段一【工单登记】**：主任务分配编号、登记 `AGENTS.md`、commit push、汇报真实 Hash，然后休眠。
2. **阶段二【环境准备】**：裁判负责完成以下环境铺路动作：
   1. 拉取最新 `main`，确认工作区和真实 HEAD 与任务基线一致。
   2. 运行 `pre-flight.sh`，完成物理状态校验。
   3. **切隔离区**：执行 `git switch -c <分支名>`。
   4. **🔥 远端推流（必做）**：立刻执行 `git push -u origin <分支名>`。确保云端有此分支，杜绝子任务 AI 因为找不到分支而自行基于旧代码乱建。
   5. **下发令箭**：把工单需求、物理契约要求、以及**远端分支名**，打包发给子任务。子任务第一句话必须是 `git fetch origin && git switch -c <分支名> origin/<分支名>`。
3. **阶段三【子任务开发】**：子任务先出方案，测试先行，只改边界内文件，全量测试通过后 push，回传 `git diff --stat`。
4. **阶段四【合并闭环】**：裁判使用 `--no-ff` 合并并 push 主干，将最终 Hash 发给主任务；主任务更新 `WORKLOG.md` 后最终 push。

**角色越位禁令：** 任何角色严禁越位，包括但不限于主任务越权编写业务代码、子任务越权修改登记表、跳过 `pre-flight.sh` 物理校验。前一阶段未完成并形成真实物理证据，不得进入下一阶段。

### 6.11 避坑指南（Pitfall Guide）

**避坑一：裁判切了分支，但忘了 push 到远端。**

- **现象**：本地建了分支，直接让子任务去拉取。子任务 AI 报错找不到，于是基于旧代码自建同名分支，导致平行宇宙。
- **规避动作**：裁判建完分支后，**必须立刻 push 到远端**，并下发包含 `git switch origin/分支名` 的强制指令。

**避坑二：AI 网络断连，试图用 GitHub API 伪造 Commit。**

- **现象**：AI 无法 push，试图调用 API 强推假节点。
- **规避动作**：严禁 AI 尝试任何 Git CLI 之外的发布通道。断网即停机，交出 `git diff` 文本，由裁判在本地主工作区人工落盘合并。若遇到 GitHub 443 端口超时或网络拒绝，严禁尝试任何 API 绕过，立刻停止操作并报告裁判，等待裁判在本地终端代为推送。

**避坑三：AI“偷懒”式伪实现。**

- **现象**：要求删按钮，AI 只加 CSS 变灰，未删 `onClick` 事件。
- **规避动作**：测试用例必须断言“元素／特定文案不存在”，而非仅仅断言样式变化。裁判需紧盯红灯测试的设计。

## 7. 多模型协同与物理契约规范

### 7.1 唯一事实源原则

以 `docs/WORKLOG.md`、物理基线文件和真实 `git HEAD` 为唯一事实源，不信对话记忆、口头状态或过期摘要。任何“已落盘、已合并、已推送、已发布”的声明都必须对应可核验的物理证据。

### 7.2 物理状态校验

开工前必须运行：

```bash
bash scripts/pre-flight.sh
cd apps/web && npm test
```

当前要求为 46 个测试文件／342 项测试全绿。pre-flight 只证明 Git 基线关系，不能替代测试、构建、Staging 或安全验收；测试数量变化必须同步更新物理基线，不得沿用旧数字。

### 7.3 云端沙盒防幻觉机制

重要文档、契约、Checklist 和验收证据必须由裁判在本地通过 `git status`、文件内容及提交记录确认真实落盘。工具文字回复、计划、附件预览或对话承诺均不能代替本地文件和 Git 证据。

### 7.4 目录与副本隔离纪律

终端首步必须 `cd` 锁定唯一工作仓库的绝对路径，再执行任何 Git 或文件操作：

```bash
cd /Users/mac/Documents/kimi/tasks/2026-11-04/11-46-42-f918d595/checkin-contracts-1105
```

不得混用 1101、1103、1104 或其他副本，不得把沙盘与打卡 App 代码互相拷贝。路径、HEAD 或工作区异常时立即停止。

### 7.5 文件级 staging、防夹带与个案复盘对照表

严禁 `git add .`。只能按明确文件路径点名暂存，提交前必须执行 `git status` 和 `git diff --cached --stat`，核对实际暂存文件与任务边界。合并前还必须重新获取远程更新，锁定目标 HEAD，并用 `git diff --stat` 与任务书文件清单逐项核验。

| 事故／现象 | 根因 | 物理规避原则 |
| --- | --- | --- |
| 裁判在本地建了分支，子任务拉不到，自己建同名分支开干 | 裁判忽视 AI 只有远端视野，无本地视野 | 远端推流原则：裁判建分支必 push，子任务基于远端分支开工 |
| AI 网络推不上去，试图通过 GitHub API 强推伪造节点 | AI 执念完成推送，缺乏物理边界意识 | 纯 Git CLI 原则：断网即停机交 diff，严禁 API 绕过 |
| 要求删按钮，AI 只加灰色 CSS 就交差 | AI 缺乏业务语义，追求最小 Diff | 语义验收原则：测试断言必须针对元素移除或文案，不认样式篡改 |

### 7.6 物理脱敏绝对红线

敏感字段必须在 SQL 层物理剥离，只返回契约允许的字段。前端隐藏、CSS 遮蔽、 TypeScript 类型省略或“页面看不到”均不算脱敏。验收必须抓取 RPC 原始 JSON 响应，确认任意层级均不含原始 `height`、`weight`、`records` 及可还原这些数据的字段。

### 7.7 职责边界

- 裁判：执行真实 Git／数据库／发布操作或单独授权，确认物理落盘，裁定方案、验收与上线。
- 主任务：登记编号与里程碑、分发任务书、审核边界、执行经授权的合并及更新公共登记文件，不代写业务代码。
- 子任务：在指定分支和文件边界内进行方案设计、测试与代码实现，交付真实红灯／绿灯及文件清单。
- 验证者：独立审查测试、权限、脱敏、并发和联调证据，不以开发者自证代替验收。

任何角色发现状态不一致时立即停止后续动作，回到 WORKLOG、真实 Git HEAD 和物理文件重新裁定。
