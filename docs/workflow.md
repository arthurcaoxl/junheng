## 二、开工前准备：修好 AGENTS.md（主任务对话）

> 通用规则：仓库根目录的 AGENTS.md 是"项目宪法"——版本、技术栈、规范、分支登记表、Git 纪律都在里面。
> 每个对话开工第一步必须读它。菌衡计划现状：AGENTS.md 版本号停在 v1.9.0（落后实际 v1.13.3），且缺登记表和 Git 纪律两节。

**发给主任务对话的 Prompt（直接复制）：**

```text
【当前任务】更新项目文档（不改任何业务代码）：
1. 工作目录：/Users/mac/Documents/kimi/tasks/2026-11-01/01-00-49-f5325b61/junheng-repo
2. 打开根目录 AGENTS.md，把版本号 v1.9.0 更新为 v1.13.3；
3. 在"技术栈与现状"部分补充：测试基线 291 项；
4. 在文档末尾追加两节：

## 分支登记表
| 编号 | 分支名 | 简述 | 状态 | 备注 |
| --- | --- | --- | --- | --- |
| （空表，由主任务在派工时登记） |

## Git 纪律
1. 禁止任何对话直接 push main；
2. 分支命名：feature-<编号>-<简述> / bugfix-<编号>-<简述>，编号全局唯一；
3. 子任务只允许改自己边界内的文件；公共文件只能由主任务在 main 上改；
4. 子任务 push 前若 main 有更新，先 merge origin/main；
5. 合并必须 --no-ff，保留分支痕迹；合并后删除远程分支并更新本表。

5. 完成后 git commit（message: docs: 更新 AGENTS.md 至 v1.13.3，补登记表与 Git 纪律）并 push；
6. 汇报 commit hash。
```

| 【通用模板规则】 | 【菌衡计划具体实操】 |
| --- | --- |
| 版本号、基线数据必须真实，文档与线上状态一致。 | 线上 v1.13.3、基线 291 项——照实写，别让文档再掉队。 |
| 登记表从第一天就建，编号从 1 开始不复用。 | 当前空表，今天第一个分支就是 feature-1-xxx。 |
| 纪律写进 AGENTS.md，所有对话每轮都可见。 | 上面 Prompt 第 4 步已含全文，主任务会代写进文件。 |

## 三、派发第一个子任务：替换 8 处旧域名

> 通用规则：派工时给"关键词"而不是"路径"，让子任务 rg 搜索定位，不许通读项目。
> 本任务特点：改动点早已明确（8 处 og/canonical），属于"小而明确"型，是练手的最佳第一个任务。

**第一步：先在主任务对话登记派工（生成模式）**

```text
我要派一个子任务：替换 index.html 与 public/h5/index.html 中 8 处旧域名的 og/canonical 标签，
新域名生效后立即执行。请分配编号、按模板 D 生成完整子任务 prompt（边界只限这两个文件）。
```

**第二步：把主任务生成的 prompt 审核后转发给新子任务对话。**
若主任务生成效果不理想，可用手动版（直接复制下面这段）：

```text
【角色】你是子任务对话，只负责【替换旧域名 og/canonical 标签】这一个任务，做完即归档。

【仓库】junheng-repo（主任务对话已告知你路径；先读根目录 AGENTS.md 和 Git 纪律）

【需求】
- 位置：index.html 和 public/h5/index.html，共 8 处旧域名的 og:url / canonical 标签；
- 动作：旧域名全部替换为新域名 <填你的新域名>；
- 要求：只改这两类标签，不顺手改页面其他任何内容；
- 自测：替换后 rg 反向搜索旧域名，这两个文件中必须 0 命中。

【开工步骤】
1. git fetch origin && git switch -c feature-1-domain origin/main；
2. rg -n "og:url|canonical" index.html public/h5/index.html 列出全部命中（应该正好 8 处，数量不对先停下问我）；
3. 执行替换；
4. rg 反向搜索旧域名确认 0 命中；npm run build 确认构建无报错；
5. commit（fix: 替换 og/canonical 旧域名共8处）并 push 分支；
6. 输出：改动文件清单 / 替换前后对照（每处一行）/ 构建结果 / 风险点（如：是否需要等 DNS 生效后再合并）。

【边界】只许改 index.html 和 public/h5/index.html；禁止 push main。

【纪律】数量对不上、发现第 9 处、或需要动其他文件时，停下来问我。
```

| 【通用模板规则】 | 【菌衡计划具体实操】 |
| --- | --- |
| 任务粒度：10~30 轮完成、≤15 文件、验收条目 ≤5 条。 | 本任务 2 个文件、1 条验收（8 处换完+0 命中），完美粒度。 |
| 交付物是"分支 + 输出报告"，不是"对话里说做完了"。 | 验收要看：push 的分支 + 替换前后对照表 + 反向搜索 0 命中。 |
| 风险如实上报（此处：新域名 DNS 是否已生效）。 | 子任务 prompt 第 6 步已要求它自报——合并时机由你判断。 |

## 四、开发过程中的检索纪律（rg 怎么用）

> 通用规则：关键词优先于路径；`rg -l` 先要清单；改完反向搜索防漏。

| 【通用模板规则】 | 【菌衡计划具体实操】 |
| --- | --- |
| 第 1 层 `rg -l "关键词"`：只列文件名，先确认范围。 | `rg -l "旧域名"` —— 全库还有哪些文件藏着旧域名？决定是否要追加任务。 |
| 第 2 层 `rg -n "关键词" 文件`：带行号看命中处。 | `rg -n "og:url\|canonical" index.html public/h5/index.html` —— 正好定位那 8 处。 |
| 第 3 层：只有要改的文件才完整读。 | 本任务两个 html 都很小，直接读全文没问题。 |
| 改完反向搜索 = 验收证据。 | `rg -n "旧域名" index.html public/h5/index.html` 返回空 → 截图存证。 |

## 五、VS Code 人工验收的标准动作

> 通用规则：对话里说的"测试通过"只是转述，你在 VS Code 里亲眼所见才是事实。
> 在 VS Code 打开 junheng-repo 文件夹，集成终端执行：

```bash
git fetch origin
git switch main && git pull
git merge --no-ff origin/feature-1-domain --no-commit   # 先不合入，纯看改动
```

| 【通用模板规则】 | 【菌衡计划具体实操】 |
| --- | --- |
| Source Control 面板逐文件看 diff。 | 只看 2 个 html；重点：是不是只动了 og/canonical 8 行，有没有夹带私货。 |
| 本地复跑构建+测试（DeepSeek 产物的硬性要求；Kimi 产物同样建议）。 | `npm run build && npm test` —— 291 项基线必须全绿。 |
| 不满意就中止，回对话返工。 | `git merge --abort` 一键回到合并前，零污染。 |
| 满意才提交合并并 push。 | `git commit -m "merge: feature-1-domain"` → `git push`。 |

```bash
git merge --abort   # 验收不通过时执行；通过后不需要
```

## 六、合并与归档

**验收通过后，发给主任务对话：**

```text
【验收合并发布】feature-1-domain 已由我在 VS Code 本地验收通过（291 项测试全绿）：
1. 执行合并：git switch main && git pull && git merge --no-ff feature-1-domain，push；
2. 删除远程分支 feature-1-domain；
3. 更新 AGENTS.md 分支登记表：1 号登记状态改为"已合并"；
4. ⚠️ 暂不发布：该改动等新域名 DNS 生效后再上线，发布前提醒我；
5. 汇报：合并 commit hash、登记表更新结果。
```

| 【通用模板规则】 | 【菌衡计划具体实操】 |
| --- | --- |
| 合并后删远程分支、更新登记表，编号不复用。 | 1 号用完即弃，下一个任务是 2 号。 |
| 发布走契约文档（docs/contracts/publish.md），构建/预览≠发布。 | 本任务特殊：合并不发布——域名标签要等 DNS 生效，发布动作留给你手动触发。 |
| 子任务对话改名归档，不再使用。 | "📦菌衡-子任务1-换域名" → "✅已合并-换域名-待发布"。 |
