# 代码审查专家库 (EXPERT-RULES V1.0)

> **文档定位**：五角架构最高质量防线。所有 AI 产出的代码，在通过契约 D（功能验收）和契约 E（反向交卷）后，必须由“代码审查专家 Agent”对照本规则库进行物理审计。
> **核心原则**：能跑通不代表没隐患，单测全绿不代表线上不崩。性能、安全、并发、健壮性是工业级代码的底线。
> **适用边界**：本规则库作为 Runbook 的 `E-C7 代码质量审核`，仅强制适用于**核心链路**（库存扣减、发码核销、高并发 RPC、状态机流转等）。纯 UI 文案或非核心静态页面可由裁判书面声明豁免。

---

## 一、 数据库与 RPC 工程红线（P0 / P1）

1. **防并发超卖（P0）**：
   - 任何涉及余额、库存、剩余次数的扣减 RPC，必须使用 `SELECT ... FOR UPDATE`（行级锁）。
   - 必须在同一个事务（Transaction）中完成查询、校验与扣减。
   - 数据库层面必须有约束兜底（如使用 `ON CONFLICT DO NOTHING` 配合唯一索引，防止高并发下的双写穿透）。
2. **防全表扫描（P1）**：
   - RPC 或前端直连的查询，凡涉及 `WHERE`、`JOIN`、`ORDER BY` 的字段，必须在迁移文件中显式建立 Index（索引）。
   - 严禁在千万级数据表上进行无索引查询。
3. **底层扩展路径（P0）**：
   - 任何使用 `pgcrypto`、`uuid-ossp` 等扩展的 PL/pgSQL 函数，必须强制声明 `set search_path = public, extensions;`。
   - 严禁裸写函数导致线上 42883 报错。
4. **物理脱敏（P0）**：
   - 涉及手机号、邮箱、ID 等隐私数据，必须在 SQL/RPC 层进行 `md5`、`hmac` 或 `regexp_replace` 脱敏后返回给前端。
   - 严禁前端使用 `.filter()` 做假脱敏。
5. **事务死锁防御（P1）**：
   - 多表更新时，必须严格按照统一的 LOCK_ORDER（如：先锁用户表再锁库存表）执行。
   - 严禁交叉加锁导致死锁。

---

## 二、 前端与性能工程红线（P0 / P1）

1. **防请求风暴（N+1 问题）（P0）**：
   - 严禁在前端的 `for` / `map` / `forEach` 循环中发起 `supabase.rpc` 或 `fetch` 请求。
   - 必须先聚合数据，再进行批量请求。
2. **防内存泄漏（P1）**：
   - 所有包含 `useEffect` 的异步请求、`setInterval`、`addEventListener` 操作，必须在 `return` 清理函数中进行取消订阅或卸载。
   - 异步请求建议使用 `AbortController` 取消未完成的网络请求，防止页面卸载后内存溢出。
3. **防白屏兜底（P0）**：
   - 所有的网络请求和业务逻辑，必须包裹 `try-catch` 或使用 `.catch()`。
   - 严禁未捕获的 Promise Reject 导致整个 React 组件树崩溃（白屏）。
4. **状态防抖（P1）**：
   - 表单输入触发的实时搜索、高频点击的按钮，必须加入防抖（Debounce）或节流（Throttle），防止击穿接口。

---

## 三、 架构与安全工程红线（P0）

1. **鉴权物理化（P0）**：
   - 所有 RPC 内部，必须通过 `auth.uid()` 进行身份与角色校验（如校验 `camp_admins` 角色）。
   - 严禁仅依赖前端路由的隐藏或禁用（前端拦截仅供体验，服务端拦截才是防线）。
2. **严禁硬编码（P0）**：
   - 凡涉及业务参数（限额、有效期、倍数、状态阈值），必须从 `SystemConfig` 动态读取。
   - 严禁出现 `if (count === 24)` 或 `const max = 30` 等字面量。
3. **无死角日志（P1）**：
   - 对于重要数据的删除、审核、划拨操作，必须强制写入 `audit_logs` 或 `inventory_logs`（且为 append-only）。
   - 保证资金、额度与资产流向 100% 可追溯。

---

## 四、 测试与验证红线（P0）

1. **Mock 隔离（P0）**：
   - 单元测试可以使用 Mock，但交付给裁判的实机截图和证据，必须连接真实的 Supabase 环境。
   - 严禁使用 Mock 数据截图糊弄交付。
2. **测试防篡改（P0）**：
   - 在未获得裁判书面批准前，严禁修改 `*.test.ts` / `*.spec.ts` 中的断言来换取绿灯。
   - 必须遵守 Runbook 中的契约 D.5（测试改动三分法）。

---

## 五、 专家审查工作流 SOP (E-C7)

1. **触发条件**：核心链路交付合并前。
2. **自审要求**：1104 或开发子任务交卷时，必须附上一份《E-C7 代码审查自审报告》，逐条核对上述红线。
3. **裁判审计**：裁判将 `git diff` 与《自审报告》对比，也可调用独立的 AI 代码审查 Agent 进行二次复核。
4. **裁定标准**：
   - 存在 P0 级问题：直接打回重做，阻断合并。
   - 存在 P1 级问题：记录 DEBT 带债发布，或退回修复。
   - 仅有 P2 建议或无问题：准予合并。

---

## 六、 专家库进化机制 (持续补充)

1. **事故驱动**：每一次线上 Bug、并发 500、数据回滚等 INC 级事故闭环时，必须反向提炼一条新的审查红线入档。**没有沉淀新规则，事故单不允许 closed。**
2. **独立 Commit**：修改 `EXPERT-RULES.md` 必须走独立的文档提交，如 `docs(expert-rules): add rule for XXX`。严禁在业务代码提交中夹带对专家库的修改，违者按“夹带私货”红线驳回。
