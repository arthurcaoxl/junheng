# AI研发流水线操作手册与五角架构 Runbook V2.3.4

**v2.3.4（正式运行完整版）**

- **文档性质**：裁判（人类）操作手册 + AI 交接模板库 + 物理防线宪法。
- **版本定位**：本版替代 v2.3.3-final，作为正式上线运行版。v2.3.3-final 及更早版本归档保留原貌，不作为后续流程依据。本版新增「门禁总则：P0-P3 风险分级管控（敏捷模式）」，E-C 清单相应扩展至 E-C7。
- **核心原则**：只认 Git 物理输出、测试退出码、真实数据库落库结果；绝不信模型口头记忆。主脑无手，裁判无脑，中枢无情，测试无情。
- **适用范围**：派单、开发、验收、合并、推流、事故归档。
- **声明**：本文件为 RUNBOOK 本体，不是交付包；契约 C 机械自检针对交付包，不针对本手册。本版不批准任何 push；push 仅由裁判在门禁通过后执行。

## 一、角色绝对边界（严禁越权）

| 角色 | 边界 |
| --- | --- |
| **主脑（架构审查）** | 只下发业务边界与工单指令，不读长日志，不做物理事实认定。 |
| **裁判（人类，物理执行）** | 派单、建沙盒（worktree）、采集归档证据、按契约 A/B/C 组装交付包、门禁通过后执行 push；拥有物理覆盖（cp）与合并冲突最终处置权，以及 Gx 分级（P0/P1/P2）判定权。 |
| **1104 / PM（并发调度）** | 绝对禁止亲自写业务代码或 SQL；负责建隔离沙盒、拆模块、派子任务、汇总交卷；汇总必须附各模块实机证据。 |
| **逻辑中枢（Tech Lead）** | 只写 [BIZ] 字典契约；找不到边界的业务标 [待确认] 并停机，严禁脑补。 |
| **开发子任务（Coder）** | 在隔离沙盒写代码；严禁跨模块、严禁改测试制造伪绿、严禁伪造截图。 |
| **裁决接口（门禁）** | 只按冻结 Gx 核验证据，只引用 Gx 编号驳回，只给 open / evidence_submitted / closed 判定；不写新叙述，不替代裁判做物理事实认定。 |

## 二、十一道绝对红线（L1 铁律，违者直接打回）

1. 禁止 `git add .` / `git add -A`；只允许显式 `git add <file>`。
2. 默认禁止修改既有测试文件。确需调整测试的，必须按契约 D.5 三分法逐项归类说明；类型 D（删除或弱化断言换绿灯）红线驳回。
3. 禁止 Mock 假全绿。涉及 UI/RPC 交付，必须提供契约 D 六件交付物；单元测试全绿不构成交付。
4. 禁止硬编码业务数值。倍数、限额、次数、有效期必须由 SystemConfig 单一来源驱动；验收须做"改配置 → 看变化"行为级测试。
5. 禁止口头汇报。必须按契约 E 的 E-C1 至 E-C6 逐条填空交卷；缺真实终端输出、Diff、截图或 SQL 原文的，直接打回。
6. 禁止跨范围修改。新发现的独立 Bug 只记录并上报，另开 -R 子工单；严禁顺手塞进当前工单。
7. 禁止口头判定分叉。分支关系唯一判据：`git merge-base --is-ancestor A B` 退出码；`git merge --ff-only` 试跑仅作辅助，且不得改变工作区。
8. 禁止 `cherry-pick --skip`。遇多父节点 Merge，必须用 `git cherry-pick -m 1 <hash>` 拆包；禁止 `git cherry-pick A..B`。
9. 禁止未授权 push。push 仅由裁判在门禁通过后执行；严禁 `--force` / `--force-with-lease`。
   终态洁净度三档要求：
   - **实施期**：工作区允许存在未提交文件，但须按契约 A.2 在交付包第一页列明清单与原因；
   - **交付期**：`git status -sb` 不得出现 M；如有 ?? 文件须逐名列明；
   - **push 前**：`git status -sb` 不得出现 M / ??；`[ahead N]` 为 push 前正常状态，push 后须消失。
10. 断网即停机。网络失败立刻输出状态停机；严禁越权强推、伪造提交或调用外部接口伪造记录。
11. 严禁滥用 Feature Flag 掩盖缺陷。系统引入的灰度开关（如 SystemConfig 中的配置）仅用于旧业务向新业务平滑过渡；开关上线满 2 周必须清理并移除，违者按"技术债违规"打回。细则见第八章门禁总则。

## 三、契约 A：交付包两段式与证据治理

### A.1 两段式交付

- **叙述段**：允许精简，不作为裁决依据。
- **证据段**：SQL 全文、终端输出、查询结果、截图与 .txt 转写，原样透传。
- 禁止改写、转写代写、记忆库调取、模板拼装、二次加工。
- 截图必须附执行者生成的 .txt 转写，同路径、同名加 `.txt`。

### A.2 第一页组成

交付包第一页必须同时包含：

1. 契约 C 机械自检命令与输出原文；
2. worktree 状态声明：`git status -sb` 原文；实施期/交付期如有未提交文件，须列明清单与原因。

二者缺一，按契约 C 驳回。

### A.3 证据段四要素

每条证据必须包含：

1. **命令**；
2. **输出原文**；
3. **执行环境**；
4. **执行时间**。

缺任一项按"证据不完整"处理。

### A.4 证据环境标注

所有 HAR、F12、数据库、终端证据必须标注：

- 工作树 HEAD：`git rev-parse HEAD` 输出；
- 迁移清单：`supabase migrations list` 或等价输出；
- 执行环境：本地 / 预发 / 生产；
- 执行时间。

无标注按"来源未知"处理，对应 Gx 不得据此 closed。

### A.5 证据同源律

- 证据必须产生于被测 HEAD。
- 旧 HEAD、旧环境证据仅作对比参考，不得作为 Gx closed 依据。
- 标注旧 HEAD 证据且用于 closed 判定，按"来源不合格"驳回。

## 四、契约 B：清单冻结、状态机与时间盒

### B.1 冻结清单

- 工单下发即锁定 G1…Gn，中途不得新增。
- 新增范围必须开 -R 子工单并说明理由；-R 不改变主单冻结清单本身。
- 同一 Gx 不得重复提出；重开须注明"原关闭证据失效原因"。

### B.2 状态机

- 状态只允许三值：`open → evidence_submitted → closed`。
- closed 必须引用证据：文件路径与哈希，或截图路径与 .txt 路径。
- 无证据引用不得写 closed。
- 驳回只引用 Gx 编号，不写新叙述。

### B.3 时间盒

- 同一 Gx 往返上限 2 轮（往返 = 一次交卷 + 一次驳回）。
- 第 2 轮未 closed，开 -R 隔离；主单该 Gx 冻结，不再往返。
- 2 轮时间盒与进化模式 3 次独立计数，不互相抵扣；任一触发即冻结代码流转。
- 禁止第 3 轮往返。

## 五、契约 C：提交前机械自检

### C.1 扫描对象

扫描对象限定为交付包的证据段、伪 SQL、模板字段与第一页声明。RUNBOOK 本体不参与扫描。

### C.2 扫描模式

以下模式命中任一即拒绝提交。为避免自检自命中，模式以码位与说明表述：

| 模式 | 说明 |
| --- | --- |
| `U+FF08` 紧跟"粘贴" | 全角左括号后接"粘贴"二字 |
| `U+005B` 紧跟"填入" | 左方括号后接"填入"二字 |
| `U+005F` 连续四次 | 连续四个下划线 |
| `U+003A` 后接两个 `U+005F` | 冒号后接两个下划线 |
| `U+002E` 连续三次 | 连续三个英文句点 |
| `U+7565` 单字 | 单独出现的"略"字 |
| `U+5DF2` 后接"归档" | "已"与"归档"连用 |
| `U+5F85` 后接"填" | "待"与"填"连用 |
| `U+5F85` 后接"补" | "待"与"补"连用 |
| `T B D` 连用 | 三个大写字母连用 |
| `U+2026` | 中文省略号 |
| "省略"连用 | 两个汉字连用 |
| "参见"连用 | 两个汉字连用 |

### C.3 白名单

- 伪 SQL 或伪代码中需指代既有实现，一律写为 `/* 见 Lxxx */` 或 `/* 见 <文件>:<行号> */`，不得使用省略标记。
- 合法引用统一写"见 \<路径>:\<行号>"，不得写"参见"。

### C.4 扫描命令与输出

扫描命令与输出原文作为交付包第一页附件。扫描命中数必须为 0；非 0 直接驳回，不进入裁决。

## 六、契约 D：功能验收门禁与六件交付物

### D.1 定义

凡涉及前端交互的 Gx，关闭条件必须包含"本地端到端人工验收记录"。无此记录，状态不得为 closed。

### D.2 记录格式

1. 启动命令与本地 URL，如 `npm run dev` 与 `http://localhost:<端口>`。
2. 验收剧本：逐步操作序列，体现"用户能否完成一次完整业务动作"。
3. 整体验收证据为契约 D 六件交付物，缺一即 evidence_submitted，不得 closed：
   - **①** 操作前状态截图，含 URL 上下文；
   - **②** 操作后状态截图，与 ① 同视角对比；
   - **③** 截图 .txt 转写，执行者生成，与截图同路径同名；
   - **④** F12 请求真实 Payload 与 Response 原文，含 URL、方法、状态码、关键字段；
   - **⑤** 服务端落库证据：关键表变更前后行数或字段值，用 SQL 查询原文佐证；不适用时按 D.2 第 4 条前置判断登记 DEBT；
   - **⑥** 逐步操作剧本，与 ① 至 ⑤ 逐条对应。
4. 证据必须由执行者在本地真实启动后产生，不得复用历史截图；按契约 A.3/A.4 标注环境与时间。
5. 剧本逐步对应 ① 至 ⑤；六件为整体验收证据，不要求每一步重复六件。

#### D.2 第 4 条落库证据适用性前置判断

- 当 Gx 验收对象是"前端不挂载 / 不发起请求"时，无写入则无落库变更，落库证据场景不适用。
- 处理方式：书面说明"受限 RPC 未发起、无写入"，登记 DEBT，不阻塞验收。
- 禁止用 RPC 响应 JSON 冒充落库查询 SQL 原文。

### D.3 F12 200 的定位

F12 200 降级为辅助证据，不是功能正确的充分条件。主证据是操作前后状态对比、服务端落库查询结果与完整剧本。

### D.4 状态约束

| 情形 | 状态 |
| --- | --- |
| 无本地 E2E 记录 | open 或 evidence_submitted |
| E2E 记录不完整（缺前后对比，或落库适用时缺落库证据） | evidence_submitted |
| E2E 完整且落库证据一致，或落库不适用已登记 DEBT | closed |

### D.5 测试改动三分法

交付涉及测试文件改动时，必须逐项归类：

| 类型 | 说明 | 判定 |
| --- | --- | --- |
| 类型 A | 纯 Mock 注入 | 合规 |
| 类型 B | 查询改异步等待 | 合规 |
| 类型 C | 断言语义变化 | 须逐项说明，归因须指向本任务范围 |
| 类型 D | 删除或弱化断言以让测试通过 | 红线驳回 |

禁止把多文件测试改动打包成"适配重构"一句话糊弄过关。裁判交付前复核测试 Diff，逐条对质。

### D.6 契约-实测矛盾排查四选一

出现"契约要求 X，实测返回 Y"时，严禁直接判定代码缺陷，必须按顺序排查：

| 排查项 | 说明 |
| --- | --- |
| **A. 旧环境** | 证据取自旧 HEAD 或旧环境；附 HEAD 与迁移清单佐证。 |
| **B. 迁移未应用** | 目标环境迁移清单缺该迁移；附 schema_migrations 清单。 |
| **C. 后续迁移覆盖** | 同名定义被后续迁移覆盖；附同名定义佐证。 |
| **D. 真代码缺陷** | A、B、C 全部排除后，才可判定为代码缺陷。 |

排查期间优先下发只读排查令；严禁边查边改。

## 七、契约 E：E-C 反向交卷验收法

### E.1 编号隔离

- 契约 E 校验项统一前缀为 E-C1 至 E-C6，与业务冻结清单 G1…Gn 物理隔离。
- 裁决接口引用时不得省略前缀：E-C3 不得简写为 C3 或 G-C3。
- E-C 清单放入派单的"交卷格式"，不放入业务冻结范围。
- 本手册 E-C1~E-C6 为通用交卷清单；单工单可特化扩展（如 TASK-10.16 的 E-C7~E-C9），特化清单以派单原文为准，引用时须带工单编号前缀。

### E.2 标准 E-C 清单

| 编号 | 门禁项 | 强制物理证据 |
| --- | --- | --- |
| **E-C1** | 文件与 Diff | `git status` 与 `git diff --stat` 原文，证明只改了允许改的文件。 |
| **E-C2** | 红转绿证据 | 修复前报错原文（红灯）与修复后通过原文（绿灯）。 |
| **E-C3** | 实机与网络 | 真实页面渲染截图（含 URL 上下文）与 F12 Network 原文；同时满足契约 D 六件交付物。 |
| **E-C4** | 落库验证 | SQL Editor 或 psql 查询业务数据原文与结果；不适用时显式声明理由并按 D.2 登记 DEBT。 |
| **E-C5** | 测试防篡改 | 证明未修改既有测试文件，或按 D.5 三分法逐项说明改动类型。 |
| **E-C6** | 终态洁净度 | `git status -sb` 原文；push 前不得出现 M / ??，`[ahead N]` 为正常；实施期与交付期按红线 push 条三档要求。 |

### E.3 交互标准

当 AI 汇报"已完成，请求合并"时，裁判直接回复：

> 请逐条汇报本次任务分配的 E-C1 至 E-Cx 的物理校验结果。没有真实终端输出、Diff、截图或 SQL 原文的，直接打回重做。

### E.4 与既有契约关系

- 契约 E 不取代契约 A/B/C/D，而是交卷动作的强制外壳。
- E-C4 与 D.2 适用性判断联动；E-C5 与 D.5 三分法联动；E-C6 与红线 push 条三档联动。
- 同一 Gx 的 E-C 驳回记录是进化模式触发计数依据。

## 八、门禁总则：P0-P3 风险分级管控（敏捷模式）

为防止一刀切导致的生产力停滞，所有代码变更按影响范围执行分级门禁：

| 级别 | 定义 | 门禁要求 |
| --- | --- | --- |
| **P0（硬核金流/底层校验）** | 如 verify_checkin、库存扣减 | 必须执行全套 E-C1~E-C7 审查，禁止任何豁免。 |
| **P1（重要业务逻辑）** | 如雷达数据聚合、教练托管 | 执行 E-C1~E-C4 + E-C7 简化版。 |
| **P2（前端 UI/文案/样式）** | 如调整布局 | 执行 E-C1（Diff）+ E-C3（截图），TDD 绿灯即可直接合并。 |
| **P3（紧急 Hotfix）** | 生产止血 | 允许"先修车后补票"。裁判必须口头声明"降级"，并强制创建 DEBT 跟踪，24 小时不补齐 E-C 报告直接锁死主干。 |

### 8.1 E-C7 扩展项定义

本章引用的 E-C7 为分级门禁扩展项，与契约 E 的 E-C1~E-C6 配套使用：

| 编号 | 门禁项 | 强制物理证据 |
| --- | --- | --- |
| **E-C7** | 分级人工复核 | P0：裁判对高风险操作做人工复算/对账记录（含对账 SQL 原文与结果）；P1：简化版，人工复核关键路径一次并留痕；P2/P3：不适用，须显式声明。 |

单工单可对 E-C7 做特化扩展，特化清单以派单原文为准，引用时须带工单编号前缀（同契约 E.1 规则）。

### 8.2 证据采集绝对纪律

- 证据必须**原样透传**，禁止任何 AI 生成器或一键脚本对终端输出进行提炼、转述或加工。
- 严禁使用带 `|| true` 或吞掉退出码的脚本伪造测试全绿假象。自动化脚本只能用于检查，不得替代真实退出码判定。
- 裁判必须直接复制 `git diff --stat` / `git status -sb` / `npm test` 的终端原始回显。

### 8.3 Feature Flag 管控细则（对应红线 11）

- 系统引入的灰度开关（如 SystemConfig 中的配置）仅用于旧业务向新业务平滑过渡，禁止用于掩盖缺陷或未完成的实现。
- 开关上线满 2 周必须清理并移除；未清理的强制挂 DEBT 跟踪（级别不低于 P1），未清理前锁死主干合流。

### 8.4 敏捷分级的反滥用防御

1. **降级一票否决**：AI 为逃避 E-C7 审查，故意将 P0 降级申报为 P1/P2 的，裁判拥有绝对一票否决权。凡涉及资金、库存、发码、状态机流转，直接按 P0 盲审，不接受申辩。
2. **全量测试防雪崩**：即使是 P2 级 UI 改动，合并前裁判必须亲跑一次主分支全量测试，确保测试基线数量不缩水，防级联崩溃。
3. **Flag 死锁主干**：Feature Flag 落地满 2 周未清理，强制挂 DEBT 跟踪，未清理前锁死主干合流。

### 8.5 与其他契约的关系

- 本章不取代契约 A/B/C/D/E，而是门禁执行的分级外壳；各契约的物理证据要求不变，仅按级别裁剪执行项。
- P3 降级 Hotfix 仍须遵守契约 A/B 与红线 push 条；E-C 报告 24 小时补齐后按正常级别归档。
- 分级判定权归裁判，判定结果须写入交付包第一页；AI 不得自行申报级别。

## 十、合并、复跑与推流 SOP

### 10.1 C.0 合并路径优先级

1. **首选**：`git merge --ff-only <branch>`。严格超集时直接快进，无冲突、无 merge 节点。
2. **次选**：`git cherry-pick -m 1 <merge>` 逐节点拆包。仅限历史遗留含 Merge 节点的非超集分支，且须裁判批准。
3. **新交卷分支**：必须保持线性历史，禁止 merge 节点；不得使用 C.0 次选。

**禁止：**

- `git cherry-pick A..B`；
- `git cherry-pick --skip`；
- `git reset --hard <中间节点>` 作为换位置手段；
- `git pull` 产生 merge 节点；
- 子任务自行解决 cherry-pick 冲突。

### 10.2 合并前检查

```bash
git log --oneline --graph <base>..<branch>
git merge-base --is-ancestor <base> <branch>; echo $?
```

- 基线关系唯一判据为 `--is-ancestor` 退出码；`--ff-only` 试跑仅辅助，且不得改变工作区。
- 确认分叉时交 1104 开合并工单重构提交序列，裁判不手工解冲突。

### 10.3 取代码与防缩水

```bash
git fetch <沙盒路径> <分支名>
git cherry-pick -m 1 <hash>
```

- 遇 CONFLICT 严禁子任务自行解决；裁判在主工作区手工文本级合并，`git add` 冲突文件后继续。
- 自动合并无冲突但测试大面积崩溃时，禁止 AI 逐行修 bug；裁判去源沙盒 `cp <原版> <目标>` 物理覆盖。
- 合并后必须比对测试基线数量：测试项减少即不合格；用 `git log -S '<丢失测试关键字符串>' --oneline --all` 溯源并强制补合。

### 10.4 契约冲突裁决

Markdown 台账冲突时：

- 保留 HEAD 的历史痕迹；
- 采纳 Incoming 的新版本号与新条目；
- 手工清理重复条目；
- 严禁 Accept Both 污染台账；
- 严禁 Incoming 覆盖抹掉 HEAD 已登记历史。

### 10.5 复跑

```bash
bash scripts/pre-flight.sh
npm test -- --run --reporter=dot
```

只看终端退出码与测试计数；不认截图替代终端原文。

### 10.6 push 前三条核对

```bash
git status -sb
git log --oneline -1 main
git ls-remote origin main
```

- `git status -sb` 不得出现 M / ??；`[ahead N]` 为 push 前正常状态，push 后须消失。
- 本地 HEAD 与远端 HEAD 关系明确。
- 缺一不得 push。

### 10.7 push

```bash
git push origin main
```

仅裁判执行；禁止 `--force`、`--all`、`--tags`。

### 10.8 push 后三条核对

```bash
git ls-remote origin main
git log --oneline -1 origin/main
git status -sb
```

- 远端等于本地 HEAD；
- origin/main 最新；
- 不再 ahead。

缺一不算闭环。

## 十一、只读排查令

当需要 AI 辅助定位问题但不允许其动手时，裁判下发只读排查令。排查令必须写死：

> 不改代码、不 commit、不 push、不 git add、不 rebase。

- 每条排查项要求：命令、输出原文、一句话事实说明。
- 查不出的写"查不出"并列出缺什么输入，不许推测。
- 排查结果不直接 closed 任何 Gx，只作为裁决依据。
- 违反"五不"的，本次排查证据全部作废重采。

## 十二、急诊排障与 Hotfix 止损

### 12.1 PostgREST 缓存死锁

- **症状**：迁移已应用，但实机调用持续 404 或 schema cache 报错，AI 反复修代码无效。
- **处理**：先在 SQL Editor 直接执行该函数 SELECT，验证数据库层可调用；数据库层通、REST 层不通即缓存问题。执行 `SELECT pg_notify('pgrst', 'reload schema');` 或重启 PostgREST。
- **铁律**：缓存未刷新前，严禁修改业务代码。

### 12.2 pgcrypto 42883

- **症状**：实机调用 RPC 返回 500/404，日志报 function 解析失败。
- **处理**：函数声明补 `set search_path = public, extensions`；重新 apply 迁移后必须实机调用一次真实 RPC；检查扩展是否安装在 extensions 模式。

### 12.3 Hotfix 止损 SOP

1. **冻结 main**：暂停一切合流与 push，通知 1104 挂起在途功能工单。
2. **定位稳定基线**：`git tag -l` 找最近稳定 Tag；无 Tag 以最后一次 push 后三条核对全通过的 HEAD 为准。
3. **切出止血分支**：`git switch -c hotfix/<编号> <稳定Tag>`。
4. **最小修复**：只收止血必需改动，走完整契约 A/B/C/D/E。
5. **独立验收合并**：hotfix 单独过门禁，裁判按 10.6 至 10.8 推流；推流后打新稳定 Tag。
6. **功能线归位**：被冻结功能分支 rebase 到新 main，由 1104 开合并工单按 C.0 归队。

## 十三、-R 子工单规范

### 13.1 定义与触发

-R 用于：

- 主单冻结清单 G1…Gn 之外的新增范围；
- 执行中新发现的独立 Bug；
- 主单某 Gx 因实施范围变更需重新界定。

触发须书面写明"新增范围、对应主单 Gx、不改变主单冻结清单本身"。

### 13.2 编号

- 格式：`<主单编号>-R<两位数>`，如 `TASK-10.16-R-01`。
- 不得复用旧 -R 编号；撤销的编号作废不复用。
- 历史非标编号（如 `...-G-S3-R2`）按旧编号作废处理，新工单一律按本节格式。

### 13.3 冻结与状态机

- -R 下发即冻结自己的 GR1…GRn。
- 状态机与主单同构：`open → evidence_submitted → closed`。
- -R closed 不自动使主单对应 Gx closed；主单须单独呈报并附 -R closed 证据引用。

### 13.4 与主单关系

- -R 不改变主单冻结清单。
- -R 的 Gx 与主单 Gx 同名时加前缀区分，如主单 G-S1 与 -R 的 GR-S1。
- -R 往返轮次独立计数，不占用主单"同一 Gx 往返 2 轮"额度。

### 13.5 时限

- -R 默认 1 轮闭环。
- 第 2 轮不齐，回主单重新界定；不开嵌套 -R。

## 十四、DEBT / INC 台账规范

### 14.1 DEBT

- **编号**：`DEBT-<三位数>`，按登记顺序递增，不复用。
- **字段**：DEBT-ID | 描述 | 级别 | 关联 Gx | 期限 | 状态 | 登记人 | 登记日期
- **状态机**：`open → closed`；禁止 debt_registered 等野值。

**带债发布分级：**

| 级别 | 规则 |
| --- | --- |
| P0 | 不可带债；P0 Gx 未 closed 前不得以 DEBT 替代。 |
| P1 / P2 | 可登记 DEBT 带债发布，发布说明须列明 DEBT-ID 与影响面。 |

- **DEBT closed 条件**：关联 Gx closed 且证据引用路径或哈希已入档。

### 14.2 INC

- **编号**：`INC-<工单号>-<两位数>`，如 `INC-1015-01`。
- **字段**：INC-ID | 标题 | 级别 | 状态 | 防御条款引用 | 关联 DEBT
- **状态机**：`open → recorded / closed`；禁止 debt_registered 等野值。
- 转 DEBT 用"关联 DEBT"字段引用，不改 INC 状态为 debt_registered。

**INC closed 条件：**

1. 根因条款已写入 RUNBOOK 事故库；
2. 防御手段已在后续工单生效，附证据引用。

### 14.3 裁决引用

- 裁决接口只引 DEBT-ID 与 INC-ID，不写新叙述；
- 野值状态直接驳回，要求按状态机重报。

## 十五、进化模式

- **触发**：同一工单或同一 Gx 发生 3 次及以上同质化驳回，立即启动进化模式。
- **强制冻结**：冻结该任务代码流转，禁止继续修改业务代码。
- **契约重构**：裁判将反复踩坑的漏洞提炼为 E-C 标准项，补入本次派单的交卷格式。
- **降维打击**：下发固定填空模板，强制逐条交卷；答不齐即打回，终结自然语言辩论。
- **计数独立**：进化模式 3 次与时间盒 2 轮独立计数，不互相抵扣。
