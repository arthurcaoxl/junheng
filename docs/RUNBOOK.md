## 第一部分：五角架构核心铁律

1. **只认物理**：只认 Git 物理输出（hash、log、status）、测试退出码与真实数据库落库结果，绝不信任何口头汇报或"大概"。
2. **契约即代码，配置即外置**：所有业务规则必须在契约中有物理映射；严禁在 SQL/前端中硬编码密钥、UUID、业务规则。
3. **防呆与脱敏**：物理脱敏必须在 SQL/RPC 层完成（如 Vault），严禁依赖前端遮罩；断网即停机，沙盒必 commit。
4. **最小权限**：新建 RPC 必须包含 `auth.uid()` 角色校验。严禁使用 `git add .`。
5. **密钥入 Vault（P0 拆弹教训）**：严禁在托管型数据库（如 Supabase）使用 GUC 参数（如 `ALTER DATABASE <库名> SET app.xxx_pepper`）硬编码密钥——该操作会被平台权限直接拒绝。所有高敏配置必须推入平台原生保险库（如 Supabase Vault），RPC 层通过 `vault.decrypted_secrets` 动态读取。
6. **终态必净（适用范围澄清，BUG-233-10）**：
   - **push 前**：`git status -sb` 必须仅含 `## main…origin/main`，无 `M` / `??`；
   - **实施期 / 交付期**：允许 staged / unstaged 文件存在，但交付包第一页须声明当前 worktree 状态与未提交文件清单；
   - 实施期未提交文件不得跨工单滞留：工单 `closed` 前须 commit 或物理删除。
7. **合并黑洞防御**：遇到多父节点 Merge Commit，**严禁 `cherry-pick --skip`**。必须使用 `git cherry-pick -m 1 <hash>` 拆包，取主分支视角的净变更；若拆包异常，立即中断排查，严禁蒙眼推进。
8. **Mock 隔离律**：任何前端测试的绿灯，绝不等于真实环境的绿灯。Mock 数据只能用于单元测试，绝不许充当联调证据。涉及前端交互的交付，关闭条件必须满足契约 D（本地 E2E 人工验收记录）；F12 Network 200 仅为辅助证据，不是功能正确的充分条件。
9. **底层扩展可见律**：Supabase (PostgreSQL) 中自定义函数若调用了 `pgcrypto` 等底层扩展，`search_path` 必须包含 `extensions`（如 `set search_path = public, extensions`），否则将触发 42883 崩溃（function pgcrypto 函数解析失败），导致前端无端 404。新建/迁移 RPC 后必须实机验证一次真实调用。
10. **UI 物理视觉验证强制律**：任何涉及 UI 变更、页面挂载或组件联调的交付，必须提供真实环境（`npm run dev`）的浏览器端渲染截图与 F12 Network 面板对应请求日志，并按契约 D 补齐操作前后状态对比与服务端落库证据。缺一即判交付不合格。截图必须包含完整页面上下文（URL 栏 / 路由可见），严禁裁剪局部冒充整体。
11. **业务参数同源律（24 倍数教训）**：任何业务数值（如 24 倍数、限额、次数、有效期）必须由 SystemConfig 单一来源驱动，UI 与 RPC 严禁各自硬编码。验证必须做"改配置 → 看变化"的行为级测试：裁判临时修改 SystemConfig 值，实机观察 UI/RPC 输出是否同步变化。不同步即业务脱节，直接打回。
12. **迁移唯一事实源（V2.3 红线）**：数据库结构变更必须以迁移文件为唯一事实源。任何手工变更（Dashboard 直改、SQL Editor 直执行）必须登记，且必须被后续迁移文件吸收，否则视同未发生。
13. **生产迁移独立审批（V2.3 红线）**：生产环境迁移必须走独立工单审批，不得与预发合并、功能合并捆绑执行。准备方案可以先行，执行必须单独放行。
14. **契约 D 六件交付物验收（V2.3.1 红线；BUG-233-04 术语统一）**：严禁"纯截图验收"。凡涉及前端交互的交付，验收证据必须包含**契约 D 六件交付物**：①操作前状态截图；②操作后状态截图；③截图 `.txt` 转写（执行者生成，与截图同路径同名）；④F12 请求真实 Payload / Response 原文；⑤服务端落库 SQL 查询原文及结果（不适用时按 D.2 第 4 条前置判断登记 DEBT）；⑥逐步操作剧本。缺一即判验收不合格。
15. **测试防篡改律（V2.3.1 红线）**：严禁通过修改测试断言、删除用例、放宽匹配条件制造伪绿。**交付前必须由裁判复核测试文件的 Diff**，对测试改动按契约 D.5 三分法逐项归类；出现"删除/弱化断言以让测试通过"（类型 D）一律红线驳回。
16. **级联缺陷隔离律（V2.3.1 红线）**：修复过程中新发现的独立 Bug，必须另开 `-R` 子工单跟踪，严禁顺手塞进当前工单扩大修复范围；工单范围以冻结清单 G1…Gn 为唯一边界。
17. **Hotfix 物理隔离律（V2.3.1 红线）**：当 main 被功能蔓延污染、或出现必须立即止血的线上缺陷时，冻结 main 的合流，基于最近稳定 Tag 切出 `hotfix/<编号>` 分支，止血修复仅在 hotfix 分支内闭环，严禁与进行中的功能分支互相污染。
18. **push 权限铁律（V2.3 红线）**：严禁未授权 push。push 仅由裁判在门禁通过后执行；严禁 `--force` / `--force-with-lease`；严禁 `git add .` / `git add -A`。
19. **基线关系判定（V2.3.2 新增；final 修订）**：分支基线关系的首选判据为只读命令 `git merge-base --is-ancestor` 的退出码；`git merge --ff-only` 试跑**仅作辅助验证**。**禁止**以"两个 merge-base 不同值"判定"分叉"。禁止 `reset --hard` 作为换位置手段；禁止 `git pull` 产生 merge 节点。确认分叉时，交由 1104 开合并工单重构提交序列，不交裁判手工解冲突。

## 第二部分：角色定义与启动（含交接 Prompt 模板）

### 角色定义

- **1104（项目经理 / Orchestrator / 执行）**：**绝对禁止亲自下场编写业务代码或 SQL**。负责主仓库之外的沙盒建立（`git worktree`）、大需求拆解、向开发子任务派发模块级工单、汇总各模块 commit 与测试结果。交卷汇总必须包含各模块的实机联调证据，无证据的模块不许进入合并队列。
- **裁判（人类 — 采集、归档、提交）**：派发标准 Prompt、操作主工作区（建沙盒、多模块合并）、采集并归档物理证据、按契约 A/B/C 组装交付包并提交裁决接口、在门禁通过后执行 push。**拥有物理覆盖（cp）与合并冲突的最终处置权。强制索要真实环境截图、Network 日志与本地 E2E 验收记录，Mock 绿灯一律不认。**
- **裁决接口（门禁检查与放行判定）**：**不是人格化角色**，不做任何叙述与二次加工；不读长日志，只读交付包第一页机械自检输出 + 证据段原文。只做三件事：
  1. 按冻结清单 `Gx` 核验证据；
  2. 引用 `Gx` 编号驳回（不写新叙述）；
  3. 给出 `open / evidence_submitted / closed` 状态判定。
- **逻辑中枢（子任务 0 — Tech Lead）**：不写业务代码，只负责将长文档提炼为结构化契约（TypeScript Interface），产出《业务逻辑中枢字典》。文档没写清的业务边界直接标注 `[待确认]`，严禁脑补。
- **开发子任务（如 Kimi 等）**：开发执行者。在 1104 分配的隔离区中编写代码，按模块独立 commit，跑定向测试，严禁跨模块混提。涉及 RPC/UI 的交付必须附带实机联调证据与本地 E2E 验收记录，否则视为未交付。**严禁篡改测试文件制造伪绿。**

### 1. 启动【逻辑中枢（子任务 0）】

适用场景：需要吞下长篇文档（如 V7.1 指南、商业模型），生成或更新《业务逻辑中枢字典》。

发给 Kimi 的 Prompt：

```text
【角色与任务】
你是项目的"逻辑中枢（Tech Lead）"。你不写业务代码，只负责将长文档提炼为结构化契约。
【动作】
1. 先运行 `bash scripts/pre-flight.sh`。
2. 阅读 `docs/architecture/` 下的商业文档。
3. 输出/更新 `docs/architecture/business-logic-hub-v1.0.md`。
【纪律】
必须使用 TypeScript Interface 定义核心状态机和脱敏接口。
如果有文档没写清的业务边界，直接标注[待确认]，严禁自己脑补。
```

### 2. 唤醒【主任务 1104】

适用场景：有新任务（如 10.7）或补丁（如 10.6.7），需要项目经理分配编号。

发给 1104 的 Prompt：

```text
【主任务统筹指令】
1. 运行 `bash scripts/pre-flight.sh`。
2. 为当前任务分配编号，在 AGENTS.md 登记表中登记分支名与简述（状态：进行中）。
3. 不要读取长篇商业文档，不要写代码。工单只需写明："目标分支 + 极简任务描述 + 强制阅读中枢字典"。
4. 同步更新 WORKLOG.md 中的 handoff_snapshot。
5. git commit（本地独立提交），汇报真实 Hash 后立刻休眠。push 由裁判在门禁通过后统一执行。
```

### 3. 派发【开发子任务】

适用场景：裁判铺好分支，将具体写代码的活派给 Kimi。

发给 Kimi 子任务的 Prompt：

```text
【第一步：强制物理契约核验】（不可跳过）
1. 执行 `bash scripts/pre-flight.sh`，必须通过 ✅。
2. 执行 `git fetch origin && git switch <分支名> origin/<分支名>`。
【第二步：阅读中枢字典】
请先阅读 `docs/architecture/business-logic-hub-v1.0.md` 中的 [指定模块]。
【第三步：任务目标】
- （一句话描述具体要改什么）
【第四步：执行纪律】
1. 方案先行：先出修改方案，等我（裁判）确认。
2. 测试先行：写红灯测试，跑出真实失败后再写实现。严禁用正则匹配 SQL 文本冒充行为测试。
3. 物理脱敏：不可在前端做敏感数据过滤。
4. 文件级提交：严禁 git add .，只 add 改动的文件。
5. 沙盒必须 commit：完成后必须在本地 commit。
   由裁判按 C.0 合并路径优先级摘取：
   --ff-only 优先；含 Merge 节点逐节点 git cherry-pick -m 1 拆包；
   禁止 git cherry-pick A..B（range 摘取）；
   禁止 git cherry-pick --skip（合并黑洞）。
6. 实机联调证据（涉及 RPC/UI 的任务）：必须提供契约 D 六件交付物——真实环境（npm run dev）
   浏览器渲染截图（含 URL 上下文）、F12 请求真实 Payload/Response、服务端落库 SQL 查询原文、
   本地 E2E 人工验收记录（启动命令 + URL、验收剧本、操作前后状态对比、服务端落库 SQL 证据）。
   Mock 数据全绿不算交付，无实机证据我直接打回。
7. 业务参数同源：凡涉及业务数值（倍数/限额/有效期），必须从 SystemConfig 读取，
   严禁写死；交付时说明配置项 key。
8. 测试防篡改：严禁修改/删除/弱化任何既有测试断言来换取绿灯；
   如确需调整测试，必须按契约 D.5 三分法逐项说明改动类型与理由。
9. 级联缺陷隔离：执行中发现的独立新 Bug，只记录不动手，回报我另开 -R 子工单，
   严禁顺手塞进当前工单。
10. 不可自证项声明：若你无法访问验证环境，必须在交付包中显式声明"不可自证项"清单，
    由裁判在对应环境代验并附原始输出。
请先输出【技术方案】。
```

### 2.4 只读排查令（V2.3.2 新增）

当需要 AI 辅助定位问题但不允许其动手时，裁判下发只读排查令。排查令必须写死：

**不改代码、不 commit、不 push、不 git add、不 rebase。**

每条排查项要求：命令 + 输出原文 + 一句话事实说明。查不出的写"查不出 + 缺什么输入"，不许推测。排查结果不直接 `closed` 任何 `Gx`，只作为裁决依据。任何在只读排查令下"顺手改代码"的行为，按边查边改事故处理（见第六部分事故库），本次排查证据全部作废重采。

## 第三部分：裁判实操 SOP（全链路执行标准）

这是每次任务在物理世界的标准流转动作。

### 阶段 A：常规核验与派单

1. 裁判接收任务，原样复制标准 Prompt 发给 1104（PM）。
2. 收到主任务的 Hash 后，确认主工作区干净（`git status -sb` 无 `M` / `??`）。
3. 严格审查主脑的派工单是否包含"冻结范围（G1…Gn）"与"明确澄清项"；**E-C1…En 反向交卷清单属【交卷格式】附件（契约 E.1），不得混入冻结范围**，缺项打回重写。
4. 在 VS Code 终端执行：

```bash
cd <主工作区绝对路径>
git pull origin main --ff-only    # ⚠️ 禁止产生 merge 节点
bash scripts/pre-flight.sh
# 切分支并推送到远端（push -u 建立跟踪，严禁 --force）
git switch -c <分支名>
git push -u origin <分支名>   # ⚠️ 必须做，否则云端 AI 找不到分支，会产生平行宇宙
```

5. 严格要求 1104 基于最新 `origin/main` 使用 `git worktree` 建立隔离沙盒（见第七部分 7.1）。

### 阶段 B：并发开发与监视

1. 1104 将任务拆解为 A/B/C 模块，派发给不同开发子任务并行开工（见第七部分 7.2）。
2. **证据原样透传（契约 A）**：测试报错或 diff 过长时，裁判将证据段（SQL 全文、终端输出、查询结果、截图 + `.txt` 转写）原样透传，严禁改写、转写代写、记忆库调取、模板拼装、二次加工。交付包按契约 A 两段式组装：叙述段可精简，证据段原样透传。
3. 红灯确认：对照证据确认失败原因是否与业务缺失一致（防止伪实现）。裁判看代码时，使用 `git diff --cached -U0` 只取增删行，防 Token 爆炸。
4. **测试防篡改复核（V2.3.1 起强制执行）**：绿灯通过后，裁判必须复核测试文件的 Diff，按契约 D.5 三分法逐项归类；发现类型 D（删除/弱化断言）立即 `git checkout` 撤销该测试文件改动，打回重做。
5. 绿灯通过后，让子任务执行 `git add <具体文件>` 并在沙盒按模块独立 commit，汇报沙盒路径和 Commit Hash。
6. **实机联调证据强制收缴**：涉及 RPC/UI 的模块，子任务必须交契约 D 六件交付物（V2.3.1 起为完整 E2E 证据链）；1104 汇总时无此证据的模块不得进入合并队列。Mock 全绿不构成交付。
7. 裁判仅盯盘，不干预开发；遇到断网/幻觉导致的越权，立刻触发停机。

### 阶段 C：合并落盘与打假复跑（针对并发多模块提交的验收标准）

由于 PM 采用并发调度，开发子任务会产生多个 commit。

#### C.0 合并路径优先级（V2.3.2 新增，不得跳级）

按以下优先级选择合并路径：

1. **首选**：`git merge --ff-only <branch>`——严格超集时直接快进，无冲突、无 merge 节点。
2. **次选（受限）**：`git cherry-pick -m 1 <merge>` 逐节点拆包——**仅限历史遗留含 Merge 节点的分支，且须经裁判批准后方可使用**；新交卷分支按 7.5 禁止 merge 节点，不适用本条。

**禁止**：
- `git cherry-pick A..B`（对含 Merge 的 range 直接报错或吞包）；
- `git cherry-pick --skip`（合并黑洞，见铁律 7）；
- `git reset --hard <中间节点>` 作为换位置手段；
- `git pull` 产生 merge 节点。

合并前必跑 `git log --oneline --graph <base>..<branch>`，输出原文附入交付包。基线关系判定一律按铁律 19（`--ff-only` 试跑 / `--is-ancestor` 退出码），确认分叉时交 1104 开合并工单重构提交序列，裁判不手工解冲突。

#### C.1 摘取、复跑与推送核验（V2.3.2 强化）

```bash
# 1. 物理摘取（依 C.0 路径，逐个合并，防冲突）
git fetch <沙盒路径> <分支名>

# ⚠️【合并黑洞防御】若某 hash 是多父节点 Merge Commit，Git 会拒绝普通 cherry-pick。
#    严禁使用 `git cherry-pick --skip` 跳过——这会把该 commit 的改动物理吞掉
#    （2146 行代码全丢的事故原型）。
#    必须使用 `git cherry-pick -m 1 <hash>` 拆包，取主分支视角的净变更；
#    若 -m 1 拆包结果异常（diff 为空或明显缺失），立即中断排查，
#    回到源沙盒用 `git show <hash>` 核实真实改动范围，严禁蒙眼推进。

# ⚠️ 若 cherry-pick 报 CONFLICT，严禁子任务自行解决，
#    必须由裁判在主工作区手工做文本级合并，git add 冲突文件后再继续。

# ⚠️【静默合并防御】若 cherry-pick 自动合并（无 CONFLICT），但全量测试出现大面积
#    SyntaxError 或逻辑缺失，严禁让 AI 逐行修 bug。
#    必须由裁判去原始沙盒（PM 目录）执行 `cp <原版> <目标>` 物理覆盖，
#    这是最快、最安全的止损手段。

# 2. 合并后，裁判亲自复跑全量构建与测试，确保 100% 全绿
bash scripts/pre-flight.sh
npm test -- --run --reporter=dot  # 静默模式防刷屏

# ⚠️【基线不缩水验证】合并后必须比对测试基线数量（合并前记录测试总数）。
#    若测试项减少（如 456 → 452），说明测试文件被 Git 静默覆盖，
#    严禁带着缩水的测试基线推流。
#    溯源命令：`git log -S '<丢失测试的关键字符串>' --oneline --all`，
#    定位吞掉测试的 commit 后强制补合，恢复至基线数量方可继续。

# ⚠️【契约冲突裁决法】若 Markdown 台账（WORKLOG.md / AGENTS.md / 中枢字典）
#    出现冲突：一律保留 HEAD 的历史痕迹，采纳 Incoming 的新版本号与新条目，
#    然后手工清理重复条目。严禁 Accept Both 直接污染台账，
#    严禁 Incoming 覆盖抹掉 HEAD 已登记的历史记录。

# 3.【强制洁净检查】push 前 3 条核对（缺一不得 push）
git status -sb              # 输出必须仅含 `## main…origin/main`，绝对严禁带 M / ??
git log --oneline -1 main   # 本地 HEAD
git ls-remote origin main   # 远端 HEAD

# 4. push（仅由裁判执行，禁止 --force / --all / --tags）
git push origin main

# 5. push 后 3 条核对（缺一不算闭环）
git ls-remote origin main   # 远端 = 本地 HEAD
git log --oneline -1 origin/main
git status -sb              # 不再 ahead

# 6. 唤醒 1104 更新台账
# 向 1104 发送："10.7 已合并，Hash 为 xxx。请更新 WORKLOG.md 和 AGENTS.md 台账。"
```

## 第四部分：断网/断联紧急兜底指南

当子任务 AI 提示"网络连接失败，无法推送"时，裁判必须立刻介入，严禁 AI 尝试任何越权操作（如调用 GitHub API 伪造提交）。

2. **断网即停机**：若沙盒内无法 `git fetch` 远端，绝不越权强推。

5. 裁判在 VS Code 中手动将 AI 生成的代码 Diff 应用到自己的 VS Code 工作区，自己执行 `git add` 和 `git commit`。
6. 继续执行正常的审核与合并流程。

## 第六部分：核心工程铁律与避坑指南（血泪教训库）

1. **物理隔离**：绝对锁定绝对路径（/Users/mac/Documents/kimi/tasks/<任务目录>），开工前必跑 `bash scripts/pre-flight.sh`。严禁跨目录操作。
2. **文件级暂存**：严禁 `git add .` / `git add -A`，只能显式 `git add <file>`。绝对禁止夹带 `tools/sandbox/sandbox.html`。
3. **物理脱敏**：前端隐藏不算脱敏，必须在 SQL/RPC 层剥离敏感字段。
4. **配置与逻辑分离**：任何业务参数（限额、次数、有效期）必须从 SystemConfig 读取，缺失即 fail-closed，严禁在代码中硬编码。
5. **禁止"伪测试"**：红灯测试必须针对真实行为（运行时计数、并发），严禁仅用正则匹配 SQL 文本冒充行为测试。
6. **密钥入 Vault**：严禁在托管型数据库（如 Supabase）使用 GUC 参数硬编码密钥。所有高敏配置必须推入 Supabase Vault，RPC 层 `vault.decrypted_secrets` 动态读取。
7. **SSOT 单一事实来源（P0-2 教训）**：同一业务实体（如教练、用户），全库必须有且只有一条物理事实判定来源，**只认服务端 RPC 落库事实**；前端 `localStorage` 与本地常量一律视为缓存或违例。新建 RPC 时，严禁凭感觉写 EXISTS 判定，必须遵守《业务逻辑中枢字典》定义的统一关联表。
8. **Mock 隔离律**：前端单元测试全绿 ≠ 真实环境可用。Mock 数据只配用于单元测试，联调交付的唯一货币是契约 D 的完整 E2E 证据链（六件交付物）。
9. **底层扩展可见律**：调用 `pgcrypto` 等底层扩展的自定义函数，`search_path` 必须包含 `extensions`，否则 42883 崩溃、前端无端 404。迁移后必须实机调用验证。
10. **UI 物理视觉验证**：页面挂载/组件联调类交付，必须提供真实渲染截图与 Network 日志，并按契约 D 补齐六件交付物，缺一不合格。
11. **业务参数同源律（24 倍数教训）**：业务数值由 SystemConfig 单一来源驱动，UI 与 RPC 严禁各自硬编码；"改配置 → 看变化"是验收的必经动作。
12. **静默合并止损**：Git 自动合并无冲突 ≠ 语义正确。一旦合并后测试大面积崩溃、权限丢失，**严禁 AI 逐行修 bug**；最高效、最安全的手段是裁判去源沙盒 `cp <原版> <目标>` 物理覆盖。
13. **终态洁净**：push 之前必须执行 `git status -sb` 终态检查，绝不让任何未提交文件（`M` / `??`）活过合并时刻。远端构建报错而本地全绿时，第一反应是检查是否有补丁文件停留在工作区。
14. **合并黑洞防御**：遇到多父节点 Merge Commit，`git cherry-pick --skip` 是物理级自杀操作——整个 commit 的改动会被静默吞掉。唯一正确姿势：`git cherry-pick -m 1 <hash>` 拆包；拆包异常立即中断排查。
15. **测试基线守恒**：合并前后测试总数必须守恒。测试项减少 = 有测试文件被静默覆盖 = 合并不合格。用 `git log -S` 溯源，强制补合至基线数量后才允许推流。
16. **迁移唯一事实源（V2.3 红线）**：迁移文件为唯一事实源；手工变更必须登记且被迁移吸收（同第一部分铁律 12）。
17. **push 权限（V2.3 红线）**：push 仅由裁判在门禁通过后执行；禁止未授权 push；禁止 `--force` / `--force-with-lease`（同第一部分铁律 18）。
18. **测试防篡改（V2.3.1 红线）**：交付前裁判必须复核测试文件 Diff，按契约 D.5 三分法归类；类型 D（删除/弱化断言）红线驳回。
19. **级联缺陷隔离（V2.3.1 红线）**：独立新 Bug 另开 `-R` 子工单，严禁扩大当前工单修复范围（同第一部分铁律 16）。
20. **基线关系判定的唯一判据（V2.3.2 红线）**：`--ff-only` 试跑 / `--is-ancestor` 退出码，禁止 merge-base 差值判定，禁止 `reset --hard` 换位置（同第一部分铁律 19）。

### Hotfix 止损 SOP（V2.3.1 新增）

当 main 被功能蔓延污染、或线上出现必须立即止血的缺陷时，按以下 SOP 执行：

1. **冻结 main**：立即暂停一切向 main 的合流与 push，通知 1104 所有在途功能工单挂起。
2. **定位稳定基线**：`git tag -l` 找到最近稳定 Tag；无 Tag 则以最后一次"push 后 3 条核对"全通过的 HEAD 为准。
3. **切出止血分支**：`git switch -c hotfix/<编号> <稳定Tag>`，hotfix 分支基于稳定点，绝不基于被污染的 main。
4. **最小修复**：hotfix 分支只收止血必需的改动，走完整 TDD + 契约 D 验收；任何顺手优化、无关重构一律按级联缺陷隔离律打回。
5. **独立验收合并**：hotfix 单独过门禁（契约 A/B/C/D），裁判按 C.1 推送核验推流；推流后打新稳定 Tag。
6. **功能线归位**：被冻结的功能分支 rebase 到新的 main 之上，由 1104 开合并工单按 C.0 路径归队，严禁功能分支与 hotfix 分支互相 merge。

### 事故库

## 第七部分：PM 并发调度协议（Agent Orchestration）

为了极致压缩交付周期，PM（1104）必须采用多智能体并发机制：

- **7.1 物理隔离**：PM 派发并发任务前，必须用 `git worktree add ../_task-xxx -b feat/xxx` 建立专属物理目录。绝不允许多个子任务在同一个文件树中写代码。
- **7.2 模块拆解**：大需求必须被切分为无交集或弱交集的模块（如：前端 UI 组件、后端 RPC 与迁移、单元测试等）。
- **7.3 原子提交**：每个子任务完成任务后，必须按照模块边界独立 commit（如 `feat(admin): 新增教练管理入口`、`fix(rpc): 修复额度校验`），严禁将多个模块揉进一个 commit。
- **7.4 聚合验收**：所有并发子任务结束后，PM 汇总所有的 commit hash、`git diff --stat` 和各自模块的测试结果，统一向裁判交卷。汇总时注明各分支与 `origin/main` 的基线关系判定方式（`--is-ancestor` 退出码 / `--ff-only` 辅助验证），供裁判按 C.0 选路。
- **7.5 禁止 merge 式提交**：子任务提交必须保持线性历史（rebase 后提交），严禁向交卷分支引入 merge commit。merge 节点会让裁判的 cherry-pick 进入黑洞风险区，违背铁律 7。
- **7.6 实机联调证据强制入卷**：PM 汇总交卷时，每个涉及 RPC/UI 的模块必须附带契约 D 六件交付物（真实环境截图 + F12 真实 Payload/Response + 落库 SQL 原文 + E2E 验收记录），证据按契约 A.5 标注环境。无证据模块一律标注"未联调"，不得进入裁判的合并队列。禁止用单元测试报告冒充联调证据。
- **7.7 级联缺陷上报（V2.3.1 新增）**：子任务执行中发现冻结范围外的独立 Bug，只允许记录并上报 PM，由 PM 向裁判申请 `-R` 子工单，严禁自行扩 scope。

## 第八部分：交付契约（A / B / C / D）

本部分为固化的四条交付契约，具有宪法效力。任何交付包、工单、验收动作均以此为准。

### 契约 A：交付包两段式

- **叙述段**：允许精简，不作为裁决依据。
- **证据段**：SQL 全文、终端输出、查询结果、截图 + `.txt` 转写，原样透传。
- 禁止改写、转写代写、记忆库调取。
- 截图必须附执行者生成的 `.txt` 转写，同路径、同名加 `.txt`。

#### 契约 A.4 证据段四要素（V2.3.2 新增）

每条证据必须包含：命令 + 输出原文 + 执行环境 + 执行时间。缺任一项按"证据不完整"处理。

#### 契约 A.5 证据环境标注（V2.3.2 新增）

所有 HAR / F12 / 数据库 / 终端证据，必须标注：

1. 工作树 HEAD（`git rev-parse HEAD` 输出）；
2. 迁移清单（`supabase migrations list` 或等价输出）；
3. 执行环境（本地 / 预发 / 生产）；
4. 执行时间。

无标注按"来源未知"处理，对应 `Gx` 不得据此 `closed`。

#### A.5.1 证据同源律（BUG-233-09，v2.3.4 新增）

- 证据必须产生于**被测 HEAD**。
- 旧 HEAD / 旧环境证据仅作对比参考，不得作为 `Gx` `closed` 依据。
- 标注旧 HEAD 证据且用于 `closed` 判定，按"来源不合格"驳回（INC-1015-06 判例）。

### 契约 B：清单冻结 + 缺口状态机

- 工单下发锁定 `G1…Gn`，中途不得新增；新增须开 `-R` 子工单并说明理由。
- 状态机：`open → evidence_submitted → closed`。
- `closed` 必须引用证据：文件路径 + 哈希，或截图路径 + `.txt` 路径。
- 驳回只引用 `Gx` 编号，不写新叙述。
- 同一 `Gx` 不得重复提出；重开须注明"原关闭证据失效原因"。

#### 时间盒与进化模式叠加规则（BUG-233-06，v2.3.4 新增）

- 同一 `Gx` 往返上限 **2 轮**（往返 = 一次交卷 + 一次驳回）；
- 第 2 轮未 `closed`，开 `-R` 隔离（第九A部分），主单该 `Gx` 冻结，不再往返；
- 同一 `Gx` 同质化驳回累计 ≥3 次，独立触发进化模式（第十一部分）；
- 2 轮时间盒与 3 次进化模式**独立计数，不互相抵扣**；任一触发即冻结代码流转。

### 契约 C：提交前机械自检

提交前扫描交付包中的占位符残留，扫描模式如下（为避免自检自命中，模式以码位与说明表述）：

| 模式 | 说明 |
|------|------|
| `U+FF08` + 粘贴 | 全角左括号紧跟"粘贴"二字 |
| `U+005B` + 填入 | 左方括号紧跟"填入"二字 |
| `U+005F` × 4 | 连续四个下划线 |
| `U+003A` + `U+005F` × 2 | 冒号紧跟两个下划线 |
| `U+002E` × 3 | 连续三个英文句点 |
| `U+7565` | 单字占位（拼音 lüe 的常用汉字） |
| `U+5DF2` `U+5F52` `U+6863` | "已" + "归档"二字连用 |
| `U+5F85` `U+586B` | "待" + "填"连用 |
| `U+5F85` `U+8865` | "待" + "补"连用 |
| `T` `B` `D` | 三个大写字母占位连用 |
| `U+2026` | 中文省略号 |
| `U+7701` `U+7565` | “省略”二字连用 |
| `U+53C2` `U+89C1` | “参见”二字连用 |

- 命中任一即拒绝提交。
- **交付包第一页 = 契约 C 机械自检命令与输出 + worktree 状态声明**（当前未提交文件清单，按铁律 6 实施期口径）。
- 扫描不通过，或第一页缺项，不进入裁决。

**扫描范围限定**：扫描对象为交付包的**证据段、伪 SQL / 伪代码与模板字段**，不扫描叙述段全文——避免"略""参见"等自然语言用词造成全包误报。

**白名单**：凡需指代既有实现，一律写为 `见 <路径>:<行号>`（或 `/* 见 <路径>:<行号> */`），白名单格式 0 命中。

### 契约 D：功能验收门禁

#### D.1 定义

凡涉及前端交互的 `Gx`，关闭条件必须包含"本地端到端人工验收记录"。无此记录，状态不得为 `closed`。

#### D.2 记录格式（强制，V2.3.2 修订）

1. 启动命令与本地 URL（如 `npm run dev` + `http://localhost:xxxx`）。
2. 验收剧本：逐步操作序列（登录 → 进入某页 → 点击某按钮 → 观察结果），剧本必须体现"用户能否完成一次完整业务动作"。
3. **整体验收六件，剧本逐步对应**：一次交付整体须备齐**契约 D 六件交付物**（缺一即 `evidence_submitted`，不得 `closed`）；逐步操作剧本（⑥）与证据①–⑤**逐条对应**——是"剧本每一步都能指到对应证据"，**不要求每一步操作单独凑齐六件**：
   - ① **操作前状态截图**（含 URL 上下文）；
   - ② **操作后状态截图**（与①同视角对比，证明流转发生）；
   - ③ **截图 `.txt` 转写**（执行者生成，与截图同路径同名）；
   - ④ **F12 请求真实 Payload / Response 原文**（URL、方法、状态码、关键字段）；
   - ⑤ **服务端落库证据**：关键表变更前后行数/字段值，用 **SQL 查询原文**佐证（不适用场景按第 4 条前置判断登记 DEBT）；
   - ⑥ **逐步操作剧本**：逐步操作序列，与①–⑤逐条对应，体现"用户能否完成一次完整业务动作"。
4. 证据必须由执行者（1104 或裁判）在本地真实启动后产生，不得复用历史截图；证据按契约 A.4/A.5 标注环境与时间。

#### D.2 第 4 条（落库证据）适用性前置判断（V2.3.2 修订）

- **适用性**：当 `Gx` 验收对象是"前端不挂载 / 不发起请求"时，无写入则无落库变更，落库证据场景不适用。
- **处理方式**：须书面说明"受限 RPC 未发起、无写入"，登记 DEBT，不阻塞验收。
- **禁止**：用 RPC 响应 JSON 冒充落库查询 SQL 原文。

#### D.3 F12 200 的定位

- F12 200 降级为辅助证据，不再是功能正确的充分条件。
- 主证据是"操作前后状态对比 + 服务端落库查询结果"。

#### D.4 状态约束

- 无本地 E2E 记录：`open` 或 `evidence_submitted`。
- E2E 记录不完整（缺前后对比或缺落库证据，落库适用时）：`evidence_submitted`。
- E2E 完整且落库证据一致（或落库不适用已登记 DEBT）：`closed`。

#### D.5 测试改动三分法（V2.3.2 新增）

交付涉及测试文件改动时，必须逐项归类：

- **类型 A：纯 Mock 注入**（合规）。
- **类型 B：查询改异步等待**（合规）。
- **类型 C：断言语义变化**（须逐项说明，归因须指向本任务范围）。
- **类型 D：删除/弱化断言以让测试通过**（红线，驳回）。

禁止把多文件测试改动打包成"适配重构"一句话糊弄过关。裁判交付前复核测试 Diff 时逐条对质。

#### D.6 契约-实测矛盾排查四选一（V2.3.2 新增）

出现"契约要求 X，实测返回 Y"时，**严禁**直接判定代码缺陷，必须按顺序排查：

1. **A. 旧环境**：证据取自旧 HEAD / 旧环境（附 HEAD 与迁移清单佐证）；
2. **B. 迁移未应用**：目标环境迁移清单缺该迁移（附 `schema_migrations` 清单）；
3. **C. 后续迁移覆盖**：同名定义被后续迁移覆盖（附同名定义佐证）；
4. **D. 真代码缺陷**：A / B / C 全部排除后，才可判定为代码缺陷。

排查期间优先下发只读排查令（第二部分 2.4），严禁边查边改。

## 第九部分：实机联调排障 SOP

TASK-10.13 实机联调战役沉淀的两条排障通法。**核心原则：先排除平台层假象，再怀疑代码层。**

### 9.1 PostgREST 缓存死锁绕过法

- **症状**：RPC/表结构迁移已成功 apply（`supabase migrations list` 显示已应用），但实机调用持续 404（`PGRST204: no rpc found` / schema cache 类报错），子任务反复"修代码"毫无效果，形成死循环。
- **根因**：PostgREST 的 schema cache 是独立快照，不随 DDL 迁移自动刷新，路由表仍是旧版本。
- **绕过法**：
  1. 先在 SQL Editor 直接执行该函数 SELECT，验证数据库层函数真实存在且可调用。**数据库层通、REST 层不通 = 缓存问题，代码无罪。**
  2. 强制刷新 schema cache：在 SQL Editor 执行 `SELECT pg_notify('pgrst', 'reload schema');`（有权限时），或通过 Dashboard 重启 PostgREST 服务。
  3. 等待数秒后重试实机调用；仍 404 再查函数签名与 search_path（转 9.2）。
- **铁律**：缓存未刷新前，**严禁**让 AI 修改任何业务代码。死锁期的一切"代码修复"都是幻觉作业。

### 9.2 pgcrypto 路径修复（42883 排障）

- **症状**：实机调用 RPC 返回 500/404，PostgREST 日志报 `function pgcrypto 函数解析失败`（SQLSTATE 42883）。
- **根因**：自定义函数体内调用了 `pgcrypto` 扩展函数，但函数声明的 `search_path` 不含 `extensions` 模式，运行时解析失败。
- **修复**：
  1. 检查函数声明，补上扩展可见性：
     ```sql
     create or replace function public.<函数名>(<参数>)
     returns <返回值> language plpgsql
     set search_path = public, extensions  -- ⚠️ 必须包含 extensions
     as $$ <函数体> $$;
     ```
  2. 重新 apply 迁移后，**必须实机调用一次真实 RPC**（带真实参数），不能只跑单测。
  3. 若仍报 42883，检查扩展是否安装在 `extensions` 模式（`select * from pg_extension where extname='pgcrypto';`），不在则先装扩展再修 search_path。
- **预防**：任何调用底层扩展的新 RPC，在《技术方案》审查阶段就必须写明 search_path 声明（铁律 9）。

## 第九A部分：-R 子工单规范（v2.3.4 新增，BUG-233-02）

### A.1 定义与触发

-R 子工单用于：

1. 主单冻结清单 G1…Gn 之外的新增范围；
2. 执行中新发现的独立 Bug（级联缺陷隔离律）；
3. 主单某 Gx 因实施范围变更需重新界定。

触发条件必须书面写明"新增范围 / 对应主单 Gx / 不改变主单冻结清单本身"。

### A.2 编号与命名

- 编号格式：`<主单编号>-R<两位数>`，示例：`TASK-10.16-R-01`、`TASK-10.16-R-02`；
- 不得复用旧 -R 编号；撤销的 -R 编号作废不复用。

### A.3 冻结与状态机

- -R 子工单下发即冻结自己的 Gx 清单（记为 GR1…GRn）；
- -R 状态机与主单同构：`open → evidence_submitted → closed`；
- -R `closed` 不自动使主单对应 Gx `closed`；主单须单独呈报并附 -R `closed` 证据引用。

### A.4 与主单关系

1. -R 不改变主单冻结清单本身；
2. -R 的 Gx 若与主单 Gx 同名，须加前缀区分（如主单 G-S1 与 -R 的 GR-S1）；
3. -R 的往返轮次独立计数，不占用主单"同一 Gx 往返 2 轮"额度（契约 B 时间盒）。

### A.5 时限

-R 子工单默认 1 轮闭环；第 2 轮不齐**须回主单重新界定范围**（主单该 Gx 按契约 B 时间盒冻结），**禁止开嵌套 -R**。

## 第九B部分：DEBT / INC 台账规范（v2.3.4 新增，BUG-233-03）

### B.1 DEBT 台账

- 编号格式：`DEBT-<三位数>`，按登记顺序递增，不复用。
- 字段：`DEBT-ID | 描述 | 级别（P0/P1/P2）| 关联 Gx | 期限 | 状态 | 登记人 | 登记日期`
- 状态机：`open → closed`；**禁止出现 `debt_registered` 等野值**。

**带债发布分级（红线）**：

- P0：不可带债。任何 P0 Gx 未 `closed` 前，不得以 DEBT 替代；
- P1 / P2：可登记 DEBT 带债发布，但发布说明须列明 DEBT-ID 与影响面。

DEBT `closed` 条件：关联 Gx `closed` 且证据引用路径/哈希已入档。

### B.2 INC 事故库

- 编号格式：`INC-<工单号>-<两位数>`，如 `INC-1015-01`。
- 字段：`INC-ID | 标题 | 级别 | 状态 | 防御条款引用 | 关联 DEBT`
- 状态机：`open → recorded / closed`；禁止 `debt_registered` 等野值；
- 转 DEBT 用字段"关联 DEBT"引用，不改 INC 状态为 `debt_registered`。

INC `closed` 条件：

1. 根因条款已写入 RUNBOOK 事故库；
2. 防御手段已在后续工单中生效（附证据引用）。

### B.3 裁决接口引用规则

- 裁决接口只引 DEBT-ID / INC-ID，不写新叙述；
- 野值状态直接驳回，要求按本节状态机重报。

## 第十一部分：迭代机制

1. **小版本迭代**：`v2.3 → v2.3.1 → v2.3.2 → v2.3.3 → v2.3.3-final → v2.4.0`（当前生效）；v2.3.4 为候选稿，修毕残留后另行发布；每次只修一类问题。
2. **触发条件**：契约条款产生歧义、机械自检误报/漏报、状态机无法表达真实状态、人工测试发现流程缺陷。
3. **迭代工单格式**：`BUG-<编号>` + 现象 + 复现步骤 + 影响条款 + 拟修条款 + 回归范围。
4. 不得就地扩项；不得夹带新功能。
5. 每次迭代在 `docs/WORKLOG.md` 顶部 `handoff_snapshot` 记录版本号、变更条款、生效时间。

### 进化模式触发机制（V2.3.3 新增）

1. **触发条件**：当同一工单（或同一 `Gx`）发生 **3 次及以上同质化驳回**（如：AI 反复因为没贴原文、没贴数据库回执、用摘要糊弄、或前后逻辑矛盾被拒），系统必须立刻启动"进化模式"。
2. **强制冻结**：启动进化模式时，立即冻结该任务的代码流转，禁止 AI 继续修改业务代码。
3. **契约重构**：裁判必须将 AI 反复踩坑的漏洞，提炼为具体的 E-C 标准项，补充进本次派单的【冻结范围】中。
4. **降维打击**：向 AI 下发固定填空模板（契约 E），强制其按模板逐条交卷，答不齐即打回，终结自然语言辩论。

## 附录 D：P0 故障应急通道（BUG-233-15，v2.4.0 生效）

本附录与第一部分铁律同级，是裁判在 P0 时刻的最高物理覆盖授权。当发生线上 P0 级故障时，裁判可行使最高物理覆盖权，走应急通道直接修复。

**必须遵守以下 3 项硬约束：**

1. **触发条件封闭枚举**：仅限"生产核心链路不可用（登录 / 打卡 / 支付）或 P0 数据事故"，由裁判书面判定，AI 不得判定。非核心链路不得走应急通道。
2. **止血范围最小化**：只动故障链路，禁夹带功能开发、UI 优化、重构；范围超出即回滚，按级联缺陷隔离律另开 `-R`。
3. **自动升级机制**：24h 内未补票（事故登记 + 迁移清单 + 回滚 SQL），自动升级为 P0 INC 并锁主干。补票不得以"监控未部署"为由延期（监控方案另立 DEBT，不阻塞补票）。

**补票三件套（24h 内入档 `docs/evidence/`）**：① 事故登记（INC 编号 + 根因）；② 迁移清单（本次应急改动的全部迁移文件）；③ 回滚 SQL（可执行、已验证）。
