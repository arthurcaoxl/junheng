请将以下内容复制保存，作为项目的 docs/RUNBOOK.md。以后你（裁判）只要照着这个手册操作，就能像指挥工业流水线一样指挥 AI。

> **文档性质**：裁判（人类）操作手册 + AI 交接 Prompt 模板库
> **使用方式**：全文可直接复制执行，Prompt 模板建议存入剪贴板快捷键工具（如 Mac 的 Raycast / Paste）

## 第一部分：裁判初始化环境（只需做一次）

在开始任何任务前，裁判（人类）必须在主工作区建立物理锚点。

```bash
# 1. 创建 WORKLOG 契约
cat > docs/WORKLOG.md << 'EOF'
current_baseline:
  milestone: "v1.13.3"
  head_commit: "当前最新的真实commit"
  test_files: 46
  test_cases: 342
  dictionary_version: "v1.0"
  status: "idle"
EOF

# 2. 创建 pre-flight 门禁脚本
cat > scripts/pre-flight.sh << 'EOF'
# (将上一章提供的 pre-flight.sh 代码粘贴到这里)
EOF

# 3. 赋予执行权限
chmod +x scripts/pre-flight.sh
```

## 第二部分：角色启动与交接 Prompt（直接复制使用）

### 1. 启动【逻辑中枢（子任务 0）】

**适用场景**：需要吞下长篇文档（如 V7.1 指南、商业模型），生成或更新《业务逻辑中枢字典》。

发给 Kimi 的 Prompt：

```text
【角色与任务】
你是项目的"逻辑中枢（Tech Lead）"。你不写业务代码，只负责将长文档提炼为结构化契约。
【动作】
1. 先运行 `bash scripts/pre-flight.sh`。
2. 阅读 `docs/architecture/` 下的商业文档。
3. 输出/更新 `docs/architecture/business-logic-hub-v1.0.md`。
【纪律】
必须使用 TypeScript Interface 定义核心状态机和脱敏接口。
如果有文档没写清的业务边界，直接标注[待确认]，严禁自己脑补。
```

### 2. 唤醒【主任务（1104）】

**适用场景**：有新任务（如 10.7）或补丁（如 10.6.7），需要项目经理分配编号。

发给 Kimi 1104 的 Prompt：

```text
【主任务统筹指令】
1. 运行 `bash scripts/pre-flight.sh`。
2. 为当前任务分配编号，在 AGENTS.md 登记表中登记分支名与简述（状态：进行中）。
3. 不要读取长篇商业文档，不要写代码。
   工单只需写明："目标分支 + 极简任务描述 + 强制阅读中枢字典"。
4. git commit 并 push 到 main。汇报真实 Hash 后，立刻休眠。
```

### 3. 切换【DeepSeek 跨对话主脑】

**适用场景**：开新窗口找 DeepSeek 审查红灯或方案。

发给 DeepSeek 的 Prompt：

```text
【主脑架构师恢复】
你是架构审查者（主脑），我是裁判。
【基线锁定】当前 main 最新 hash 为 [填 hash]，字典版本为 v1.0，测试基线 342 项。
【铁律】
- 物理脱敏在 SQL/RPC 层
- 严禁 git add .
- 静态推断不进根因
- 只审查不写实现
【接力动作】子任务即将开发 [编号]。
我现在把它的《技术方案》贴给你，请审查：
1. 方案是否包含物理脱敏
2. 是否防笛卡尔积
3. 判断是否允许进入红灯测试
若给通过意见，请附带下一步指令。
```

### 4. 派发【开发子任务】

**适用场景**：裁判铺好分支，将具体写代码的活派给 Kimi。

发给 Kimi 子任务的 Prompt：

```text
【第一步：强制物理契约核验】（不可跳过）
1. 执行 `bash scripts/pre-flight.sh`，必须通过 ✅。
2. 执行 `git fetch origin && git switch <分支名> origin/<分支名>`。

【第二步：阅读中枢字典】
请先阅读 `docs/architecture/business-logic-hub-v1.0.md` 中的 [指定模块]。

【第三步：任务目标】
- （一句话描述具体要改什么）

【第四步：执行纪律】
1. 方案先行：先出修改方案，等我（裁判）确认。
2. 测试先行：写红灯测试，跑出真实失败后再写实现。
3. 物理脱敏：不可在前端做敏感数据过滤。
4. 文件级提交：严禁 git add .，只 add 改动的文件。

请先输出【技术方案】。
```

## 第三部分：裁判在 VS Code 的实操 SOP（全链路执行标准）

> 这是每次任务在物理世界的标准流转动作。

### 阶段 A：准备与切分支

收到主任务的 Hash 后，在 VS Code 终端执行：

```bash
cd <主工作区绝对路径>
git pull origin main
bash scripts/pre-flight.sh

# 切分支并强制推送到远端
git switch -c <分支名>
git push -u origin <分支名>   # ⚠️ 必须做，否则云端 AI 找不到分支，会产生平行宇宙
```

### 阶段 B：审核方案与红灯

| 步骤 | 动作 |
| --- | --- |
| 1 | 将子任务的《技术方案》丢给 DeepSeek 审查 |
| 2 | 审核通过后，让子任务跑红灯测试 |
| 3 | 红灯日志贴给 DeepSeek，确认失败原因是否与业务缺失一致（**防止伪实现**） |
| 4 | 绿灯通过后，让子任务执行 `git add <具体文件>` 并 push |

### 阶段 C：合并落盘（收尾）

裁判在本地执行：

```bash
git switch main
git merge --no-ff <分支名>
bash scripts/pre-flight.sh   # 确认合并没有破坏基线
npm test                     # 必须 100% 全绿
git push origin main         # 拿真实的合并 Hash
```

随后唤醒主任务（1104）：

```text
10.7 已合并，Hash 为 xxx。请更新 WORKLOG.md 和 AGENTS.md 台账，并 push。
```

## 第四部分：断网/断联紧急兜底指南

当子任务 AI 提示"网络连接失败，无法推送"时，裁判必须**立刻介入**，严禁 AI 尝试任何越权操作（如调用 GitHub API 伪造提交）。

**操作步骤：**

1. 命令子任务："立刻停止操作，输出你的 `git diff` 或 `git show`。"
2. 裁判在 VS Code 中，进入该子任务对应的分支目录（如果是本地沙盒）。
3. 手动将 AI 生成的代码 Diff 应用到自己的 VS Code 工作区。
4. 裁判自己执行 `git add` 和 `git commit`。
5. 继续执行正常的审核与合并流程。

## 第五部分：AI 幻觉与撒谎的识别与治疗

如果大模型出现以下症状，请立刻使用红线法则：

| AI 幻觉症状 | 治疗方法（裁判执行） |
| --- | --- |
| **虚报合并**："我已经合并到 main 了。" | 裁判直接敲击 `git log --oneline -1 origin/main`。如果是旧的，立刻打回："远端没有你的提交，立刻重推或报告网络错误。" |
| **伪实现**："我已删除了敏感字段。" | 要求 AI 贴出 TypeScript 的 Interface 定义和 SQL 的 `SELECT` 语句。如果它是用前端 `.filter()` 过滤的，直接判定不合格，打回重写。 |
| **假装测试通过**："红灯测试通过了。" | 要求它贴出完整的 Terminal 控制台输出截图或纯文本。断言必须包含"期望抛出 xxx 错误，实际未抛出"。 |

## 7.5 主脑接力上下文资产化（Brain Handoff Contract）

大模型主脑（如 DeepSeek）在长对话、断网或新建对话时，不可避免地会产生“上下文断裂（失忆）”。为了彻底消除人工复制长对话历史的低效与遗漏，五角架构必须将“接力上下文”转化为物理资产。

### 7.5.1 双文件锚定机制
接力上下文必须由“物理事实”与“架构语义”两部分组成，分别由主任务与逻辑中枢维护：
1. **物理状态锚点（主任务维护）**：在 `docs/WORKLOG.md` 顶部的 YAML 中，强制维护 `handoff_snapshot` 字段。该字段必须包含：当前业务版本、代码版本、当前活动任务、最后合并哈希、测试基线以及一句必读的《交接嘱托》。
2. **架构语义锚点（逻辑中枢维护）**：在 `docs/architecture/brain-handoff-context.md` 中维护当前字典版本、已完成的核心防线、暂缓的 Backlog 以及对下一个任务的核心提醒。

### 7.5.2 强制恢复纪律
任何新开启的主脑对话，第一条 Prompt 严禁包含长篇大论的进度说明。必须使用标准化的【主脑接力恢复模板】，通过读取上述两份资产，让主脑在 5 秒内满血复活。

### 7.5.3 标准接力模板
新对话启动时，裁判必须发送以下模板：
【主脑恢复与接力】
你是主脑/架构师，我是裁判。新对话开启，请基于以下物理快照恢复记忆。
【物理状态快照】
（在此粘贴 WORKLOG.md 中的 handoff_snapshot YAML 块）
【架构防线索引】
请立刻读取 docs/architecture/brain-handoff-context.md 了解最新架构防线。
请确认当前基线、当前活动任务，并复述一句《交接嘱托》。确认无误后，等待裁判下达具体审查任务。

## 7.6 断联兜底与主脑无损切换（Offline Failover）

大模型主脑在上下文严重超载时，可能直接丧失结构化输出能力。因此，接力信息不得依赖濒死的主脑自行总结。主脑接力包的生成权，必须由外部常驻角色接管。

### 7.6.1 接力包生成权
1. **物理侧**：由主任务（1104）随时读取最新的 Git 状态与 `WORKLOG.md`，生成 YAML 快照。
2. **语义侧**：由逻辑中枢（子任务 0）随时读取当前的字典版本与防御重心，生成架构防线摘要。
3. **裁判动作**：当发现主脑反应迟钝或报错时，裁判直接向主任务和中枢下达指令，获取打包好的接力信息，实现“无接触拔管”。

### 7.6.2 主脑无损切换 SOP
1. 冻结旧对话：裁判停止向过载的主脑发送新任务。
2. 提取物理快照：向 1104 发送指令：“输出最新接力快照”。
3. 提取架构防线：向中枢 0 发送指令：“输出最新防线提醒”。
4. 唤醒新主脑：新开 DeepSeek 对话，将提取的两段信息合二为一发送，瞬间满血恢复。
