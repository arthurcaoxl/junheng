# 沙盘与平台数据打通：架构与算法方案

- 状态：待裁判评审，未批准前不得进入实现
- 设计版本：`sandbox-snapshot 1.0`（建议契约，不是已实现接口）
- 适用范围：本地经营沙盘、未来平台只读数据适配、版本化经营快照
- 明确排除：本方案不新增表、迁移、RPC 或权限，不连接真实数据库，不修改现有引擎、`schema.ts`、`finance.ts` 或任何生产代码

## 0. 结论与不可变边界

推荐采用 **“统一快照契约 + 分阶段数据来源”**，最终形态为 **版本化、可审计的预计算快照（路径三）**。落地顺序是：先用人工导入且经过校验的快照建立契约与勾稽，再补齐真实库存／订单／现金台账，然后接入受控只读适配器，最后才自动生成和发布快照。只读适配器是快照生产者，不是浏览器滑块的在线数据源。

以下边界不随实施阶段改变：

1. 当前 `platformStockBoxes = 200` 只是默认经营假设，不是平台真实库存，也不是数据库读取结果。
2. 真实模式与假设模式必须显式分离；未知值不得静默写成 0，假设值不得冒充实际值。
3. 平台未发出库存与教练已拿货库存分开建模；任何负数截断只保留为既有显示防线，不得吞掉数据异常。
4. 缺货机会成本按销售额损失计算；教练回款与平台采购付款是不同现金事件；库存资产不重复计入现金或利润。
5. 浏览器继续通过同源纯函数同步重算，不在滑块渲染路径读取网络、文件或 Supabase。
6. 既有 BEP 参考结果 **393／317** 锁定，本方案不改变其算法、输入语义或历史防线。
7. `userCode` 不是登录身份、认证主体或全局关联键，不进入平台数据联接设计。

## 一、现状与差距分析

### 1.1 当前沙盘输入及其性质

当前沙盘是本地独立工具。`SandboxInput` 的版本为 `7.1`，包含产品、种子用户、用户分流、教练政策、员工、财务和场景系数；样本价格与成本均属于推演输入。引擎生成月度教练拿货、教练库存和缺货等模拟结果，不能当作平台业务事实。

| 当前输入／结果 | 当前来源 | 当前性质 | 真实来源差距 |
| --- | --- | --- | --- |
| `product.boxPrice` → `revenuePerBox` | `SandboxInput.product` | 人工终端盒价假设 | 缺有效期间、渠道和实际成交价口径 |
| `product.coachPurchasePrice` → `coachPickupPrice` | `SandboxInput.product` | 人工教练拿货价假设 | 缺价格生效记录、订单价格快照 |
| `product.unitCost` → `unitCost` | `SandboxInput.product` | 人工单盒成本假设 | 缺采购成本、计价期间和成本方法 |
| `platformStockBoxes` | `html-generator.ts` 显式固定为 200 | 默认经营假设 | 缺期初、采购入库、其他出库、调整和期末实盘 |
| `coachPickupBoxes` | 推演月结果的 `coachOrderBoxes` | 模拟教练拿货 | 缺真实订单、配货、发货、签收及取消记录 |
| `stockoutBoxes` | 推演月结果的 `shortageBoxes` | 模拟缺货 | 缺未满足需求、欠货、取消及补发记录 |
| 教练已拿货库存 | 引擎 `coachInventory` | 模拟结存 | 缺教练期初、终端消耗／销售、退换和调整 |
| 教练回款 | 现有纯函数按“拿货盒数 × 拿货价”估算 | 推演现金流入 | 缺真实应收、收款、退款和核销流水 |
| 平台备货支出 | 现有纯函数按“备货盒数 × 单盒成本”估算 | 推演现金流出 | 缺采购订单、入库、应付和实际付款流水 |
| 期间、快照时间、来源版本 | 当前无平台快照契约 | 缺失 | 无法证明数据属于哪个月、何时截取、是否可重放 |

平台现有 Supabase 能力主要是 `checkin_sync` 打卡同步、`camp_admins` 管理员白名单及 `admin_checkin_overview()` 只读统计。现有资料没有证明平台已经拥有库存、教练订单、采购、回款或支付业务表／API，因此本方案不为它们指定任何“现有表名”。

### 1.2 200 盒的过渡定位

`200` 只能保留为无真实数据时的场景假设，并应在未来界面和导出物中标注“假设模式”。接入真实快照后：

- 实际模式的 `platformStockBoxes` 必须来自库存勾稽后的标准化结果；
- 缺真实库存时，实际模式应报告缺失，不得回退为 200；
- 只有用户主动进入假设模式时才允许使用 200，且不得与真实快照混算后宣称是实际经营结果；
- 历史假设报告继续可重现，但不能通过替换快照元数据伪装成真实报告。

### 1.3 关键业务缺口

1. **库存**：没有可核验的期初、入库、出库、调整、期末和实盘差异链。
2. **教练拿货**：没有订单、配货、实际发出、签收、退货的口径分离；不能把订单量直接当出库量。
3. **平台采购**：采购下单、验收入库、成本确认和付款可能跨期，当前没有对应事实链。
4. **回款**：拿货收入、应收与实际现金收款没有分离，退款和跨月核销未定义。
5. **缺货**：模拟短缺不等于真实未满足需求；需定义欠货需求、分配超卖和取消需求。
6. **单价**：终端销售额单价、教练拿货价、单盒成本缺少渠道、币种、生效时间和订单快照。
7. **审计**：缺来源记录 ID、来源修订号、操作者、快照版本、修正链和内容哈希。

## 二、数据源与所有权矩阵

下表中的“所有者”是建议责任角色，不代表仓库已有组织或模块；“未来业务台账”均须由裁判先确定承载系统。除明确标注为当前沙盘输入或现有 Supabase 能力外，均不是对现有数据库／API 的断言。

| 沙盘字段 | 真实数据来源 | 数据所有者 | 当前是否存在 | 认证与权限要求 | 时间口径 | 空值／缺失处理 | 转换规则 | 审计要求 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `platformStockBoxes` | 未来库存台账的期初、入库、授权调整及非教练出库 | 库存／仓储责任角色 | 否；现值 200 为假设 | 管理员或受控快照生成角色，只读 | 期间内可供教练发出的累计口径，期末由同一时点勾稽 | 实际模式报错；假设模式才可显式用 200 | `期末平台未发出 + 教练实际拿货`，即扣除其他出库后的可供教练口径 | 保留库存来源修订、调整凭证、快照哈希 |
| `coachPickupBoxes` | 未来教练订单／出库台账中的实际发出量 | 订单履约责任角色 | 否；现为模拟值 | 聚合只读；个人明细不进入浏览器 | 以实际控制权转移／发出事实的服务端时间归属 | 未知不得当 0；无发生须由来源明确确认 | 取 `pickedUpBoxes`，不取下单量或分配量 | 保留订单／出库不透明 ID、来源事件 ID、取消与退货修订 |
| `stockoutBoxes` | 未来需求／欠货台账中期间内未满足盒数 | 订单运营责任角色 | 否；现为模拟值 | 聚合只读 | 按缺货确认时间或裁判批准的期间规则 | 缺失则缺货 KPI 为未知，不按 0 | 仅计有效未满足需求，剔除取消与重复；不从负库存反推 | 保留需求来源、去重键、补发关联和原因码 |
| `unitCost` | 未来采购成本／成本快照 | 财务责任角色 | 否；现为人工输入 | 财务／管理员只读 | 对期末库存计价有效的成本期间 | 不得用 0 或销售额单价替代 | 统一为 CNY 最小货币单位／盒；旧函数边界再转为元 | 保留成本方法、有效期间和批准人 |
| `coachPickupPrice` | 未来价格快照或订单成交价 | 商务／财务责任角色 | 否；现为人工输入 | 管理员只读 | 以订单价格快照及控制权转移期间为准 | 缺失则现金估算不可用 | 统一为最小货币单位／盒；多价订单按实际金额聚合，不自行平均 | 保留价格版本、订单金额和折扣依据 |
| `revenuePerBox` | 未来对应销售渠道的销售额单价快照 | 商务／财务责任角色 | 否；现为人工终端盒价 | 管理员只读 | 与缺货需求同渠道、同期间 | 未决／缺失时缺货机会成本为未知，绝不改用成本价 | 采用裁判批准的渠道口径，记录 `priceBasis` | 保留渠道口径、价格版本和选择原因 |
| 库存期初 | 上一已结账期末或经批准的期初建账 | 库存责任角色 | 否 | 管理员只读；调整需授权 | 期初时点，`periodStart` | 首期无批准期初则拒绝实际快照 | 与上一期期末一致；链断裂即报错 | 建账凭证、批准人、前序快照 ID |
| 入库 | 未来采购／退货入库事实 | 仓储／采购责任角色 | 否 | 聚合只读 | 验收入库服务端时间 | 缺数据源为未知；确认无入库才为 0 | 采购入库与退货入库分列后汇总，避免重复 | 入库事件 ID、来源修订、验收时点 |
| 出库 | 教练实际拿货及其他授权出库 | 仓储责任角色 | 否 | 聚合只读 | 发出／控制权转移时间 | 缺出库类型不得全部归教练 | `outbound = coachPickup + otherOutbound` | 出库事件 ID、类型、关联订单、修订 |
| 调整 | 经授权的盘盈、盘亏、损耗、更正 | 库存责任角色＋财务审批 | 否 | 普通沙盘用户不可写；生成器只读 | 授权生效时间 | 无调整为 0；未授权记录进入异常 | 唯一允许带符号的盒数字段，正负分列审计 | 原因码、批准人、凭证和前后值 |
| 期末 | 库存流水推导值，并以实盘核验 | 库存／财务责任角色 | 否 | 聚合只读 | `periodEnd` 前一刻／结账时点 | 流水不完整则拒绝，不用截断伪造 | `期初 + 入库 - 出库 ± 调整` | 推导值、实盘值、差异和快照哈希 |
| 教练已拿货库存 | 教练期初＋实际拿货－终端销售／消耗±教练调整 | 教练渠道运营责任角色 | 否；现为模拟值 | 仅最小聚合，禁止个人敏感信息 | 与平台相同结账期间 | 缺教练端数据时标未知，不并入平台库存 | 独立结存，不与平台未发出库存相加冒充同一仓库 | 教练聚合口径、调整原因、期间 |
| 教练回款 | 未来可审计收款／核销流水 | 财务责任角色 | 否；现为估算 | 财务／管理员只读；不含支付原始报文 | 实际到账／核销规则由裁判确定，现金按到账时间 | 未接流水则只能标估算，不能称实际回款 | 按现金事件求和；退款单列，不与采购付款互抵 | 不透明收款 ID、金额、时点、核销关联、修订 |
| 平台采购付款 | 未来采购付款流水 | 财务／采购责任角色 | 否；现为估算 | 财务／管理员只读；不含支付原始报文 | 实际付款时间 | 无流水则实际现金支出未知 | 按现金事件求和，与入库和成本确认分离 | 不透明付款 ID、采购关联、金额、时点、修订 |
| 数据所属期间 | 快照生成器依据业务日历生成 | 平台数据治理责任角色 | 否 | 服务端生成，客户端不可指定财务事实 | 半开区间 `[periodStart, periodEnd)` | 缺失／边界不合法则拒绝 | 月度本地边界由服务端转 UTC | 期间规则、时区、生成参数 |
| 快照时间与来源修订 | 快照生成器及上游版本信息 | 平台数据治理责任角色 | 否 | 服务端可信时钟 | UTC ISO 8601 毫秒 | 缺来源修订不得进入自动生成实际快照 | `generatedAt/asOf/sourceRevision` 分层记录 | 内容哈希、生成者、修正链、审计日志 |

### 最小数据集原则

快照只包含盒数、最小货币单位金额、不透明来源 ID、期间和审计元数据。教练、订单、采购、收付款的明细仅在受控来源域内保存；沙盘默认使用月度聚合。报名资料、联系方式、Supabase UID、邮箱、本机 `userCode`、支付原始报文均不进入沙盘快照。

## 三、快照输入契约设计

### 3.1 设计原则

1. 新契约与 `SandboxInput 7.1` 分离，避免为平台接入修改现有 `schema.ts`。
2. 快照是某一期间和来源修订下的不可变事实包；经营场景调整是另一层输入，不回写事实包。
3. 盒数使用整数；金额使用 CNY 最小货币单位的非负整数，禁止浮点金额。调整盒数可为有符号整数，退款／冲正优先以独立正向事件和类型表达。
4. 所有服务端时间点使用 UTC ISO 8601、毫秒精度；期间采用半开区间。
5. “空数组”表示来源明确声明该期间无事件；“字段缺失”表示未知，两者不得等价。

### 3.2 建议 TypeScript 契约

以下仅为文档内设计，不创建实现文件。`?` 表示可选；其余均为必填。

```ts
type ISOUtc = string;          // 例如 2026-10-31T16:00:00.000Z
type MinorMoney = number;      // 非负安全整数，CNY 分
type Boxes = number;           // 非负整数
type OpaqueId = string;        // 不含姓名、联系方式或 userCode

type SourceEventRef = {
  sourceEventId: OpaqueId;     // 来源域内去重键
  revision: number;            // >= 1
  occurredAt: ISOUtc;          // 业务事实时间，不是客户端时间
};

type Money = {
  amountMinor: MinorMoney;
  currency: "CNY";
};

type DataIssue = {
  code: string;                // 稳定机器码
  severity: "warning" | "error";
  field?: string;
  message: string;             // 不含敏感原文
  sourceEventIds?: OpaqueId[];
};

type SandboxSnapshotV1 = {
  schemaVersion: "1.0";
  snapshotId: OpaqueId;
  source: {
    kind: "manual-validated" | "readonly-adapter" | "precomputed";
    sourceSystem: string;      // 来源系统的不透明逻辑名
    dataMode: "actual" | "assumption";
    generatorVersion: string;
  };
  generatedAt: ISOUtc;         // 快照生成时点
  asOf: ISOUtc;                // 上游事实截止时点
  periodStart: ISOUtc;
  periodEnd: ISOUtc;           // 必须晚于 periodStart，半开区间
  timezone: string;            // IANA 名称，例如 Asia/Shanghai
  sourceRevision: string;      // 覆盖全部上游输入的单调版本或规范哈希
  supersedesSnapshotId?: OpaqueId;

  inventory: {
    openingPlatformBoxes: Boxes;
    inboundBoxes: Boxes;
    otherOutboundBoxes: Boxes;
    authorizedAdjustmentBoxes: number; // 有符号整数，必须有审批依据
    closingPlatformBoxes: Boxes;
    physicalCountBoxes?: Boxes;
    coachOpeningBoxes?: Boxes;
    coachSoldOrConsumedBoxes?: Boxes;
    coachAdjustmentBoxes?: number;
    coachClosingBoxes?: Boxes;
  };

  coachOrders: {
    orderedBoxes?: Boxes;       // 需求量，不能替代实际拿货
    allocatedBoxes?: Boxes;     // 已分配量，用于识别超卖
    pickedUpBoxes: Boxes;      // 实际发出／控制权转移量
    stockoutBoxes?: Boxes;      // 未知时不得填 0
    sourceRefs: SourceEventRef[];
  };

  productPricing: {
    currency: "CNY";
    unitCostMinor?: MinorMoney;
    coachPickupPriceMinor?: MinorMoney;
    revenuePerBoxMinor?: MinorMoney;
    stockoutPriceBasis?: "terminal-sales" | "coach-pickup";
    effectiveFrom: ISOUtc;
    effectiveTo?: ISOUtc;
    priceRevision: string;
  };

  cashMovements: {
    coachReceipts: Array<SourceEventRef & {
      amount: Money;
      orderRef?: OpaqueId;
      kind: "receipt" | "refund";
    }>;
    procurementPayments: Array<SourceEventRef & {
      amount: Money;
      purchaseRef?: OpaqueId;
      kind: "payment" | "refund";
    }>;
  };

  dataQuality: {
    status: "complete" | "degraded" | "rejected";
    issues: DataIssue[];
    missingFields: string[];
    duplicateSourceEventIds: OpaqueId[];
  };
};
```

`coachOpeningBoxes` 等教练结存字段在 v1 可选，是因为真实来源尚未建立；若展示“真实教练库存”，则这一组字段必须同时齐备并通过勾稽。`stockoutBoxes`、`revenuePerBoxMinor` 缺省时，缺货机会成本只能显示“未知”。`dataMode = actual` 时，任何影响所展示 KPI 的缺失均为错误，不得自动切到假设值。

### 3.3 标准化为现有沙盘输入

快照不直接替换整个 `SandboxInput`，而由纯计算层之外的适配器生成两份输入：

1. 既有 `SandboxInput`：仅把已批准的价格、成本等映射到 `product`；其他经营假设仍保留并标识。
2. 库存财务标准化输入：

```text
platformStockBoxes = closingPlatformBoxes + pickedUpBoxes
coachPickupBoxes   = pickedUpBoxes
stockoutBoxes      = coachOrders.stockoutBoxes
unitCost           = unitCostMinor / 100
coachPickupPrice   = coachPickupPriceMinor / 100
revenuePerBox      = revenuePerBoxMinor / 100
```

第一行等价于“期初＋入库－其他出库±调整”，因此既有 `max(0, platformStockBoxes - coachPickupBoxes)` 在数据合法时恰好得到真实 `closingPlatformBoxes`。若存在其他出库，不得错误使用“全部入库－教练拿货”作为期末库存。旧函数只接受元时，转换不中间四舍五入；未来新纯函数应直接计算最小货币单位整数。金额必须处于 JavaScript 安全整数范围，超限拒绝。

### 3.4 缺失、重复、迟到与修正

| 情况 | 处理 |
| --- | --- |
| 必填字段缺失 | 实际快照拒绝生成；不得默认为 0。假设模式必须显式标注假设来源 |
| 可选指标缺失 | 对应 KPI 显示未知，其他已通过勾稽的指标可计算，状态至少为 `degraded` |
| 重复来源事件 | 以 `sourceEventId` 去重；同 ID 同修订同内容返回首次结果，同 ID 不同内容报冲突 |
| 同事件新修订 | 提高 `revision`，改变 `sourceRevision`，生成新快照；不得覆盖旧快照 |
| 开放期间迟到事件 | 重新生成该期间快照，旧快照保留，新的 `supersedesSnapshotId` 指向旧 ID |
| 已结账期间迟到事件 | 按裁判批准的结账政策生成修正快照或计入开放期间；现金事实始终归属实际到账期间，不改写客户端日期 |
| 期间外事件 | 不纳入本期聚合，可由对应期间快照处理；不得为凑勾稽移动事件时间 |
| 冲突或无法解释的勾稽差异 | 实际模式拒绝发布，输出稳定原因码和受影响字段，不以截断或调平隐藏 |

### 3.5 幂等与可重现性

- 建议 `snapshotId` 由 `schemaVersion`、来源逻辑名、期间、时区、`sourceRevision` 和规范化业务载荷的 SHA-256 派生；`generatedAt` 不参与业务载荷哈希。
- 相同规范化业务载荷和来源修订得到相同 `snapshotId`。首次生成结果持久化后，再次请求返回首次结果，包括首次 `generatedAt`。
- 同一 `snapshotId` 对应不同规范化内容必须返回 `SNAPSHOT_CONFLICT`，不能覆盖。
- 同一 `sourceRevision` 若对应不同载荷必须报上游修订冲突。
- 规范化包括固定字段顺序、数组按稳定来源键排序、UTC 时间规范化、整数校验和未知可选字段规则；禁止使用 `Date.now()`、随机数或客户端本地时间参与计算。
- 同一历史快照、同一算法版本和同一组场景输入，必须逐字段得到相同结果。算法版本变化应产生新的报告算法版本，不能改写旧报告的含义。

### 3.6 契约升级

遵循 `schemaVersion = 主版本.次版本`：

- 次版本只允许新增可选字段、原因码或更丰富的可选审计信息；旧消费者必须忽略未知可选字段。
- 删除／改名必填字段、改变单位、期间、价格或库存语义、缩小取值范围，必须升级主版本。
- 读取器显式声明支持的主版本；不支持的主版本拒绝，不尝试猜测转换。
- 跨主版本迁移由独立适配器完成并保留原快照；黄金样例同时覆盖旧版和新版。
- 报告同时记录快照契约版本与计算算法版本，二者不得混用。

## 四、架构路径比较与推荐

| 维度 | 路径一：人工导入校验 JSON／CSV | 路径二：受控只读适配器读 Supabase 聚合 | 路径三：版本化、可审计预计算快照 |
| --- | --- | --- | --- |
| 数据新鲜度 | 取决于人工导出，最低 | 接近上游，较高 | 取决于调度，可明确到分钟／小时／结账批次 |
| 实现复杂度 | 最低，先解决契约与校验 | 中等，需要认证、RLS、聚合与来源修订 | 最高，需要生成、存储、调度、监控与审计 |
| 权限与隐私 | 文件易扩散，需受控目录和最小聚合 | 在线权限清晰但攻击面较大；浏览器仅 anon key | 可只发布最小快照并集中审计，快照仍需防扩散 |
| 离线可用性 | 强 | 弱，读取时依赖网络 | 强，已生成快照可离线使用 |
| 可重现性 | 中高，前提是不可变保存文件与元数据 | 直接查询较弱，上游变化会改变结果 | 最强，不可变快照＋来源修订＋内容哈希 |
| 对纯函数注入的影响 | 无；注入前标准化 | 无；读取在生成器外完成 | 无；只注入已标准化数据 |
| 回滚成本 | 低，停用文件 | 中，停用适配器并回退文件 | 低至中，切回上一快照／算法版本，保留审计链 |

**明确选择：路径三为目标架构，路径一为首个实施入口，路径二只作为路径三的可替换采集器。**

理由：

1. 当前最大风险不是“实时性不足”，而是没有真实来源、勾稽和可重现证据；先做在线读取会放大未定义数据。
2. 人工快照能以最小改动验证字段、算法、权限和报告语义，失败时只需弃用文件。
3. 直接让浏览器查询平台会破坏离线能力，也容易把异步请求带入滑块路径。
4. 预计算快照把在线采集与纯计算解耦，可同时满足同源重算、历史重放、审计和低成本回滚。
5. 只有真实来源稳定、修订号和权限路径均经裁判批准后，自动化才有可靠基础。

推荐数据流：

```text
经批准的业务来源
  → 采集／人工导入（非纯函数层）
  → 契约校验、去重、期间归属、库存现金勾稽（非浏览器渲染路径）
  → 不可变 SandboxSnapshot
  → 标准化适配器
  → SandboxInput + 库存财务输入
  → HTML 生成与 fn.toString() 同源注入
  → 浏览器内同步纯函数重算
```

## 五、库存与现金算法

### 5.1 符号与输入

对同一期间、同一产品、同一币种：

- `B0`：期初平台未发出库存；`I`：期间入库；`A`：经授权调整，可正可负。
- `P`：教练实际拿货出库；`O`：其他出库；`B1`：期末平台未发出库存。
- `H0/H1`：教练期初／期末已拿货库存；`S`：教练终端销售或消耗；`HA`：教练库存调整。
- `C`：单盒成本；`R`：对应销售额单价；`Q`：有效缺货盒数。
- `CR`：期间实际教练回款；`PP`：期间实际平台采购付款。

所有盒数必须为非负整数，只有 `A`、`HA` 是有符号整数；金额在标准层使用非负最小货币单位整数。输入缺单位、币种不一致、非有限数、非整数或安全整数溢出均拒绝。

### 5.2 平台库存与教练库存

**平台期末库存：**

```text
B1 = B0 + I - P - O + A
```

**映射给既有函数的可供教练口径：**

```text
platformStockBoxes = B0 + I - O + A = B1 + P
```

**教练已拿货库存：**

```text
H1 = H0 + P - S + HA
```

平台与教练库存是两个库位／所有权阶段，不得互相覆盖。若教练端数据不完整，`H1` 为未知，不影响已核验的 `B1`，也不得把 `B1 + H1` 解释为某一单库的实盘数。

**勾稽不变量：**

1. `B0 + I - (P + O) + A = B1`。
2. `platformStockBoxes - P = B1`，且 `platformStockBoxes >= 0`。
3. 有实盘数时，`abs(physicalCountBoxes - B1)` 必须按批准原因形成调整或差异异常，不可静默调平。
4. 相邻期间已结账快照满足“上期 `B1`＝本期 `B0`”；修正链未重开期间时不得改变历史期初。
5. 教练数据齐备时，`H0 + P - S + HA = H1`。

### 5.3 库存货值

```text
inventoryAssetValueMinor = B1 × unitCostMinor
```

输出为库存资产，不是现金，也不是本期费用。`B1 < 0`、`unitCostMinor` 缺失或负数时为错误；不得先取绝对值。现有 `Math.max(0, ...)` 仅可作为显示层最后防线，实际快照在调用前必须已证明 `B1 >= 0` 并暴露所有异常。

### 5.4 缺货机会成本

```text
stockoutOpportunityCostMinor = Q × revenuePerBoxMinor
```

这是销售额损失估计，不直接等于利润损失，不改成 `Q × C`，也不直接冲减现金。`Q` 必须来自去重后的有效未满足需求；`R` 使用与缺货需求同渠道、同期间的销售额单价。价格口径未决或任一输入缺失时输出“未知”和警告，不输出 0。

### 5.5 现金、成本与利润边界

```text
coachReceiptsMinor       = Σ 期间实际教练回款事件金额
procurementPaymentsMinor = Σ 期间实际平台采购付款事件金额
inventoryCashNetMinor    = coachReceiptsMinor - procurementPaymentsMinor
```

`inventoryCashNetMinor` 只表示这两条现金流的净额，不代表平台总现金流。退款按独立事件类型和裁判批准的符号规则处理，不能与另一现金域互抵。

采购和现金的时间归属：

| 业务事实 | 库存／损益／现金归属 |
| --- | --- |
| 采购下单 | 形成承诺或订单事实；不自动增加库存，不自动形成现金支出 |
| 验收入库 | 按入库时点增加库存；按批准成本方法形成存货成本 |
| 采购付款 | 按实际付款时点计入现金流出；预付款与到货不得重复计成本 |
| 教练下单／分配 | 形成需求／分配；不自动作出库或现金流入 |
| 教练实际拿货 | 按控制权转移时点做出库；按批准规则确认收入与销货成本 |
| 教练回款 | 按实际到账时点计入现金流入；跨月回款不倒填到订单月现金 |
| 终端销售／消耗 | 减少教练已拿货库存；与平台未发出库存分开 |

销货成本在控制权转移时确认，采购入库不等于当期费用。利润口径可概括为“确认收入－销货成本－其他费用”，期末库存仍保留为资产。**不得把库存货值再加入现金余额，也不得把同一存货价值同时计入资产和利润。**

### 5.6 缺货、超卖、迟到数据与账实不符

这些状态必须分别输出原因码，不能统一表现为负库存：

| 状态 | 判别与处理 |
| --- | --- |
| 缺货 | 有效需求 `orderedBoxes` 大于已满足量，且存在未取消欠货；记 `Q`，平台库存仍须非负 |
| 超卖 | `allocatedBoxes > 可供分配库存`，说明分配承诺超额；单独报 `OVERSOLD_ALLOCATION`，不把它当实际出库 |
| 迟到／不完整数据 | 实际拿货大于可供库存，且期初、入库或出库来源不完整；报 `INCOMPLETE_SOURCE`，实际快照拒绝发布 |
| 账实不符 | 来源齐备但流水推导与实盘不一致，或无凭证出库导致 `P > B0 + I - O + A`；报 `INVENTORY_MISMATCH`，等待授权调整 |
| 显示截断 | 既有函数仍可把负显示值截为 0，但必须同时保留错误，不得使快照通过验收 |

### 5.7 异常处理优先级

1. 契约、单位、类型和期间错误：拒绝。
2. 重复冲突、来源修订冲突、非法调整：拒绝。
3. 库存勾稽失败或实际拿货超过可发出量：拒绝实际快照并分类。
4. 可选价格／教练端数据缺失：相关 KPI 未知，快照 `degraded`。
5. 任何异常均不得通过凭空补库存、客户端改日期、静默置 0 或重新标价来“修复”。

历史快照由不可变输入和固定算法版本重算，结果必须一致；BEP 393／317 不因本方案变化。

## 六、纯函数与同源注入边界

### 6.1 环境边界

`finance.ts` 及未来浏览器重算函数必须保持环境无关、同步、确定性：

- 禁止 `fs`、`path`、`process`、Supabase 客户端、网络请求、`fetch`、动态 `import()` 和浏览器异步数据 API；
- 禁止读取当前时间、随机数、DOM、全局配置或模块外可变变量；
- 数据读取、CSV 解析、JSON 校验、网络访问、权限判断、快照生成和持久化全部在纯计算层之外；
- HTML 注入前只接收已通过契约和勾稽的标准化输入；原始响应、CSV 行或数据库行不得直接进入报告；
- 滑块事件只更新本地状态并调用同源函数。现有 50ms 界面防抖可保留，但防抖后不得触发异步取数。

### 6.2 `fn.toString()` 依赖闭包与顺序

被注入函数的源码会脱离原模块执行，因此每个函数的运行时依赖必须同时注入：

1. 叶子纯函数不得引用未注入的辅助函数、常量、枚举对象或导入值；TypeScript 类型可以引用，因为编译后擦除。
2. 当前财务注入顺序保持：`computeInventoryAssetValue`、`computeStockoutOpportunityCost`、`computeInventoryCashFlow`、`computeInventoryKpis`。
3. `computeInventoryKpis` 依赖前三个函数；未来新增辅助函数必须加入注入清单并排在所有调用者之前。函数声明虽有提升，显式拓扑顺序仍作为评审和测试契约。
4. 引擎函数、`parseControlValue` 与财务函数分别在既定脚本区注入；不得依赖 Node 包装器、模块作用域或服务端变量。
5. 标准化快照数据通过 JSON 注入，不通过拼接可执行 JavaScript。序列化需转义 `<`、`</script>`、U+2028／U+2029 等边界，防止数据变成脚本。
6. 算法所需的固定常量必须随函数显式注入或作为参数传入，版本变化纳入算法版本和黄金测试。

建议的实现期验收方式是用 `new Function` 在无关模块环境中提取并执行注入函数，再比对 Node 与浏览器结果；这只是测试设计，本任务不编写测试代码。

## 七、身份、权限与隐私

### 7.1 身份

- 认证使用 Supabase Auth 的认证主体；管理员授权可由现有 `camp_admins` 白名单语义扩展评估，但任何权限变化须另行批准。
- `userCode` 仅属于本机打卡业务码，禁止作为登录凭证、数据联接主键、订单／教练／库存关联键或审计 actor。
- 若未来需要教练服务端身份，使用独立不透明 ID；若确需关联本机打卡身份，必须另立映射契约，明确主动授权、一次性绑定、唯一性、冲突、解绑、撤销和保留期，不得隐式复用打卡身份。

### 7.2 权限路径

1. 浏览器侧只允许 `anon key`；`service_role` 严禁进入仓库、HTML、日志或前端。
2. 实际经营快照默认为 `internal`，仅授权管理员／经营分析角色读取；不进入公共事件或公开页面。
3. 若使用 Supabase 只读路径，RLS 必须基于 `auth.uid()` 和明确角色／白名单，默认拒绝；只能返回批准的最小聚合列。
4. 直接表／视图读取或只读 RPC 是否允许均属待裁判决策；本方案不假定其存在。任何新 RPC 都应只读、参数受限、返回聚合、记录审计，并通过非管理员与越权测试。
5. 自动快照生成器若需更高权限，应位于受控服务端，凭据不入仓库；其输出仍只含最小数据集。
6. 审计日志追加写，记录不透明 actor、动作、`snapshotId`、`sourceRevision`、内容哈希、时间和原因码，不记录敏感原文。

### 7.3 隐私与泄露防护

- 公共事件、HTML 输入快照、错误信息和普通日志不得包含报名资料、联系方式、邮箱、Supabase UID、本机 `userCode`、支付原始报文或受限身份映射。
- 实际快照导出的 HTML 与源快照同级管理；生成可公开版本时必须重新使用假设数据，不是简单隐藏几个字段。
- 文件下载、日志和监控只记录文件名／ID／哈希等最小元数据；访问与导出保留审计。
- 数据保留期限、快照下载范围、是否允许教练级下钻均需裁判决定；未批准前只设计月度聚合。

## 八、时间与日期

### 8.1 三种时间不得混用

1. **服务端时间点**：UTC ISO 8601、毫秒精度，例如 `2026-10-31T16:00:00.000Z`。
2. **业务日历期间**：使用 IANA 时区解释月度边界，再由服务端转换为 UTC 半开区间。
3. **本机 `YYYY-MM-DD`**：仅属于既有浏览器本地打卡日期键，不是服务端财务事实时间，不参与库存、订单或现金期间计算。

客户端本地时间不得决定采购、出库、销售、回款、结账或快照时间。客户端可提交显示时区偏好，但服务端必须依据批准的合同与可信时间源确定事实归属。

### 8.2 月度与跨月规则

- 月度期间为 `[月初 00:00@timezone, 次月月初 00:00@timezone)`，由服务端转换为 UTC；不能统一写成固定 24 小时天数。
- 跨月订单按事实拆分：下单归下单月、入库归验收月、出库／收入／成本归控制权转移月、付款／回款归实际现金月。
- 迟到回款计入实际到账开放期间，同时保留对原订单的核销关联；不把现金倒填到订单月。
- 已结账期间的修正采用新 `sourceRevision` 和新快照，记录 `supersedesSnapshotId`；是否重述历史报表或作为本期调整由裁判批准。
- `generatedAt` 是生成时间，`asOf` 是数据截止时间，`periodStart/End` 是业务期间，三者不可互相替代。
- 时区、月度结账日和历史修正政策属于待裁判决策；确定前不得自动结账。

## 九、分阶段实施计划

所有阶段均以本方案获裁判批准为总前置条件。A—C 阶段不得要求修改线上数据或执行 Supabase 迁移；只有 D 阶段才可在单独评审批准后考虑迁移、RPC、快照表或权限变更。

### 阶段 A：人工快照导入与契约校验

- **前置条件**：批准 v1 字段、单位、期间和假设／实际标签；准备无敏感信息的黄金样例。
- **独立交付物**：快照 JSON Schema／校验器设计实现、人工 JSON 导入、CSV 到 JSON 的受控转换、标准化适配器、数据质量报告；CSV 元数据不全时拒绝而非猜测。
- **预计涉及文件或模块**：未来新增 `tools/sandbox` 的快照契约／导入／适配模块及测试；报告入口的接线需单独评审。不得修改底层引擎和 BEP。
- **测试要求**：黄金样例、缺失／重复／负数、金额单位、期间、幂等、历史重放、HTML 注入与滑块重算；现有 64 项回归。
- **回滚方式**：停用导入入口，删除未发布生成物，恢复纯假设输入；无需数据库回滚。
- **不得同时发生的范围扩张**：不接 Supabase、不加真实用户明细、不做自动调度、不改线上数据、不创建表／RPC。

### 阶段 B：真实库存／订单数据补齐

- **前置条件**：裁判确定权威业务系统、所有者、事件口径、成本与缺货价格口径；A 的勾稽测试通过。
- **独立交付物**：真实库存、教练订单、采购和现金事件的数据字典及离线台账；来源 ID／修订号；经授权调整流程；历史起始点和数据质量基线。
- **预计涉及文件或模块**：未来独立数据契约、脱敏样例、离线采集／对账工具及文档；如需业务系统表结构，必须另行派工，不在本阶段擅动 Supabase。
- **测试要求**：期初到期末连续勾稽、跨月订单、迟到回款、退款、超卖、实盘差异、相邻期间链、现金与收入成本分离。
- **回滚方式**：停止采用新来源，回退到 A 的已验证快照；保留来源审计，不删除历史证据。
- **不得同时发生的范围扩张**：不同时做实时同步、不开放前端直读、不借打卡表存经营数据、不自动修正账实差异。

### 阶段 C：只读平台适配器

- **前置条件**：B 的真实来源稳定；已存在且获批的只读聚合访问能力；RLS／权限方案和最小数据集通过安全评审；来源修订可用。
- **独立交付物**：服务端或生成期的受控只读适配器、权限映射、聚合查询、脱敏与错误分类；输出仍是 A 定义的不可变快照。
- **预计涉及文件或模块**：未来平台只读适配模块、服务端配置和契约测试；浏览器仅使用 anon key 的既有边界不变。
- **测试要求**：非管理员拒绝、跨角色越权、敏感字段扫描、空数据、上游超时、重复／乱序事件、来源修订冲突、离线上届快照可用。
- **回滚方式**：禁用适配器并切回 A／B 的人工快照；快照契约和纯函数无需回滚。
- **不得同时发生的范围扩张**：不开启浏览器在线滑块取数、不引入写权限、不放 `service_role` 到前端、不自动发布快照。

### 阶段 D：自动快照、监控与审计

- **前置条件**：C 稳定运行；裁判单独批准自动化、存储、刷新频率、保留期，以及是否新增只读 RPC／快照表／迁移。
- **独立交付物**：计划生成、不可变快照存储、内容哈希、修正链、监控告警、访问与导出审计、版本切换和保留策略。
- **预计涉及文件或模块**：未来快照生成任务、受控服务端模块，以及经单独批准的 Supabase 迁移／RPC／RLS；任何线上变更另行验收。
- **测试要求**：调度幂等、重复执行、失败重试、历史重放、回滚、权限与泄露、监控告警、版本兼容、负载与恢复。
- **回滚方式**：停用调度，切到上一快照和上一算法版本；新增数据库对象按已批准迁移计划回退，不覆盖历史快照。
- **不得同时发生的范围扩张**：不借自动化改变财务口径、不自动结账未决期间、不公开实际 HTML、不直接推送 `main` 或发布网站。

## 十、测试与验收方案

以下只定义测试，不编写测试代码。

| 类别 | 样例／操作 | 验收结果 |
| --- | --- | --- |
| 黄金库存样例 | `B0=100, I=200, P=150, O=20, A=-10` | `B1=120`，`platformStockBoxes=270`，全部勾稽成立 |
| 黄金教练库存 | `H0=30, P=150, S=140, HA=0` | `H1=40`，与平台期末 120 分列 |
| 黄金资产与缺货 | 成本 160 元／盒、缺货 10 盒、销售额单价 660 元／盒 | 库存资产 19,200 元；缺货机会成本 6,600 元；不使用成本价算缺货 |
| 现金与成本分离 | 分别提供实际回款、采购付款、入库和出库事件 | 现金按到账／付款月，存货按入库，销货成本按出库，无重复计入 |
| 库存与现金勾稽 | 连续多期含采购、出库、回款、调整 | 每期及跨期不变量成立；库存资产不进入现金或利润 |
| 缺货 | 有效需求大于满足量且库存不为负 | 输出缺货量和销售额机会成本，不制造负库存 |
| 超卖 | 分配量大于可分配量，实际出库仍合法 | 输出超卖异常，不把它等同实际拿货或缺货 |
| 负数与非法数 | 负盒数、负金额、非整数、NaN／Infinity、超安全整数 | 实际快照拒绝；授权调整以外的负值不被截断隐藏 |
| 拿货大于可供量 | 来源完整／不完整各一例 | 分别分类账实不符／来源不完整；实际快照拒绝，显示 0 也不能掩盖错误 |
| 重复数据 | 同事件重复、同 ID 不同内容、新修订 | 去重、冲突拒绝、新快照三种行为正确 |
| 空数据 | 来源明确无事件与来源缺失各一例 | 前者为 0，后者为未知／拒绝，语义不混淆 |
| 部分字段缺失 | 缺价格、教练库存、现金或期初 | 仅批准的降级 KPI 可用；必要字段缺失即拒绝 |
| 快照幂等 | 同输入多次生成、同 ID 不同载荷 | 返回首次结果；冲突报 `SNAPSHOT_CONFLICT` |
| 历史可重现 | 固定快照＋算法版本跨环境重算 | 逐字段一致，不受当前时间、随机数和网络影响 |
| `fn.toString()` 注入 | 脱离模块执行所有注入函数 | 无外部闭包／Node API，依赖完整，顺序正确 |
| 滑块同步重算 | 修改全部滑块、数字输入和场景 | 只使用已注入数据与同源函数，无网络请求，结果与生成期一致 |
| HTML 安全 | 含脚本边界字符的快照字段 | 不逃逸脚本上下文，不执行注入内容 |
| 权限与泄露 | 非管理员、跨角色、公开事件、HTML、日志扫描 | 默认拒绝；无报名、联系方式、UID、userCode、支付原文 |
| 契约兼容 | 同主版本新增可选字段、主版本语义变化 | 前者旧读者可用，后者拒绝猜测并经独立迁移 |
| 现有回归 | 执行完整沙盘测试和类型检查 | 7 个文件、64 项测试全绿，类型检查通过 |
| BEP 防线 | 重跑既有指标／生成器测试及历史反向断言 | 393／317 不回归；既有历史反向断言保持不删不改 |

验收还需证明：仅新增本设计文档；没有生产代码、数据库、迁移、线上配置或发布变更。

## 十一、待裁判决策清单

以下问题无法仅凭现有仓库确定，不得用猜测替代：

1. 真实库存由哪个业务系统维护，哪个角色拥有最终解释权？
2. 教练订单的“拿货”以配货、发货、签收还是控制权转移为准？退货如何归属？
3. 平台采购与教练回款是否存在可审计流水；来源事件 ID、修订号和核销关系是否完整？
4. 缺货销售额单价采用终端、教练还是其他渠道口径；混合渠道如何处理？
5. 缺货按需求确认、分配失败、欠货还是补发口径计量，取消需求如何剔除？
6. 单盒成本采用标准成本、移动加权、批次还是其他方法；期末库存适用哪个成本快照？
7. 数据刷新频率、可接受延迟和上游不可用时允许的降级方式是什么？
8. 历史数据起始日期、期初建账时点和历史快照保留期限是什么？
9. 月度业务时区、结账日、已结账修正和重述政策是什么？
10. 是否允许新增只读 RPC、快照表、相关视图或权限变更；由谁审批和维护？
11. 是否允许教练级数据下钻，还是仅允许月度聚合？各角色可见字段是什么？
12. 实际经营快照及生成 HTML 的分发范围、下载权限和保留期是什么？
13. 其他出库包含哪些类型，教练退换货和平台退货入库如何单独建模？
14. 采购预付款、退款、教练退款和跨月核销采用什么现金与调整口径？
15. 是否存在多产品、多仓库或多币种；若存在，v1 是否明确限定单产品、单汇总库位和 CNY？
16. 若未来需要教练身份或本机打卡关联，是否批准另立身份映射契约及其授权／撤销流程？
17. 自动快照生成所需的调度环境、密钥托管、监控责任人与故障响应时限是什么？

在上述事项获批前，实施任务只能围绕已批准的阶段和契约展开，不得以“打通数据”为由扩展到线上写操作或生产发布。
