# 一盒一码激活契约 v1

- 状态：待裁判审核，未实现
- 所属体系：10.1 打卡 App 业务重构契约
- 交付边界：仅逻辑契约；不包含 SQL、迁移、RPC 或前端实现

> 依据：裁判定稿《系统模块蓝图》及 10.1 任务书。当前仓库未提供《V7.1 运营指南》原文，4.1 工单与 6.1 准入的原文细则未能独立核验；相关补充规则均标记为 `[待裁判确认]`。

## 1. 目标与所有权

本契约定义产品码、激活审核、打卡权限和教练归属的最小业务闭环：

1. 无有效产品码的用户可以浏览，但不能激活 21 天营打卡权限，也不能产生计入经营漏斗的有效激活数据。
2. 体验码用于首购或种子期免费体验；充值码用于复购、延伸营或维持期续费。
3. 激活成功后才写入或延续 `user_coach_relation`，记录当前 `referrer_id`。
4. 教练每生成一箱 24 盒，系统在同一原子操作中预生成 24 个全局唯一的 `unused` 码。
5. 本模块不改变 `storage-v3` 的本机 `userCode`、日期键、每日记录或迁移语义，不把产品码当作登录凭证。

产品码模块拥有码和激活事实；教练关系模块拥有当前归属及归属历史；发货模块只提供已核验发货事实。任何前端均不得直接写入这些权威状态。

## 2. 码格式与用途

| 类型 | 前缀 | 格式 | 用途 |
| --- | --- | --- | --- |
| 体验码 | `JH-EL` | `JH-EL-XXXX` | 首购或种子期免费产品激活 |
| 充值码 | `JH-RC` | `JH-RC-XXXX` | 复购、延伸营或维持期续费激活 |

- `XXXX` 为 4 位随机码；字符集、是否排除易混字符及是否增加校验位均为 `[待裁判确认]`。
- 完整码全局唯一，生成碰撞必须重试；不得把本机 `userCode`、手机号、姓名或教练编号嵌入码面。
- 码类型由服务端生成记录决定，客户端不得通过修改前缀改变类型。
- 码面属于敏感操作凭证：普通日志、公共事件和雷达结果不得输出完整码，只保留不透明 `codeId` 或经遮蔽的码面。

## 3. 逻辑实体

### 3.1 ProductCode

| 字段 | 规则 |
| --- | --- |
| `codeId` | 不透明服务端 ID，公共事件只引用此 ID。 |
| `codeType` | `experience / recharge`，分别对应 `JH-EL / JH-RC`。 |
| `codeHash` | 用于服务端核验的码面散列；是否额外加密保存由安全设计确定。 |
| `state` | `unused / pending_review / active / revoked`。 |
| `coachId` | 本码所属教练；平台官方库存使用 `PLATFORM_ID`。 |
| `caseId` | 所属箱；每箱固定 24 个码。 |
| `activationId` | 激活后关联的唯一激活记录。 |
| `version / createdAt / updatedAt` | 通用并发与审计字段。 |

### 3.2 CodeActivation

至少保存 `activationId`、`codeId`、申请人 `authUserId`、受限 `camperCode` 映射、发货核验引用、审核决定、激活时间、操作者与 `version`。申请资料、发货凭证等敏感内容仅以受限引用保存。

### 3.3 user_coach_relation

| 字段 | 规则 |
| --- | --- |
| `relationId` | 不透明关系 ID。 |
| `authUserId` | 用户登录主体，等于 `auth.uid`；激活和托管均不得改写。 |
| `camperCode` | 用户本机 `userCode` 的受限映射；不是认证主体，不得因激活或托管改变。 |
| `referrer_id` | 当前归属教练或平台官方账号 `PLATFORM_ID`。 |
| `sourceCodeId` | 建立本次归属的产品码。 |
| `validFrom / validTo` | 当前归属有效期；历史关系不得覆盖删除。 |
| `reason` | `activation / dormancy_trusteeship / admin_correction`。 |
| `version` | 并发控制与审计。 |

同一用户同一时间最多一条有效当前关系。关系历史永久保留；“永久绑定”指可追溯的归属链，不排除第 10 号休眠托管契约规定的平台接管。

## 4. 状态机

```text
unused ──用户输入码──> pending_review ──发货与申请核验通过──> active
  │                         │                                  │
  └──────────────┬──────────┴──────────────┬───────────────────┘
                 └────授权撤销／作废──────> revoked
```

| 当前状态 | 事件 | 下一状态 | 必备条件与副作用 |
| --- | --- | --- | --- |
| `unused` | 用户提交激活申请 | `pending_review` | 码存在、未撤销、格式与类型合法；仅创建审核申请，不开放打卡、不绑教练。 |
| `pending_review` | 核验发货并通过审核 | `active` | 原子完成激活、打卡授权和归属写入；见第 5 节。 |
| `unused / pending_review / active` | 授权撤销或作废 | `revoked` | 仅授权角色执行，记录原因码与操作者；保留历史。 |
| `revoked` | 任意激活命令 | 不变并拒绝 | 终态，不得重新激活或换绑。 |

- `active → revoked` 是可审计撤销分支，不是每个激活码的必经步骤。
- 审核拒绝后回到 `unused`、进入 `revoked`，还是使用独立拒绝状态，为 `[待裁判确认]`；未确认前不得由客户端自行恢复码状态。
- 审核超时、重复申请和发货核验失败的工单类型、处理角色与 SLA 为 `[待裁判确认]`。

## 5. 激活原子流程

激活必须由服务端命令执行，并满足以下顺序与原子性：

1. 校验调用者已认证，读取其 `auth.uid`；不得信任客户端提交的 uid。
2. 锁定待激活码及申请记录，确认状态为 `pending_review`，并校验幂等键。
3. 核验发货事实、申请人与收货关系、码类型和业务期次；任何必需事实缺失均不得激活。
4. 将码由 `pending_review` 推进为 `active`，创建唯一 `CodeActivation`。
5. 写入或延续 `user_coach_relation`，记录当前 `referrer_id` 和 `sourceCodeId`。
6. 开通对应产品范围的打卡权限；权限范围、营期和是否允许叠加激活按第 6 节处理。
7. 追加激活、归属与授权审计事件，再提交同一业务事务。

任一步骤失败，整个激活命令回滚；不得出现“码已 active 但未授权”“已授权但未绑教练”或“扣减库存但未激活”的部分状态。跨模块无法使用单事务时，必须使用带补偿的可重试编排，并禁止中间状态被当作有效激活读取。

## 6. 体验码与充值码规则

### 6.1 体验码

- 适用于首购和种子期免费产品；免费不代表可以绕过发货、激活或归属审核。
- 首次有效激活建立当前 `referrer_id`，通常为本码所属教练。
- 体验码激活是否计入“月新增付费”默认不计入；如存在付费体验产品，其计入条件为 `[待裁判确认]`。
- 同一用户可激活的体验码数量、重复体验限制和营期覆盖规则为 `[待裁判确认]`。

### 6.2 充值码

- 用于复购、延伸减脂营或维持期产品，不得借用体验码冒充复购。
- 已有当前归属时，充值码激活不得擅自把用户改绑到发码教练；收益归属以当前有效关系及休眠托管生效时间为准。
- 无任何当前关系时，是否允许充值码直接建立 `referrer_id` 为 `[待裁判确认]`。
- 支付成功、发货核验和激活的先后依赖，以及退款后是否撤销打卡权限，为 `[待裁判确认]`；未确认前不得仅凭客户端支付截图激活。

## 7. 箱、库存与补货数量

1. 教练获得有效拿货资格后，每生成一箱，系统创建唯一 `caseId`，固定箱规格为 24 盒。
2. 创建箱与预生成 24 个 `unused` 码必须是同一原子操作；不足 24 个不得把箱标记为可发放。
3. `unusedCodesCount` 只统计该教练当前 `state = unused` 的码；`pending_review`、`active`、`revoked` 均不计入。
4. 码进入 `pending_review` 即不再属于可自由分配库存，防止一个码同时发给多人。
5. 默认补货预警线为 12；纯函数和 `< 12` 的边界由 `coach-radar-desensitized-v1.md` 统一定义。
6. 箱内码是否允许体验码与充值码混合、混箱时的数量配比为 `[待裁判确认]`。
7. 休眠教练名下未使用码的移交、冻结或撤销规则见托管契约；未决部分为 `[待裁判确认]`。

## 8. 教练准入衔接

教练进入可拿货状态前，必须满足“18 天有效打卡＋8 人完赛”的业务门槛。有效打卡的统计窗口、8 人的去重主体、完赛证据、审核工单和发放资格的服务端命令细节为 `[待裁判确认]`。

未取得有效资格时，禁止生成教练箱和教练所属码。平台官方库存使用 `PLATFORM_ID`，不得绕过教练准入规则。

## 9. 幂等、并发与安全

- 激活、审核、撤销和生成箱命令均要求 `idempotencyKey`；实体写操作要求 `expectedVersion`。
- 同一码的重复相同激活请求返回首次结果；相同幂等键对应不同用户、发货单或码时返回 `IDEMPOTENCY_CONFLICT`。
- 两个用户同时提交同一码时，最多一个申请能占用该码；其他请求得到 `STATE_CONFLICT`，不得排队共享激活。
- 码输入必须限流并记录安全审计；失败响应不得区分“接近正确的码”或泄露有效码清单。
- 浏览器只有 `anon key` 不代表拥有激活权限；所有权威写入必须由受控服务端或具备明确授权与 RLS 的 RPC 完成。
- 禁止 `service_role` 进入前端、仓库、日志或生成报告。

## 10. 事件与错误码

建议领域事件：`CodeActivationRequested`、`CodeActivated`、`CodeRevoked`、`CoachCaseGenerated`、`UserCoachRelationAssigned`。事件只包含不透明 ID、状态事实、时间、原因码和关联 ID，不包含完整码面、原始发货资料或本机 `userCode`。

模块错误至少区分：

- `CODE_NOT_AVAILABLE`：码不存在、已使用、已占用或已撤销，外部响应可按安全策略合并。
- `CODE_TYPE_MISMATCH`：码类型不适用于当前业务。
- `SHIPMENT_VERIFICATION_REQUIRED`：缺少已核验发货事实。
- `ACTIVATION_STATE_CONFLICT`：状态或版本不允许激活。
- `COACH_NOT_ELIGIBLE`：教练无有效拿货资格。
- `CASE_CODE_GENERATION_INCOMPLETE`：一箱未能完整生成 24 个码。
- `IDEMPOTENCY_CONFLICT`：幂等键相同但业务载荷不同。
