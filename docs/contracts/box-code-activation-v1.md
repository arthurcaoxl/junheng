# 一盒一码激活契约 v1

- 状态：裁判终裁已落实，未实现
- 所属体系：10.1 打卡 App 业务重构契约
- 交付边界：仅逻辑契约；不包含 SQL、迁移、RPC 或前端实现

> 依据裁判终裁与 V7.1 运营指南，重点落实 4.1 无线上支付版工单闭环、6.1 教练准入及 7.1 归属稳定边界。

## 1. 目标与所有权

本契约定义产品码、激活审核、打卡权限和教练归属的最小业务闭环：

1. 无有效产品码的用户可以浏览，但不能激活 21 天营打卡权限，也不能产生计入经营漏斗的有效激活数据。
2. 体验码用于首购或种子期产品体验；充值码用于复购、延伸营或维持期续费。体验码一律不计入教练月新增付费用户。
3. 激活成功后才写入或延续 `user_coach_relation`，记录当前 `referrer_id`。
4. 教练每生成一箱 24 盒，系统在同一原子操作中预生成 24 个全局唯一的 `unused` 码。
5. 一码一用；一个码最多绑定一个激活主体和一条激活事实，一经绑定不可解绑、不可复用、不可改绑其他用户。
6. 本模块不改变 `storage-v3` 的本机 `userCode`、日期键、每日记录或迁移语义，不把产品码当作登录凭证。

产品码模块拥有码和激活事实；教练关系模块拥有当前归属及归属历史；发货与线下收款模块只提供经人工核验的事实。任何前端均不得直接写入这些权威状态。

## 2. 码格式与用途

| 类型 | 前缀 | 格式 | 用途 |
| --- | --- | --- | --- |
| 体验码 | `JH-EL` | `JH-EL-XXXX` | 首购或种子期产品体验激活 |
| 充值码 | `JH-RC` | `JH-RC-XXXX` | 复购、延伸营或维持期续费激活 |

- `XXXX` 为 4 位随机码，字符集固定为 `ABCDEFGHJKMNPQRSTUVWXYZ23456789`，排除易混淆的 `I`、`L`、`O`、`0`、`1`。指南只规定 `JH-EL-XXXX` 示例，未另定字符集，故采用裁判批准字符集。
- v1 不增加校验位，不扩展码长；完整码全局唯一，生成碰撞必须重试。
- 不得把本机 `userCode`、手机号、姓名或教练编号嵌入码面。
- 码类型由服务端生成记录决定，客户端不得通过修改前缀改变类型。
- 码面属于敏感操作凭证：普通日志、公共事件和雷达结果不得输出完整码，只保留不透明 `codeId` 或经遮蔽的码面。

## 3. 逻辑实体

### 3.1 ProductCode

| 字段 | 规则 |
| --- | --- |
| `codeId` | 不透明服务端 ID，公共事件只引用此 ID。 |
| `codeType` | `experience / recharge`，分别对应 `JH-EL / JH-RC`。 |
| `codeHash` | 用于服务端核验的码面散列；额外加密属于安全实现，不改变本契约。 |
| `state` | `unused / pending_review / active / revoked`。 |
| `coachId` | 本码发放来源教练；平台官方库存使用 `PLATFORM_ID`，该字段保留来源事实。 |
| `caseId` | 所属箱；每箱固定 24 个码。 |
| `activationId` | 激活后关联的唯一激活记录，永不得改指向另一用户。 |
| `version / createdAt / updatedAt` | 通用并发与审计字段。 |

### 3.2 CodeActivation

至少保存 `activationId`、`codeId`、申请人 `authUserId`、受限 `camperCode` 映射、发货与线下收款核验引用、审核决定、激活时间、操作者与 `version`。申请资料、发货凭证等敏感内容仅以受限引用保存。

审核拒绝必须记录拒绝原因、审核人和时间，并关联补发的新 `codeId`；原激活绑定和审核历史不得删除。

### 3.3 user_coach_relation

| 字段 | 规则 |
| --- | --- |
| `relationId` | 不透明关系 ID。 |
| `authUserId` | 用户登录主体，等于 `auth.uid`；激活和托管均不得改写。 |
| `camperCode` | 用户本机 `userCode` 的受限映射；不是认证主体，不得因激活或托管改变。 |
| `referrer_id` | 当前归属教练或平台官方账号 `PLATFORM_ID`。 |
| `sourceCodeId` | 建立本次归属的产品码。 |
| `validFrom / validTo` | 当前归属有效期；历史关系不得覆盖删除。 |
| `reason` | `activation / dormancy_trusteeship / admin_correction`。 |
| `version` | 并发控制与审计。 |

同一用户同一时间最多一条有效当前关系。关系历史永久保留；一码一用和不可解绑不排除休眠托管或经审计的人工权益保护更正，但这些流程必须新建关系区间，不得改写激活码的原始绑定事实。

## 4. 状态机

```text
unused ──提交申请──> pending_review ──审核通过──> active
  │                     │
  │                     └──审核拒绝──> revoked ──补发──> 新 codeId 的 unused
  │
unused / active ──授权撤销或作废──> revoked
```

| 当前状态 | 事件 | 下一状态 | 必备条件与副作用 |
| --- | --- | --- | --- |
| `unused` | 用户提交激活申请 | `pending_review` | 码存在、格式与类型合法；仅创建审核申请，不开放打卡、不绑教练。 |
| `pending_review` | 发货、申请及必要线下收款核验通过 | `active` | 原子完成激活、打卡授权和归属写入；见第 5 节。 |
| `pending_review` | 审核拒绝 | `revoked` | 记录原因并重新发放一个全新的 `unused` 码；原码不得回到库存。 |
| `unused / active` | 授权撤销或作废 | `revoked` | 仅授权角色执行，记录原因与操作者；不删除绑定和归属历史。 |
| `revoked` | 任意激活、恢复或换绑命令 | 不变并拒绝 | 终态，不得重新激活、恢复为 `unused` 或换绑。 |

- `active → revoked` 是可审计撤销分支，不是正常激活的必经步骤；撤销不等于解绑或允许原码再次使用。
- 审核补发必须创建新 `codeId`、新码面和新审计关联，不得复制原码的激活事实。
- v1 工单按指南由运营人工核验，不设自动审核通过或自动超时关闭；未决申请保持 `pending_review`，重复申请按第 9 节处理。

## 5. 激活原子流程

激活必须由服务端命令执行，并满足以下顺序与原子性：

1. 校验调用者已认证，读取其 `auth.uid`；不得信任客户端提交的 uid。
2. 锁定待激活码及申请记录，确认状态为 `pending_review`，并校验幂等键。
3. 按指南 4.1 核验发货记录、用户信息、授权状态和必要的线下真实收款凭证；系统状态不得替代真实财务凭证。
4. 将码由 `pending_review` 推进为 `active`，创建唯一 `CodeActivation`。
5. 写入或延续 `user_coach_relation`，记录当前 `referrer_id` 和 `sourceCodeId`。
6. 开通已核验产品范围内的打卡权限，不在 v1 自动叠加或延长既有营期。
7. 追加激活、归属与授权审计事件，再提交同一业务事务。

任一步骤失败，整个激活命令回滚；不得出现“码已 active 但未授权”“已授权但未绑教练”或“扣减库存但未激活”的部分状态。跨模块无法使用单事务时，必须使用带补偿的可重试编排，并禁止中间状态被当作有效激活读取。

## 6. 体验码与充值码规则

### 6.1 体验码

- 适用于首购和种子期产品体验；免费体验不代表可以绕过发货、激活或归属审核。
- 首次有效激活建立当前 `referrer_id`，通常为体验码来源教练；来源教练已休眠时由平台审核并保持或建立 `PLATFORM_ID` 归属，不得回绑休眠教练。
- 体验码无论是否对应首购场景，均不计入教练月新增付费用户；付费用户统计只按生命周期契约的真实付费口径执行。
- v1 不支持体验码叠加、自动续期或自动延长营期；重复体验申请必须人工审核，不自动产生额外权益。

### 6.2 充值码

- 用于复购、延伸减脂营或维持期产品，不得借用体验码冒充复购。
- 已有当前归属时，充值码激活不得改绑到发码教练；休眠托管后的当前归属为 `PLATFORM_ID`，复购继续归平台，不回绑原教练。
- 无当前关系且来源教练具备有效经营资格时，可由充值码激活建立来源教练归属；来源教练休眠或无资格时建立 `PLATFORM_ID` 归属。
- v1 采用线下收款、人工对账和审核后激活，不处理线上支付或资金清算。退款、撤销与权益调整必须人工复核并留痕，不自动解绑或复用原码。

## 7. 箱、库存与补货数量

1. 教练获得有效拿货资格后，每生成一箱，系统创建唯一 `caseId`，固定箱规格为 24 盒。
2. 创建箱与预生成 24 个 `unused` 码必须是同一原子操作；不足 24 个不得把箱标记为可发放。
3. `unusedCodesCount` 只统计该教练当前 `state = unused` 的码；`pending_review`、`active`、`revoked` 均不计入。
4. 码进入 `pending_review` 即不再属于可自由分配库存，防止一个码同时发给多人；审核拒绝后进入 `revoked`，不得回补库存。
5. 默认补货预警线为 12；`unusedCodesCount < 12` 触发预警，12 不触发，与雷达契约一致。
6. v1 每箱只包含一种 `codeType`，不支持体验码与充值码混箱及箱内配比。
7. 教练休眠不自动把 `unused / pending_review / active` 改写为其他状态。休眠后来源代码停止以原教练名义新发放，由平台复核库存、在途申请和发货；已激活权益继续有效，后续复购归属仍按当前关系确定。

## 8. 教练准入衔接

教练进入可拿货状态前，必须同时满足指南 6.1 的门槛：

- 本人完成 21 天营且有效 `recordedDays >= 18`，以本人打卡和结营记录为证。
- 扶持 8 名去重用户完成 21 天打卡，以 8 名用户的归属和完赛记录为证。
- 运营完成准入审核，保存审核人、时间、证据引用和价格权限记录；达成后解锁 7 折拿货资格，首箱 24 盒。

未取得有效资格时，禁止生成教练箱和教练所属码。平台官方库存使用 `PLATFORM_ID`，不得绕过教练准入规则。

## 9. 幂等、并发与安全

- 激活、审核、撤销、补发和生成箱命令均要求 `idempotencyKey`；实体写操作要求 `expectedVersion`。
- 同一码的重复相同激活请求返回首次结果；相同幂等键对应不同用户、发货单或码时返回 `IDEMPOTENCY_CONFLICT`。
- 两个用户同时提交同一码时，最多一个申请能占用该码；其他请求得到 `ACTIVATION_STATE_CONFLICT`，不得排队共享激活。
- 码输入必须限流并记录安全审计；失败响应不得泄露有效码清单或码面近似信息。
- 浏览器只有 `anon key` 不代表拥有激活权限；所有权威写入必须由受控服务端或具备明确授权与 RLS 的 RPC 完成。
- 禁止 `service_role` 进入前端、仓库、日志或生成报告。

## 10. 事件与错误码

领域事件包括：`CodeActivationRequested`、`CodeActivated`、`CodeActivationRejected`、`CodeReplacementIssued`、`CodeRevoked`、`CoachCaseGenerated`、`UserCoachRelationAssigned`。事件只包含不透明 ID、状态事实、时间、原因码和关联 ID，不包含完整码面、原始发货资料或本机 `userCode`。

模块错误至少区分：

- `CODE_NOT_AVAILABLE`：码不存在、已使用、已占用或已撤销，外部响应可按安全策略合并。
- `CODE_TYPE_MISMATCH`：码类型不适用于当前业务。
- `SHIPMENT_VERIFICATION_REQUIRED`：缺少已核验发货事实。
- `PAYMENT_VERIFICATION_REQUIRED`：应核验真实付费但缺少线下收款核验事实。
- `ACTIVATION_STATE_CONFLICT`：状态或版本不允许激活。
- `COACH_NOT_ELIGIBLE`：教练无有效拿货资格。
- `CASE_CODE_GENERATION_INCOMPLETE`：一箱未能完整生成 24 个码。
- `IDEMPOTENCY_CONFLICT`：幂等键相同但业务载荷不同。

## 11. 契约验收清单

- [ ] 两种前缀严格区分，4 位字符均来自批准字符集，完整码全局唯一。
- [ ] 一码最多激活一次；绑定后不可解绑、复用或改绑，撤销也不能恢复原码。
- [ ] 审核拒绝进入 `revoked` 并补发新码，原码永不回到 `unused`。
- [ ] 无码、待审核和已撤销状态均不能获得有效打卡权限。
- [ ] `pending_review` 不提前写当前归属；只有激活原子流程才能写。
- [ ] 激活后 `auth.uid` 与本机 `userCode` 不变，当前 `referrer_id` 可追溯。
- [ ] 体验码不计月新增付费；休眠后的充值激活不回绑原教练。
- [ ] 每箱严格生成 24 个同类型 `unused` 码，部分失败不留下可用半箱。
- [ ] `unusedCodesCount` 口径统一，11 个触发预警、12 个不触发。
- [ ] 日志、公共事件、雷达和普通错误信息不泄露完整码、原始档案或打卡记录。
- [ ] 未修改 `storage-v3`，未混入 CEO 沙盘纯函数引擎代码。
