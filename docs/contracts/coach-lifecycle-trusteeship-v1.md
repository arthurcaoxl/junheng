# 教练生命周期与休眠托管契约 v1

- 状态：裁判终裁已落实，未实现
- 所属体系：10.1 打卡 App 业务重构契约
- 交付边界：仅逻辑契约；不包含 SQL、迁移、批处理脚本或前端实现

> 依据裁判终裁与 V7.1 运营指南，重点落实 4.1 工单、6.1 准入、6.3 活跃与休眠、7.2 休眠托管及 7.3 用户权益。

## 1. 目标与不变量

本契约定义教练从活跃到缓冲、再到休眠托管的月度状态机，以及用户归属和复购收益的切换边界。

必须始终满足：

1. 用户本机 `userCode` 不变。
2. 用户登录 `auth.uid` 不变。
3. 休眠生效后，当前关系的 `referrer_id` 转给平台官方账号 `PLATFORM_ID`，原教练关系进入历史。
4. 休眠生效后的复购不再向原教练计提差价；平台接管不等于删除用户历史或重置打卡营期。
5. 状态迁移、归属转移和收益 cutoff 使用同一可审计 `effectiveAt`，不能由前端按钮分散修改。
6. 原 coach 及其 staff 在托管后失去已转平台用户的雷达访问，不获得任何财务分润权限。

## 2. 逻辑实体

### 2.1 CoachLifecycle

| 字段 | 规则 |
| --- | --- |
| `coachId` | 不透明教练主体 ID，不使用邮箱或 userCode。 |
| `state` | `active / buffer / dormant`。 |
| `bufferStreak` | 连续满足低新增条件的月份数；active 为 0。 |
| `lastEvaluatedPeriod` | 最近已结算月份，防止重复推进。 |
| `stateEnteredAt` | 当前状态生效的服务端 UTC 时间。 |
| `dormantAt` | 休眠生效时间；非 dormant 为空。 |
| `version` | 并发控制。 |

### 2.2 CoachMonthlyMetric

至少包含 `coachId`、`period`、`newPaidUsers`、`evaluationRunId`、`sourceRevision`、`calculatedAt` 和指标证据引用。指标是按 `Asia/Shanghai` 自然月生成的不可变事实，不得由客户端直接填写。

### 2.3 托管事件与关系历史

每次托管保存 `trusteeshipId`、`coachId`、`effectiveAt`、原 `referrer_id`、目标 `PLATFORM_ID`、影响关系数量、批次运行 ID 和审计引用。`user_coach_relation` 的历史字段与一盒一码契约共用，不另建冲突的归属真相。

## 3. 状态机

```text
active ──上月新增付费 < 4──> buffer ──连续第 2 个低新增月──> dormant
   ↑                            │
   └────缓冲月新增付费 ≥ 4──────┘
```

| 当前状态 | 月度评估 | 下一状态 | 计数与副作用 |
| --- | --- | --- | --- |
| `active` | `newPaidUsers >= 4` | `active` | `bufferStreak = 0`，不转移关系。 |
| `active` | `newPaidUsers < 4` | `buffer` | `bufferStreak = 1`，发送缓冲提醒，不转移关系。 |
| `buffer` | `newPaidUsers >= 4` | `active` | `bufferStreak = 0`，取消未执行的休眠动作。 |
| `buffer` | `newPaidUsers < 4` | `dormant` | 这是连续第 2 个低新增月，执行平台托管。 |
| `dormant` | 普通月度评估 | `dormant` | 不重复转移已托管关系。 |

“连续两月”指连续两个已结算的完整自然月均满足 `newPaidUsers < 4`。第二个月评估完成后才进入 `dormant`，不得在第一个低新增月提前转用户。

- 评估月缺失、指标不完整或批处理失败时不得猜测为 0 并推进状态。
- `newPaidUsers = 4` 为恢复／保持活跃；只有严格 `< 4` 才进入低新增计数。
- v1 不支持 `dormant → active` 自动恢复，也不自动回绑原用户。确有误判或服务争议时走人工复核，仅生成独立审计结论，不改写既有托管事实。
- 教练主动退出、违规停用不属于本月度生命周期状态机，必须使用独立管理原因和权限流程，不得冒充低新增休眠。

## 4. 月新增付费口径

1. 统计单位为去重后的新付费用户数，不是码数、订单数或盒数。
2. 只统计统计月内首次形成有效付费关系、具备真实线下收款核验和发货核验并完成有效激活的用户；系统审核状态不得替代真实财务凭证。
3. 体验码一律不计入“新增付费”，无论其用于首购还是种子期体验。
4. 同一用户只在首次形成有效付费关系的自然月计一次；历史用户复购、延伸、维持和回流不计“新增”，同月多个有效充值激活也只计一次。
5. 归属教练以首次有效付费激活时的当前 `user_coach_relation.referrer_id` 为准；平台归属不计入任何教练。
6. 自然月固定使用 `Asia/Shanghai`，每月从当月 1 日 00:00:00 起至次月 1 日 00:00:00 前；上一完整自然月闭区间由相邻两个月界确定。
7. 退款、撤销激活或迟到事实通过新 `sourceRevision` 和人工复核记录修正，不静默覆盖已执行指标，不自动反向托管或重复计提收益。
8. 指标必须保存来源修订，任何历史修正均不得改变已发生关系的原始时间线。

## 5. 每月 1 日批处理设计

### 5.1 调度与输入

- 受控调度器固定于每月 1 日 00:00（`Asia/Shanghai`）触发，统计上一个完整自然月。
- 本次托管 `effectiveAt` 固定为当前月 1 日 00:00（`Asia/Shanghai`）对应的 UTC 时刻；延迟重试仍使用该月界，不使用客户端时间或任意重试时刻另立 cutoff。
- 首次运行只评估已经完整结束且事实齐备的自然月；v1 不对缺少完整历史事实的早期月份做推断性补跑。
- 输入为已冻结或具有明确 `sourceRevision` 的上月激活与关系事实；不得在指标未齐备时推进状态。
- 调度身份只存在于受控服务端，禁止把 `service_role` 写入浏览器、仓库或日志。

### 5.2 运行步骤

1. 以 `jobType + period` 创建唯一 `evaluationRunId`，同一月份重复触发返回已有运行或进入受控重试。
2. 计算并持久化全部教练的 `CoachMonthlyMetric`，记录来源修订和异常清单。
3. 按 `coachId` 锁定生命周期记录，检查 `lastEvaluatedPeriod` 和 `expectedVersion`，防止两个批次重复推进。
4. 先输出状态迁移计划：保持 active、进入 buffer、恢复 active、进入 dormant。
5. 对 dormant 计划执行用户托管和收益 cutoff，写入审计事件。
6. 更新 `lastEvaluatedPeriod`，生成处理摘要和复核工单。
7. 任一教练失败不得被静默跳过；按教练隔离错误并进入可重试队列，整批状态标记为部分失败或失败。

### 5.3 幂等与补跑

- 同一教练、同一月份、同一来源修订重复执行不得重复转移关系或重复生成工单。
- 同一月份来源修订变化时创建新修订评估，不直接改写历史；反向托管或收益调整只能人工审核，不在 v1 自动执行。
- 具备完整事实的历史补跑必须按时间顺序执行，并先模拟后续月份受到的影响；不得跳过中间月份直接休眠。
- 并发批处理与人工归属调整冲突时，以版本检查和可审计人工裁定解决，禁止最后写入者无声覆盖。

## 6. 休眠托管原子流程

进入 dormant 时，按教练执行以下最小闭环：

1. 确认第二连续低新增月的指标有效，记录 `dormantAt = effectiveAt`。
2. 将教练生命周期状态推进为 `dormant`。
3. 由员工复核服务记录、异常工单和未结事项，保证用户服务连续性；复核不改动月度判定事实。
4. 找出 `effectiveAt` 时仍归属该教练的当前 `user_coach_relation`。
5. 对每条关系结束原区间：`validTo = effectiveAt`、`reason = dormancy_trusteeship`，保留原 `referrer_id` 历史。
6. 创建以 `PLATFORM_ID` 为当前 `referrer_id` 的新关系区间，`validFrom = effectiveAt`。
7. 保持每条关系的 `authUserId` 与受限 `camperCode` 映射不变。
8. 将 `effectiveAt` 及之后成立的新复购差价计提对象切为平台，原教练不再获得该期间后的差价。
9. 创建平台服务接管工单并记录影响数量；未结教练工单转平台责任队列，保留原处理链，原 coach 及其 staff 不得继续凭旧范围处理。

同一教练的关系转移必须可重试且可核对。无法保证单事务时，应使用“准备—执行—核验—完成”的编排状态，中间状态不得被收益系统误读为仍归教练；不得先改收益再遗留用户关系，也不得只改显示层标签。

## 7. 收益与复购 cutoff

- `effectiveAt` 前已成立的教练差价按原归属保留，历史关系和历史结算事实不因托管重写。
- `effectiveAt` 及之后成立的复购，不向原教练计提差价。
- cutoff 以复购权益有效激活的成立时间与 `effectiveAt` 比较；线下支付和发货核验是激活前置证据，不另设相互冲突的归属时点。
- 依指南 7.2，托管后的复购收益按平台规则核算，原教练不再计提托管后的差价与相关奖励；不得把原教练继续列为服务或奖励归属主体。
- 退款或未结算调整必须按原始生效时间人工对账，防止双重计提，不自动回写托管历史。
- 财务分润 RPC 不属于 staff 权限，托管过程也不得向 staff 返回金额或收益明细。

## 8. `PLATFORM_ID` 与身份约束

- `PLATFORM_ID` 是受控服务端环境配置的平台官方关系主体，不是本机 `userCode`，也不能是某个真实教练的 ID。
- 每个环境必须有唯一、稳定且受控的映射，客户端不得传入或选择该值；具体配置与 provisioning 属于实现边界，不改变本契约。
- 平台接管只改变当前 `referrer_id` 与服务责任，不改变用户登录、匿名身份、打卡记录或历史营期。
- 归属、休眠和托管规则须在使用前向相关角色公示并完成合规评审；托管后保留通知和人工申诉记录，不降低用户权益，v1 不把用户再次同意设为系统托管前置条件。

## 9. 准入与库存衔接

- 教练获得 active 经营资格前，须完成 21 天营且本人 `recordedDays >= 18`，并扶持 8 名去重用户完成 21 天打卡；以本人记录、结营结果、用户归属和完赛记录为证。
- 运营审核保存审核人、时间、证据引用和价格权限记录，达成后解锁 7 折拿货资格，首箱 24 盒。
- 进入 buffer 不自动撤销拿货资格或冻结码库存。
- 进入 dormant 不自动改变产品码状态：停止以来源教练名义新发放 `unused` 码，`pending_review` 由平台复核，`active` 权益保持有效；任何补发、撤销或发货均须平台留痕，不得回绑休眠教练。
- 已激活关系按本契约转平台；不得通过重新生成用户码或修改 auth 账号完成所谓“转移”。

## 10. 事件、工单与审计

事件包括：`CoachEnteredBuffer`、`CoachReactivatedFromBuffer`、`CoachEnteredDormant`、`CoachUsersTrusteed`、`CoachMonthlyEvaluationFailed`。

事件只包含教练 ID、期间、状态、数量、来源修订、生效时间和原因码，不携带用户明细。用户级托管记录保存在受限审计存储中。

工单类型固定覆盖 `buffer_review / dormancy_review / platform_takeover / evaluation_failure`，由员工或平台责任队列处理；依指南进行每日异常检查、每周服务复盘和每月托管核对，v1 不另设数字化 SLA。批处理日志不得输出完整用户码、健康档案、联系方式或财务明细。

## 11. 契约验收清单

- [ ] 首个低新增月只进入 buffer，不转用户、不切收益。
- [ ] 第二个连续低新增月才进入 dormant；中间任意月份 `>= 4` 会清零连续计数。
- [ ] 月界与调度固定为 `Asia/Shanghai` 每月 1 日 00:00，只统计上一完整自然月。
- [ ] 体验码、历史复购和平台归属均不计教练月新增付费。
- [ ] 指标缺失或批次失败不会被当成 0 推进状态。
- [ ] 每月 1 日重复运行、补跑和并发运行均不会重复托管。
- [ ] 托管前后用户本机 `userCode` 与 `auth.uid` 完全不变。
- [ ] 当前 `referrer_id` 转为 `PLATFORM_ID`，原关系及原因完整留痕。
- [ ] cutoff 后复购不计原教练差价，cutoff 前历史不被重写。
- [ ] dormant 后原 coach／staff 失去已转平台用户雷达访问，staff 仍无法读取财务分润。
- [ ] 未修改 `storage-v3`，未混入 CEO 沙盘纯函数引擎代码。
