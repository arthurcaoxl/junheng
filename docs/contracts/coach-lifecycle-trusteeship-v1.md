# 教练生命周期与休眠托管契约 v1

- 状态：待裁判审核，未实现
- 所属体系：10.1 打卡 App 业务重构契约
- 交付边界：仅逻辑契约；不包含 SQL、迁移、批处理脚本或前端实现

> 依据：裁判定稿《系统模块蓝图》及 10.1 任务书。当前仓库未提供《V7.1 运营指南》原文，4.1 工单、6.1 准入和 7.2 休眠托管的原文细则未能独立核验；恢复资格、统计时区等未决项均标记为 `[待裁判确认]`。

## 1. 目标与不变量

本契约定义教练从活跃到缓冲、再到休眠托管的月度状态机，以及用户归属和复购收益的切换边界。

必须始终满足：

1. 用户本机 `userCode` 不变。
2. 用户登录 `auth.uid` 不变。
3. 休眠生效后，当前关系的 `referrer_id` 转给平台官方账号 `PLATFORM_ID`，原教练关系进入历史。
4. 休眠生效后的复购不再向原教练计提差价；平台接管不等于删除用户历史或重置打卡营期。
5. 状态迁移、归属转移和收益 cutoff 必须有同一可审计生效时间，不能由前端按钮分散修改。

## 2. 逻辑实体

### 2.1 CoachLifecycle

| 字段 | 规则 |
| --- | --- |
| `coachId` | 不透明教练主体 ID，不使用邮箱或 userCode。 |
| `state` | `active / buffer / dormant`。 |
| `bufferStreak` | 连续满足低新增条件的月份数；active 为 0。 |
| `lastEvaluatedPeriod` | 最近已结算月份，防止重复推进。 |
| `stateEnteredAt` | 当前状态生效的服务端 UTC 时间。 |
| `dormantAt` | 休眠生效时间；非 dormant 为空。 |
| `version` | 并发控制。 |

### 2.2 CoachMonthlyMetric

至少包含 `coachId`、`period`、`newPaidUsers`、`evaluationRunId`、`sourceRevision`、`calculatedAt` 和指标证据引用。指标是按自然月生成的不可变事实，不得由客户端直接填写。

### 2.3 托管事件与关系历史

每次托管保存 `trusteeshipId`、`coachId`、`effectiveAt`、原 `referrer_id`、目标 `PLATFORM_ID`、影响关系数量、批次运行 ID 和审计引用。`user_coach_relation` 的历史字段与一盒一码契约共用，不另建冲突的归属真相。

## 3. 状态机

```text
active ──上月新增付费 < 4──> buffer ──连续第 2 个低新增月──> dormant
   ↑                            │
   └────缓冲月新增付费 ≥ 4──────┘
```

| 当前状态 | 月度评估 | 下一状态 | 计数与副作用 |
| --- | --- | --- | --- |
| `active` | `newPaidUsers >= 4` | `active` | `bufferStreak = 0`，不转移关系。 |
| `active` | `newPaidUsers < 4` | `buffer` | `bufferStreak = 1`，发送缓冲提醒，不转移关系。 |
| `buffer` | `newPaidUsers >= 4` | `active` | `bufferStreak = 0`，取消未执行的休眠动作。 |
| `buffer` | `newPaidUsers < 4` | `dormant` | 这是连续第 2 个低新增月，执行平台托管。 |
| `dormant` | 普通月度评估 | `dormant` | 不重复转移已托管关系；恢复规则另行批准。 |

“连续 2 月 buffer”指连续两个已结算自然月均满足 `newPaidUsers < 4`。第二个月评估通过后才进入 `dormant`，不得在第一个低新增月提前转用户。

- 评估月缺失、指标不完整或批处理失败时不得猜测为 0 并推进状态。
- `newPaidUsers = 4` 为恢复／保持活跃；只有严格 `< 4` 才进入低新增计数。
- `dormant → active` 的恢复条件、是否经过人工审核、是否重新分配原用户均为 `[待裁判确认]`。未确认前不自动恢复或回绑。
- 教练主动退出、违规停用与休眠的关系为 `[待裁判确认]`；不得混用原因码。

## 4. 月新增付费口径

1. 统计单位为去重后的用户数，不是码数、订单数或盒数。
2. 默认仅统计已完成有效充值码激活、具备已确认交易及发货核验的新增付费关系；免费体验码不计入“新增付费”。
3. 同一用户同一月份多个有效充值激活只计一次；历史用户复购是否算“新增”默认不算，若裁判希望计入回流用户，需 `[待裁判确认]`。
4. 归属教练以激活时当前有效 `user_coach_relation.referrer_id` 为准；平台归属不计入任何教练。
5. 退款、撤销激活、跨月激活和迟到支付事实的统计修正规则为 `[待裁判确认]`。
6. 统计自然月时区建议为 `Asia/Shanghai`，但最终业务时区、月界和迟到事实重述政策为 `[待裁判确认]`。
7. 指标必须保存来源修订，修正历史月份时不得静默覆盖已经执行的托管事件。

## 5. 每月 1 日批处理设计

### 5.1 调度与输入

- 每月 1 日由受控调度器触发，统计上一个完整自然月。
- 具体触发时刻、时区、首次运行月份和历史补跑范围为 `[待裁判确认]`。
- 输入为已冻结或具有明确 `sourceRevision` 的上月激活与关系事实；不得在指标未齐备时推进状态。
- 调度身份只存在于受控服务端，禁止把 `service_role` 写入浏览器、仓库或日志。

### 5.2 运行步骤

1. 以 `jobType + period` 创建唯一 `evaluationRunId`，同一月份重复触发返回已有运行或进入受控重试。
2. 计算并持久化全部教练的 `CoachMonthlyMetric`，记录来源修订和异常清单。
3. 按 `coachId` 锁定生命周期记录，检查 `lastEvaluatedPeriod` 和 `expectedVersion`，防止两个批次重复推进。
4. 先输出状态迁移计划：保持 active、进入 buffer、恢复 active、进入 dormant。
5. 对 dormant 计划执行用户托管和收益 cutoff，写入审计事件。
6. 更新 `lastEvaluatedPeriod`，生成处理摘要和待办工单。
7. 任一教练失败不得被静默跳过；按教练隔离错误并进入可重试队列，整批状态标记为部分失败或失败。

### 5.3 幂等与补跑

- 同一教练、同一月份、同一来源修订重复执行不得重复转移关系或重复生成工单。
- 同一月份来源修订变化时创建新修订评估，不直接改写历史；是否需要反向托管或收益调整必须人工审核。
- 补跑历史月份必须按时间顺序执行，并先模拟后续月份受到的影响；不得跳过中间月份直接休眠。
- 并发批处理与人工归属调整冲突时，以版本检查和可审计人工裁定解决，禁止最后写入者无声覆盖。

## 6. 休眠托管原子流程

进入 dormant 时，按教练执行以下最小闭环：

1. 确认第二连续低新增月的指标有效，记录 `dormantAt = effectiveAt`。
2. 将教练生命周期状态推进为 `dormant`。
3. 找出 `effectiveAt` 时仍归属该教练的当前 `user_coach_relation`。
4. 对每条关系结束原区间：`validTo = effectiveAt`、`reason = dormancy_trusteeship`，保留原 `referrer_id` 历史。
5. 创建以 `PLATFORM_ID` 为当前 `referrer_id` 的新关系区间，`validFrom = effectiveAt`。
6. 保持每条关系的 `authUserId` 与受限 `camperCode` 映射不变。
7. 将 `effectiveAt` 之后的新复购差价计提对象切为平台；原教练不再获得该期间后的差价。
8. 创建平台服务接管工单并记录影响数量；未结教练工单的转移策略为 `[待裁判确认]`。

同一教练的关系转移必须可重试且可核对。无法保证单事务时，应使用“准备—执行—核验—完成”的编排状态，中间状态不得被收益系统误读为仍归教练；不得先改收益再遗留用户关系，也不得只改显示层标签。

## 7. 收益与复购 cutoff

- `effectiveAt` 前已成立的教练差价按原归属保留；是否追溯调整未结算或退款部分为 `[待裁判确认]`。
- `effectiveAt` 及之后成立的复购，不向原教练计提差价。
- 激活时间、支付时间、发货核验时间不一致时，哪个事实决定收益 cutoff 为 `[待裁判确认]`；未确认前必须选择保守的人工对账，不得双重计提。
- 奖励抵扣、数据奖励和裂变奖励是否同样停止，需与差价分开裁定；本契约不自动扩大“停止差价”到其他奖励。
- 财务分润 RPC 不属于 staff 权限，托管过程也不得向 staff 返回金额或收益明细。

## 8. `PLATFORM_ID` 与身份约束

- `PLATFORM_ID` 是受控服务端配置的平台官方关系主体，不是本机 `userCode`，也不能是某个真实教练的 ID。
- 具体配置位置、主体 provisioning 方式和多环境映射为 `[待裁判确认]`。
- 平台接管只改变当前 `referrer_id` 与服务责任，不改变用户登录、匿名身份、打卡记录或历史营期。
- 用户无感迁移的告知文案、通知渠道和是否需要用户同意为 `[待裁判确认]`。

## 9. 准入与库存衔接

- 教练获得 active 经营资格前，须满足“18 天有效打卡＋8 人完赛”；证据与审核工单细则为 `[待裁判确认]`。
- 进入 buffer 不自动撤销拿货资格或冻结码库存。
- 进入 dormant 后，未使用产品码、在途激活申请、已发货未激活订单的处理方式为 `[待裁判确认]`。
- 已激活关系按本契约转平台；不得通过重新生成用户码或修改 auth 账号完成所谓“转移”。

## 10. 事件、工单与审计

建议事件：`CoachEnteredBuffer`、`CoachReactivatedFromBuffer`、`CoachEnteredDormant`、`CoachUsersTrusteed`、`CoachMonthlyEvaluationFailed`。

事件只包含教练 ID、期间、状态、数量、来源修订、生效时间和原因码，不携带用户明细。用户级托管记录保存在受限审计存储中。

缓冲、休眠和批处理失败均需生成规范工单；工单类型、责任人、通知方式和 SLA 为 `[待裁判确认]`。批处理日志不得输出完整用户码、健康档案、联系方式或财务明细。

## 11. 契约验收清单

- [ ] 首个低新增月只进入 buffer，不转用户、不切收益。
- [ ] 第二个连续低新增月才进入 dormant；中间任意月份 `>= 4` 会清零连续计数。
- [ ] 指标缺失或批次失败不会被当成 0 推进状态。
- [ ] 每月 1 日重复运行、补跑和并发运行均不会重复托管。
- [ ] 托管前后用户本机 `userCode` 与 `auth.uid` 完全不变。
- [ ] 当前 `referrer_id` 转为 `PLATFORM_ID`，原关系及原因完整留痕。
- [ ] cutoff 后复购不计原教练差价，cutoff 前历史不被重写。
- [ ] dormant 重复评估不会重复转移关系或生成重复工单。
- [ ] staff 无法经托管或雷达接口读取财务分润。
- [ ] 未修改 `storage-v3`，未混入 CEO 沙盘纯函数引擎代码。
