# 教练雷达脱敏契约 v1

- 状态：待裁判审核，未实现
- 所属体系：10.1 打卡 App 业务重构契约
- 交付边界：仅逻辑契约；不包含 SQL、迁移、RPC 或前端实现

> 依据：裁判定稿《系统模块蓝图》及 10.1 任务书。当前仓库未提供《V7.1 运营指南》原文，8.1 雷达 SOP 的原文细则未能独立核验；工单 SLA、无记录灯号等未决项均标记为 `[待裁判确认]`。

## 1. 目标与权限边界

`get_coach_radar_v1()` 用于教练和被授权 staff 的服务跟进，不是原始健康档案查询、财务分润查询或公共统计接口。

- coach：只能查看自己当前名下用户的雷达结果。
- staff：只能查看自己被分配教练名下的用户，且必须通过同一 RPC 的服务端权限过滤。
- admin：可按管理职责查看，但仍受本契约最小返回字段约束。
- 调用者身份只取服务端 `auth.uid`；不得通过传入 coachId、staffId、userCode 或邮箱切换查看范围。
- 未认证、角色无效、分配已撤销或超出分配范围时返回空结果或 `FORBIDDEN`，不得返回目标用户是否存在的额外信息。

角色与分配关系以 `staff-role-permissions-v1.md` 为准。

## 2. RPC 签名与执行约束

```text
get_coach_radar_v1()
```

v1 不接受客户端范围参数。服务端根据调用者角色和当前有效分配关系自动确定可见集合，避免“先传教练 ID 再补权限检查”的越权设计。

- 查询为只读、同步返回，不修改打卡、归属、库存或财务状态。
- 任何直接表访问、后续字段扩展和导出功能都必须重新执行同等权限与脱敏评审。
- 浏览器仅使用 `anon key`；服务端必须再次鉴权，不能信任前端隐藏按钮。
- 财务分润字段、金额、教练收益和奖励负债不得进入本 RPC。

## 3. 返回字段与绝对禁止项

### 3.1 已批准的用户级字段

| 字段 | 类型与单位 | 规则 |
| --- | --- | --- |
| `camper_code` | string | 受限体验官代码的雷达展示映射，不是 `auth.uid`，不得作为登录或授权依据。 |
| `weight_delta` | number \| null，kg | 当前有效代表体重减初始有效体重；原始体重不返回。 |
| `waist_delta` | number \| null，cm | 当前有效腰围减初始有效腰围；原始腰围不返回。 |
| `bmi` | number \| null | 服务端根据当前身高和当前有效代表体重计算；身高不返回。 |
| `stage` | string | 当前业务阶段，建议枚举 `camp / extension / maintenance / completed`；最终枚举为 `[待裁判确认]`。 |

差值和 BMI 的保留位数、四舍五入规则及 `-0` 归一规则为 `[待裁判确认]`。缺失身高、初始值或当前有效值时返回 `null`，不得用 0 冒充，也不得为了计算差值返回原始值。

### 3.2 灯号字段冲突 `[待裁判确认]`

任务同时要求“展示红／黄／绿灯”和“只返回上述五个字段”。仅有余下五个字段时，客户端无法在不接触 `last_checkin_at` 或 `records` 的情况下可靠计算灯号。

因此，v1 落地前必须由裁判二选一确认：

1. **推荐方案**：允许每个用户行额外返回唯一的派生字段 `light: red / yellow / green / unknown`，由服务端按第 4 节计算；仍不得返回最后打卡时间或原始记录。
2. 将 `stage` 明确定义为同时包含业务阶段和灯号的结构化对象，但这会改变 `stage` 的既有语义，需要同步确认结构。

在裁判确认前，实现不得擅自增加字段，也不得把最后打卡时间、结营时间或复购记录塞入 `stage` 绕过脱敏限制。`unknown` 仅用于时间证据缺失，不能伪装成绿灯。

### 3.3 绝对禁止返回

以下字段不得以顶层、嵌套、数组、别名、调试字段或错误详情形式出现：

- `height_cm`
- `initial_weight_kg`
- `records`

同时禁止返回：原始体重或腰围、饮食照片、每日行为项、联系方式、姓名、邮箱、`auth.uid`、完整产品码、支付信息、财务分润、原始复购记录、精确最后打卡时间，以及可还原上述信息的序列化快照。

## 4. 灯号逻辑

灯号由服务端可信时间和有效打卡事实计算，优先级如下：

| 优先级 | 灯号 | 条件 |
| --- | --- | --- |
| 1 | 红灯 | 距最后一次有效打卡超过 72 小时，或已结营但未完成规定复购。 |
| 2 | 黄灯 | 不满足红灯，且距最后一次有效打卡超过 48 小时。 |
| 3 | 绿灯 | 不满足红／黄灯，且打卡与复购状态正常。 |

边界规则：

- “超过”使用严格 `>`；恰好 48 小时不属于黄灯，恰好 72 小时不属于因超时产生的红灯。
- 红灯条件优先；结营未复购即使在 48 小时内也为红灯。
- 48 小时＜未打卡时长 ≤ 72 小时为黄灯；未打卡时长 ＞ 72 小时为红灯。
- 时间比较使用服务端当前时间和统一时间戳，不信任客户端时钟。
- 既有本机 `records` 只有本地日期键时，如何得到小时级最后打卡时间，以及从未打卡、数据缺失、跨时区和离线未同步用户的灯号，均为 `[待裁判确认]`。不得凭空补时间或直接判绿。
- “结营”的完成条件、“未复购”的宽限期、充值码激活是否等同于复购，以及退款后的灯号处理为 `[待裁判确认]`。

## 5. 指标计算口径

1. 当前体重必须沿用 `storage-v3` 的 `getRepresentativeWeight` 语义，由服务端或受控适配器计算，不在雷达另写一套早／中／晚权重。
2. 衣物扣减只读取每日快照，不得用当前全局默认值重算历史，更不得通过雷达修改任何每日记录。
3. 初始体重遵循用户显式初始值优先、缺失时按既有契约推导的规则；原始初始体重仍不得返回。
4. 当前值取当前业务窗口内日期最晚的有效值；当前窗口与 `stage` 的对应关系为 `[待裁判确认]`。
5. BMI 使用未四舍五入的原始值参与后续分类，展示精度与分类阈值分离；本 RPC 不返回身高。
6. 数据不足时相关派生指标为 `null`，其他已批准字段仍可返回；不得为补齐指标回传 `records`。

## 6. 补货预警纯函数

```ts
checkRestockAlert(unusedCodesCount, restockPoint = 12): boolean
```

逻辑定义：

```text
checkRestockAlert = unusedCodesCount < restockPoint
```

- 默认 `restockPoint = 12`，因此 11 个触发，12 个不触发。
- `unusedCodesCount` 只统计 `unused` 产品码，不包含 `pending_review / active / revoked`。
- 两个参数都必须是非负安全整数；非法值应抛出参数错误或由调用方在边界拒绝，不得静默截断、取绝对值或四舍五入。
- 函数保持同步、确定、无副作用；不读取数据库、DOM、网络、当前时间或沙盘引擎。
- 该函数只判断库存预警，不决定教练是否具备拿货资格，也不直接创建补货订单。
- RPC 是否返回教练级 `unusedCodesCount / restockAlert` 属于雷达字段扩展，需 `[待裁判确认]`；不得借库存预警返回用户额外信息。

## 7. 雷达 SOP 与工单衔接

| 灯号 | 业务动作 | 待确认事项 |
| --- | --- | --- |
| 绿灯 | 保持正常服务，不创建高优先级催办。 | 例行回访频率 `[待裁判确认]`。 |
| 黄灯 | 创建跟进任务，由当前教练或被分配 staff 联系用户。 | 首次跟进时限、提醒次数和升级条件 `[待裁判确认]`。 |
| 红灯 | 创建高优先级流失挽回或结营复购工单。 | 处理 SLA、升级给平台的时间、关闭原因码 `[待裁判确认]`。 |

- 工单只保存不透明用户引用、灯号、原因码、责任人和状态，不把原始健康记录复制到工单。
- 归属休眠转平台后，新工单责任人必须为平台；历史工单保留原处理链，是否重新分配未结工单为 `[待裁判确认]`。
- 用户拒绝联系、号码无效、已复购等关闭原因应使用规范原因码，不记录不必要的自由文本敏感信息。

## 8. 审计、速率与数据保护

- 记录调用者、角色、结果数量、查询时间、关联 ID 和授权结果，不记录返回的原始敏感载荷。
- 对异常高频查询、连续角色切换和分配撤销后的访问进行安全审计；速率阈值为 `[待裁判确认]`。
- 雷达页面不得提供“导出原始记录”或经浏览器隐藏字段绕过脱敏的能力。
- 缓存键必须包含调用者与授权版本；角色、归属或分配变化后立即使旧缓存失效。
- 公共事件不得携带雷达用户行；CEO 沙盘如需使用，只能接收另行批准的最小聚合快照，不能复用本 RPC 的个人级结果。
