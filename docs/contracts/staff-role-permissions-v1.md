# Staff 角色与权限契约 v1

- 状态：待裁判审核，未实现
- 所属体系：10.1 打卡 App 业务重构契约
- 交付边界：仅逻辑契约；不包含 SQL、迁移、RPC 或前端实现

> 依据：裁判定稿《系统模块蓝图》及 10.1 任务书。当前仓库未提供《V7.1 运营指南》原文，4.1 工单和 8.1 雷达 SOP 的原文细则未能独立核验；角色冲突和 150 用户口径等未决项均标记为 `[待裁判确认]`。

## 1. 目标与最小权限原则

本契约把现有 `camp_admins` 邮箱白名单扩展为受控业务角色目录，支持 `admin / coach / staff` 三类角色。

- `camp_admins` 是历史表名，不代表其中每行都是管理员。
- 角色只由受控服务端或 admin 管理，用户不得通过前端、JWT 自定义声明或修改本地存储自助提权。
- 默认拒绝：没有有效角色、角色停用、分配失效或权限无法证明时，不得读取业务数据。
- staff 的唯一业务数据能力是查看被分配教练的脱敏雷达及处理相应服务工单，不具有财务分润查看权。

## 2. `camp_admins.role` 逻辑变更

新增逻辑列：

| 字段 | 规则 |
| --- | --- |
| `role` | 必填枚举 `admin / coach / staff`。 |
| `is_active` | 停用后所有该角色权限立即失效。 |
| `auth_user_id` 或等效受限映射 | 用于把登录 `auth.uid` 与角色稳定关联；邮箱不能替代认证主体。 |
| `version / updatedAt / updatedBy` | 角色变化必须可并发控制、可审计。 |

- 既有白名单行在迁移设计中的默认角色建议为 `admin`，但正式回填策略为 `[待裁判确认]`；本契约不编写迁移。
- 同一认证主体是否允许多个有效角色为 `[待裁判确认]`。未确认前按单一有效角色设计，禁止通过叠加角色绕过 staff 限制。
- 邮箱变更、匿名账号升级为邮箱账号和 auth 用户删除后的角色清理规则为 `[待裁判确认]`。
- `service_role` 只存在于受控服务端，不得进入前端、仓库、错误日志或报告。

## 3. 权限矩阵

| 能力 | admin | coach | staff |
| --- | --- | --- | --- |
| 管理角色与 staff-coach 分配 | 允许 | 禁止 | 禁止 |
| 查看脱敏雷达 | 按管理职责 | 仅当前自己名下用户 | 仅被分配教练名下用户 |
| 处理雷达服务工单 | 允许 | 仅自己责任工单 | 仅分配范围内服务工单 |
| 查看原始 `records` | 不因 admin 身份自动获得；另行授权 | 禁止 | 禁止 |
| 查看 `height_cm / initial_weight_kg` | 不通过雷达返回；其他管理能力另行授权 | 禁止 | 禁止 |
| 查看财务分润 RPC | 按财务权限另行批准 | 仅本人财务且另行批准 | **绝对禁止** |
| 管理产品码、撤销激活 | 按专门命令授权 | 仅本人被授权操作 | 禁止 |
| 执行休眠批处理 | 仅受控系统／专门管理命令 | 禁止 | 禁止 |
| 修改 `referrer_id` | 仅受控托管或人工裁定命令 | 禁止 | 禁止 |

前端菜单隐藏不是权限。所有 RPC、直接表访问、视图、导出、事件订阅和错误响应都必须执行同样的服务端授权。

## 4. Staff-Coach 分配关系

### 4.1 逻辑实体 `staff_coach_assignment`

| 字段 | 规则 |
| --- | --- |
| `assignmentId` | 不透明 ID。 |
| `staffId` | 必须对应有效 staff 角色。 |
| `coachId` | 必须对应有效 coach 角色。 |
| `state` | `active / revoked / expired`。 |
| `validFrom / validTo` | 分配有效期；历史不得覆盖删除。 |
| `assignedBy / assignedAt` | 仅 admin 或受控系统写入。 |
| `version` | 并发与容量校验。 |

### 4.2 人效上限

1. 每个 staff 同时有效的 coach 分配数最多 5，即严格 `1:5`。
2. 每个 staff 所分配 coach 名下的当前服务用户总数最多 150；达到任一上限都不得继续分配。
3. 第 6 个 coach 必须拒绝，不得先分配成功再在 UI 显示超限警告。
4. 150 用户按激活用户、当前打卡用户还是全部历史关系统计，以及 dormant 托管用户是否计入，为 `[待裁判确认]`。
5. 一个 coach 是否允许分配多个 staff 为 `[待裁判确认]`；即使允许，也不能突破每个 staff 的 5 教练与 150 用户上限。
6. coach 进入 buffer 不自动解除分配；进入 dormant 后用户转平台，staff 分配是否自动失效或保留历史为 `[待裁判确认]`。

### 4.3 分配原子性

- 创建、恢复、撤销分配均要求 `idempotencyKey` 和 `expectedVersion`。
- 创建时必须锁定 staff 容量版本，重新计算当前有效 coach 数和用户数；两个并发分配不得共同突破上限。
- 容量不足返回 `STAFF_CAPACITY_EXCEEDED`，不得返回用户清单或财务信息。
- 撤销后权限立即失效，历史工单和审计仍保留；缓存必须按授权版本失效。
- 不允许客户端直接写 `staff_coach_assignment`，也不允许 staff 为自己创建分配。

## 5. 雷达 RPC 授权

`get_coach_radar_v1()` 不接受客户端传入范围参数，服务端按以下规则生成可见集合：

1. 从 `auth.uid` 读取当前有效角色与授权版本。
2. coach 仅解析其当前 `referrer_id = coachId` 的用户关系。
3. staff 先解析 `state = active` 且在有效期内的 coach 分配，再解析这些 coach 的当前用户关系。
4. admin 按管理职责获得集合，但返回字段仍受雷达脱敏契约限制。
5.  dormant 生效后的用户归属为 `PLATFORM_ID`，原 coach 与其 staff 不得继续查看，除非另有平台授权。

返回字段、灯号和禁止项以 `coach-radar-desensitized-v1.md` 为唯一契约。staff 不得通过以下方式扩大范围：

- 传入其他 coachId、camper_code、邮箱或 auth.uid；
- 直接查询 `checkin_sync`、关系表、角色表或底层视图；
- 使用导出、搜索、分页总数、排序或错误详情推断不可见用户；
- 利用旧缓存、撤销前链接或修改前端角色标识继续访问。

## 6. 财务分润隔离

staff 对当前及未来所有财务分润能力默认拒绝，包括但不限于：教练差价、数据奖励、裂变奖励、奖励抵扣、收益负债、补货回款、结算单、财务 CSV 和相关聚合图表。

- 不得仅禁止某一个已知 RPC 名称；新增财务 RPC 必须默认拒绝 staff，并采用显式角色允许列表。
- staff 调用财务 RPC 返回 `FORBIDDEN`，不得返回金额、部分结果或可用于推断收益的错误详情。
- staff 的雷达结果不得夹带财务字段，服务工单不得复制分润内容。
- coach 查看本人财务也需独立财务权限，不因拥有 coach 角色自动获得全部平台财务。
- admin 的雷达权限不自动证明其财务权限；高敏财务仍应单独授权和审计。

## 7. 工单权限与字段最小化

staff 只能处理分配范围内的客情服务工单，例如黄灯跟进、红灯挽回和结营复购提醒。

- 工单仅包含不透明用户引用、灯号、阶段、原因码、责任人和处理状态。
- 不包含原始健康档案、联系方式明文、财务分润或完整产品码；实际联系方式如需用于电话／微信服务，必须另立受限联系契约 `[待裁判确认]`。
- 工单类型、处理 SLA、转派规则和关闭原因码为 `[待裁判确认]`。
- 分配撤销或用户托管后不得继续新建原范围工单；历史未结工单的处理方式与托管契约一致。

## 8. 角色变更与审计

以下事件必须追加审计：角色授予、角色变更、角色停用、分配创建、分配撤销、容量拒绝、越权访问和财务 RPC 拒绝。

- 审计只记录操作者、目标主体、角色、分配 ID、时间、结果和原因码，不记录雷达用户明细或财务金额。
- 角色或分配变化必须立即影响新请求；不得等待用户重新登录才撤权。
- 管理员不能仅凭伪造邮箱修改他人角色；所有管理命令需认证、授权和版本检查。
- 角色目录和分配关系的普通读取按最小字段返回，不能向 staff 暴露完整人员通讯录。

## 9. 错误码

- `UNAUTHORIZED`：未认证。
- `ROLE_REQUIRED`：无有效角色或角色已停用。
- `FORBIDDEN`：角色或分配范围不允许，包括 staff 调用财务 RPC。
- `STAFF_CAPACITY_EXCEEDED`：超过 5 教练或 150 用户上限。
- `ASSIGNMENT_CONFLICT`：分配状态或版本冲突。
- `ROLE_ASSIGNMENT_CONFLICT`：目标主体角色不匹配或存在未决角色冲突。
- `IDEMPOTENCY_CONFLICT`：相同幂等键对应不同分配或角色操作。

错误响应不得泄露其他教练、用户或财务记录是否存在。

- [ ] staff 只能查看当前分配教练的脱敏雷达，撤销后立即不可见。
- [ ] staff 对每一个财务分润 RPC 均为服务端拒绝，而非仅隐藏菜单。
- [ ] 第 5 个教练可分配，第 6 个被拒绝；150 用户上限同样在写入时校验。
- [ ] 两个并发分配不能突破任一容量上限。
- [ ] coach、staff、admin 均不能通过直接表、导出、缓存或错误详情绕过脱敏。
- [ ] dormant 后原 coach／staff 失去已转平台用户的雷达访问。
- [ ] 用户 `userCode` 与 `auth.uid` 不因角色或分配变化而改变。
- [ ] 角色、分配、容量拒绝和越权访问均有最小化审计。
