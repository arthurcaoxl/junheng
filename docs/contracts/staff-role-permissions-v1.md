# Staff 角色与权限契约 v1

- 状态：裁判终裁已落实，未实现
- 所属体系：10.1 打卡 App 业务重构契约
- 交付边界：仅逻辑契约；不包含 SQL、迁移、RPC 或前端实现

> 依据裁判终裁与 V7.1 运营指南，重点落实 4.1 工单、8.1 雷达 SOP、9.2 人效参考及 10.2 最小可见原则。

## 1. 目标与最小权限原则

本契约把现有 `camp_admins` 邮箱白名单扩展为受控业务角色目录，支持 `admin / coach / staff` 三类角色。

- `camp_admins` 是历史表名，不代表其中每行都是管理员。
- 角色只由受控服务端或 admin 管理，用户不得通过前端、JWT 自定义声明或修改本地存储自助提权。
- 默认拒绝：没有有效角色、角色停用、分配失效或权限无法证明时，不得读取业务数据。
- staff 的基础业务数据能力是查看被分配教练当前名下的脱敏雷达及处理相应服务工单；TASK-10.13-FINAL-CLEARANCE 仅追加第 3.1 节的直营库存定向例外。任何例外都不开放财务分润、员工管理、平台生成、他人库存或跨范围雷达。

## 2. `camp_admins.role` 逻辑变更

新增逻辑列：

| 字段 | 规则 |
| --- | --- |
| `role` | 必填枚举 `admin / coach / staff`。 |
| `is_active` | 停用后所有该角色权限立即失效。 |
| `auth_user_id` 或等效受限映射 | 用于把登录 `auth.uid` 与角色稳定关联；邮箱不能替代认证主体。 |
| `version / updatedAt / updatedBy` | 角色变化必须可并发控制、可审计。 |

- v1 每个 `auth.uid` 只能有一个有效角色，禁止通过叠加角色绕过 staff 限制。
- 历史白名单行不得仅凭邮箱自动获得新角色；上线前由 admin 逐行核验角色与 `auth_user_id` 映射，未核验行保持无业务权限。本契约不编写迁移。
- 邮箱变更不改变权限；匿名账号升级、认证主体更换或 auth 用户删除后的角色重绑与停用必须由 admin 人工复核，不自动继承旧邮箱权限。
- `service_role` 只存在于受控服务端，不得进入前端、仓库、错误日志或报告。

## 3. 权限矩阵

| 能力 | admin | coach | staff |
| --- | --- | --- | --- |
| 管理角色与 staff-coach 分配 | 允许 | 禁止 | 禁止 |
| 查看脱敏雷达 | 按管理职责 | 仅当前自己名下用户 | 仅被分配教练当前名下用户 |
| 处理雷达服务工单 | 允许 | 仅自己责任工单 | 仅分配范围内服务工单 |
| 查看原始 `records` | 不因 admin 身份自动获得；另行授权 | 禁止 | 禁止 |
| 查看原始 `height / weight / height_cm / initial_weight_kg` | 不通过雷达返回；其他管理能力另行授权 | 禁止 | 禁止 |
| 查看财务分润 RPC | 按财务权限另行批准 | 仅本人财务且另行批准 | **绝对禁止** |
| 管理产品码、撤销激活 | 按专门命令授权 | 仅本人被授权操作 | 仅第 3.1 节的本人被划拨库存与受控直推；其余禁止 |
| 执行休眠批处理 | 仅受控系统／专门管理命令 | 禁止 | 禁止 |
| 修改 `referrer_id` | 仅受控托管或人工裁定命令 | 禁止 | 禁止 |

### 3.1 平台直营员工库存定向例外（TASK-10.13-FINAL-CLEARANCE）

1. 仅有效 Admin 可通过 `allocate_codes_to_staff_v1(p_staff_id, p_count)` 从平台可用库存向有效 staff 划拨任意正整数盒。事务复用 `box_codes / coach_inventory / inventory_logs`，追加 `staff_allocated` 流水与 `staff_inventory_allocated` 审计；库存不足时码行、计数、流水与审计整体回滚。返回固定为 `{ok:true, allocatedCount:number}`。
2. 有效 staff 只能通过 `get_my_code_inventory / get_coach_inventory_v3` 读取 `auth.uid()` 本人名下 `unused` 且已划拨的码；不得传入持有者参数，不得读取其他 staff、coach 或平台库存。`get_my_access_profile.can_manage_inventory` 仅同步这一本人库存能力，不构成额外授权。
3. 有效 staff 可调用既有 `coach_push_code_v1`，但码必须为本人持有，目标关系必须同时满足 `valid_to IS NULL` 和“其当前 `referrer_id` 教练在该 staff 当前有效 `staff_coach_assignment` 范围内”。不满足时返回 `FORBIDDEN`，不得扩展为任意用户、历史归属或其他教练范围。
4. 直推仍只创建 `coach_push` 来源的 pending 申请，不能直接激活、改归属或扣库存。Admin 唯一终审保持不变；对 staff 持有码，`admin_review_box_code_activation_v2` 只有在目标为有效 staff、申请为 `coach_push` 且当前关系仍在该 staff 分配范围时才允许继续，终审归属仍为关系中的 coach，库存从 staff 持有者扣减。
5. staff 不得平台生成、向任何人划拨、管理员工或角色、补货申请、读取教练在审列表、终审或撤销激活；原雷达仍只有当前分配范围五字段及既有营期状态，财务权限继续绝对禁止。staff 停用或分配撤销后，新请求立即失去相应直推能力，历史库存与审计事实不改写。
6. `admin_search_staff_directory_v1(p_query)` 仅有效 Admin 可调用，按 email 模糊搜索有效 staff，空或 NULL 查询返回空，非空结果最多 10 条；字段与 `admin_get_staff_directory` 完全一致，不泄露 Admin、coach 或失效 staff。

前端菜单隐藏不是权限。所有 RPC、直接表访问、视图、导出、事件订阅和错误响应都必须执行同样的服务端授权。

## 4. Staff-Coach 分配关系

### 4.1 逻辑实体 `staff_coach_assignment`

| 字段 | 规则 |
| --- | --- |
| `assignmentId` | 不透明 ID。 |
| `staffId` | 必须对应有效 staff 角色。 |
| `coachId` | 必须对应有效 coach 角色。 |
| `state` | `active / revoked / expired`。 |
| `validFrom / validTo` | 分配有效期；历史不得覆盖删除。 |
| `assignedBy / assignedAt` | 仅 admin 或受控系统写入。 |
| `version` | 并发控制与审计。 |

### 4.2 人效软容量提示

指南 9.2 将 `1 名员工：5 名教练：150 名用户` 定义为服务容量参考，而不是强制拉新指标；裁判进一步明确其仅为软提示：

1. 每个 staff 当前有效分配 coach 数超过 5 时触发醒目 UI 红字警告；第 6 个及后续分配仍允许成功。
2. 每个 staff 所分配 coach 名下当前服务用户总数超过 150 时触发醒目 UI 红字警告；业务分配仍允许成功。
3. 两项均为治理提示，绝不得通过数据库外键、唯一约束、触发器、RPC 容量拒绝、服务端前置阻断或其他硬限制阻止分配。
4. coach 数按该 staff 当前有效且未过期的分配关系统计。用户数按这些 coach 当前有效 `referrer_id` 关系中的去重用户统计，不按打卡活跃度过滤，不包含已转 `PLATFORM_ID` 或仅历史存在的用户。
5. v1 不设置一名 coach 只能分配一名 staff 的唯一限制；多个 staff 可服务同一 coach，但每人仍受最小权限和相同软容量提示约束。
6. coach 进入 buffer 不自动解除分配；进入 dormant 后原分配历史保留，未失效分配也不授予已转平台用户的访问权，平台用户不再计入原 staff 容量。
7. 超过参考值时必须记录容量警告审计并生成治理跟进事项，由 admin 复盘工作量、调整分配或评估扩编；警告不阻断主流程。

### 4.3 分配原子性与警告

- 创建、恢复、撤销分配均要求 `idempotencyKey` 和 `expectedVersion`，用于防重和状态并发控制，不得用于实施容量硬限制。
- 创建与恢复时计算当前 coach 数和用户数，返回分配结果的同时返回软容量警告；即使超过 5 或 150，也必须允许业务继续。
- 分配页面、管理看板和后续容量变化均须显示醒目红字警告，并保留审计与治理跟进记录；不得只写日志而不提示。
- 撤销后权限立即失效，历史工单和审计仍保留；缓存必须按授权版本失效。
- 不允许客户端直接写 `staff_coach_assignment`，也不允许 staff 为自己创建分配。

## 5. 雷达 RPC 授权

`get_coach_radar_v1()` 不接受客户端传入范围参数，服务端按以下规则生成可见集合：

1. 从 `auth.uid` 读取当前有效角色与授权版本。
2. coach 仅解析其当前 `referrer_id = coachId` 的用户关系。
3. staff 先解析 `state = active` 且在有效期内的 coach 分配，再解析这些 coach 的当前用户关系。
4. admin 按管理职责获得集合，但返回字段仍受雷达脱敏契约限制。
5. dormant 生效后的用户归属为 `PLATFORM_ID`，原 coach 与其 staff 不得继续查看；旧分配、旧工单和旧缓存均不能形成平台用户权限。

10.5 返回字段统一为 `camper_code / weight_delta / waist_delta / bmi / alert_level`，以及确有必要时的批准库存汇总字段；后续恢复 `stage` 必须重新评审。`alert_level` 仅允许 `red / yellow / green`，由 SQL 层在服务端计算；staff 和其他前端角色均不得自行计算。其余禁止项以 `coach-radar-desensitized-v1.md` 为唯一契约。

staff 不得通过以下方式扩大范围：

- 传入其他 coachId、camper_code、邮箱或 auth.uid；
- 直接查询 `checkin_sync`、关系表、角色表或底层视图；
- 使用导出、搜索、分页总数、排序或错误详情推断不可见用户；
- 利用旧缓存、撤销前链接或修改前端角色标识继续访问。

## 6. 财务分润隔离

staff 对当前及未来所有财务分润能力默认拒绝，包括但不限于：教练差价、数据奖励、裂变奖励、奖励抵扣、收益负债、补货回款、结算单、财务 CSV 和相关聚合图表。

- 不得仅禁止某一个已知 RPC 名称；新增财务 RPC 必须默认拒绝 staff，并采用显式角色允许列表。
- staff 调用财务 RPC 返回 `FORBIDDEN`，不得返回金额、部分结果或可用于推断收益的错误详情。
- staff 的雷达结果不得夹带财务字段，服务工单不得复制分润内容。
- coach 查看本人财务也需独立财务权限，不因拥有 coach 角色自动获得全部平台财务。
- admin 的雷达权限不自动证明其财务权限；高敏财务仍应单独授权和审计。

## 7. 工单权限与字段最小化

staff 只能处理分配范围内的客情服务工单，包括黄灯跟进、红灯挽回、结营复购提醒和需升级事项。

- 工单仅包含不透明用户引用、`alert_level`、`stage`、原因码、责任人和处理状态。
- 处理节奏依指南为红灯优先、黄灯跟进、绿灯反馈，状态采用 `已触达 / 待回复 / 已解决 / 需升级`；异常未解决不得静默关闭。
- 工单不包含原始健康档案、联系方式明文、财务分润或完整产品码。v1 不在工单内提供明文联系方式，实际联系使用另行授权的运营渠道并保留触达结果。
- v1 按每日异常检查、每周复盘执行，不另设数字化 SLA 或提醒次数；转派必须保留原处理链。
- 分配撤销或用户托管后不得继续新建原范围工单；未结工单按托管契约转平台责任队列，原 staff 不得凭旧分配继续处理。

## 8. 角色变更与审计

以下事件必须追加审计：角色授予、角色变更、角色停用、分配创建、分配撤销、软容量警告、治理跟进、越权访问和财务 RPC 拒绝。

- 审计只记录操作者、目标主体、角色、分配 ID、时间、结果和原因码，不记录雷达用户明细或财务金额。
- 软容量审计记录触发时的 coach 数、去重用户数和警告类型，但不得记录用户清单；它不代表分配被拒绝。
- 角色或分配变化必须立即影响新请求；不得等待用户重新登录才撤权。
- 管理员不能仅凭伪造邮箱修改他人角色；所有管理命令需认证、授权和版本检查。
- 角色目录和分配关系的普通读取按最小字段返回，不能向 staff 暴露完整人员通讯录。

## 9. 错误码与警告标识

- `UNAUTHORIZED`：未认证。
- `ROLE_REQUIRED`：无有效角色或角色已停用。
- `FORBIDDEN`：角色或分配范围不允许，包括 staff 调用财务 RPC。
- `ASSIGNMENT_CONFLICT`：分配状态或版本冲突，不得用于容量拒绝。
- `ROLE_ASSIGNMENT_CONFLICT`：目标主体角色不匹配或角色冲突。
- `IDEMPOTENCY_CONFLICT`：相同幂等键对应不同分配或角色操作。
- `STAFF_CAPACITY_WARNING`：非阻断警告标识，可与成功分配结果同时返回，不是错误码，不得导致回滚或失败。

错误响应不得泄露其他教练、用户或财务记录是否存在。容量相关响应只能使用非阻断警告，不得造成分配失败或回滚。

## 10. 契约验收清单

- [ ] `camp_admins.role` 仅允许 admin／coach／staff，每个 `auth.uid` 只有一个有效角色，历史行未经核验无新增权限。
- [ ] staff 的雷达仍只覆盖当前分配教练，撤销或托管后立即不可见；库存例外不扩大雷达范围。
- [ ] 直营 staff 只能读取本人被划拨库存并向当前分配范围营员直推，不能读取他人库存、平台生成、划拨或管理员工。
- [ ] staff 对每一个财务分润 RPC 均为服务端拒绝，而非仅隐藏菜单。
- [ ] 第 6 个 coach 和超过 150 用户的分配均允许成功，同时出现醒目红字警告、审计和治理跟进。
- [ ] 不存在任何以 1:5 或 1:150 阻断分配的数据库、触发器、RPC 或服务端硬限制。
- [ ] coach、staff、admin 均不能通过直接表、导出、缓存或错误详情绕过脱敏。
- [ ] `alert_level` 由 SQL 层计算且仅含 red／yellow／green，staff 无原始字段可重建灯号。
- [ ] dormant 后原 coach／staff 失去已转平台用户的雷达和工单访问。
- [ ] 用户 `userCode` 与 `auth.uid` 不因角色、分配或托管变化而改变。
- [ ] 未修改 `storage-v3`，未混入 CEO 沙盘纯函数引擎代码。
